# 打洞模块设计

状态：草案 v0.9（2026-10-04，中转改为 UDP 中转为主、WS 中转兜底，6.2 增加中转报文类型 7~9，6.6、10.2 相应修改，详见 [data-channel.md](../protocol/data-channel.md)；v0.8 2026-10-04，新增 PCP/NAT-PMP 端口映射与 IPv6 打洞支持，见 12.5；打洞 S1/S3 跨服务器实测见 12.4；NAT 探测见 4.4；v0.5 2026-09-29）：地址探测借鉴 STUN 的机制，但改用私有的加密报文格式，避免被识别和屏蔽；探测服务器自行实现，部署在至少两台不同 IP 的机器上；提名报文改用两端 E2E 协商的密钥（见 [security.md](security.md) 9.5）

**用语**：本文的"设备"泛指运行打洞模块的一端，可以是节点（NAS 设备端、控制台节点），也可以是纯客户端；一次呼叫中两端的角色称为主叫与被叫（[security.md](security.md) 8.5）。

本文描述 NPF 的 NAT 穿透（打洞）模块：不依赖 libjuice，自行实现 NAT 探测、候选收集、同时打洞与暴力打洞，成功后把 UDP 路径交给 AnLiu。不使用 libjuice 的原因：libjuice（截至 v1.7.4）每个 agent 只有一个 UDP socket，候选上限 30 个，无法实现暴力打洞。

---

## 1. 目标与非目标

**目标**

1. 在两端都能访问 UDP 的前提下，尽可能提高直连成功率，尤其是"一侧对称型 NAT"的情况；
2. 线上没有固定协议特征：地址探测与打洞探测的报文全部加密、长度随机，不使用标准 STUN 报文（第 6 节）；
3. 打洞与中转并行：会话先经服务器中转开始传数据，打洞在后台进行，成功后无缝切换，失败不影响可用性；
4. 设备端保持轻量：单线程事件循环，不引入额外依赖；
5. 可观测：每次打洞尝试都上报 NAT 类型组合、所用策略、耗时与结果，用数据调参。

**非目标**

- 兼容标准 ICE（RFC 8445）或与 WebRTC 互通；
- TCP 打洞（成功率低，收益不值得复杂度）；
- 两端都是随机端口分配的对称型 NAT：这种情况直接走中转，不做尝试。

## 2. 术语：NAT 行为分类

按 RFC 4787 / RFC 5780，从三个维度描述 NAT，而不是"全锥 / 限制锥 / 端口限制锥 / 对称"四分类：

| 维度 | 取值 | 含义 |
|---|---|---|
| **映射行为** mapping | EIM（与目标无关） | 同一内部 socket 发往任何目标，都使用同一个公网 IP:端口 |
| | ADM（与目标地址有关） | 目标 IP 不同则映射不同 |
| | APDM（与目标地址和端口有关） | 目标 IP:端口 不同则映射不同，即通常说的"对称型" |
| **过滤行为** filtering | EIF | 映射建立后，任何外部地址都能发进来 |
| | ADF | 只接受本端发送过的目标 IP |
| | APDF | 只接受本端发送过的目标 IP:端口 |
| **端口分配** allocation | 保持端口 | 尽量让公网端口等于内部端口 |
| | 顺序分配 | 新映射的端口按固定步长递增（常见步长 1 或 2） |
| | 端口块 | CGNAT 给每个用户分配一段端口（常见 512~4096 个），在块内分配 |
| | 随机 | 在整个端口范围内随机分配 |

后文把映射行为为 EIM 的一侧称为**易侧（easy）**，映射行为为 ADM/APDM 的一侧称为**难侧（hard）**。决定打洞策略的主要是映射行为和端口分配方式，过滤行为只影响"谁先发包"。

## 3. 总体流程

```
设备启动 / 网络变化
   │
   ▼
① NAT 探测（周期性，结果缓存为 NAT 画像）
   │
会话建立（信令）：中转路径立即可用，AnLiu 连接先跑在 UDP 中转上（UDP 不通时走 WS 中转，不打洞）
   │
   ▼
② 候选收集：host（IPv4/IPv6）、公网映射、端口映射（UPnP/PCP）、预测候选
   │
   ▼
③ 经信令交换：NAT 画像 + 候选 + 打洞密钥
   │
   ▼
④ 选择策略（按双方画像查决策表，第 7 节）
   │
   ▼
⑤ 服务器下发同步开始指令 → 双方按计划发送探测包
   │
   ├── 成功：选定路径 → ⑥ 移交给 AnLiu，切换出中转
   └── 失败：留在中转；按退避策略稍后重试
   │
   ▼
⑦ 路径保活与失效检测：直连失效 → 回退中转 → 重新打洞
```

## 4. NAT 探测

### 4.1 探测服务器

NAT 探测借鉴 STUN（RFC 8489）的 Binding 机制：设备发送请求，服务器在响应中返回它看到的源地址（公网映射地址）。报文不使用标准 STUN 格式，而是 6.4 定义的加密报文，避免被识别和屏蔽。探测服务器**自行实现**（Go，服务器端 `natprobe` 模块），不依赖第三方公共 STUN。

一台机器只有一个公网 IP，因此"不同 IP"要由**不同机器**提供。每台探测服务器在自己的 IP 上监听两个端口，探测时从两台机器中选出 3 个端点：

| 端点 | 位置 | 用途 |
|---|---|---|
| E1 = IP_A:P1 | 服务器 A | 基准 |
| E2 = IP_A:P2 | 服务器 A 的第二个端口 | 判断映射是否与目标端口有关 |
| E3 = IP_B:P1 | 服务器 B | 判断映射是否与目标地址有关 |

- **部署要求**：至少两台公网 IP 不同的机器运行探测服务。两台机器之间不需要任何协作，只要 IP 不同即可；可以是同一云厂商、同一地域的两台机器（时延相近，重传超时更好设置）；
- **部署形态**（2026-10-19 改）：`natprobe` 内嵌在 `npf-server` 中运行（`probe_listen`、`probe_public`），每台信令服务器同时是一台探测服务器，用的就是 `server.json` 里的 `probe_master`、`ticket_secret`。原来的独立程序 `npf-probe` 已删除：每台信令服务器本来都跑探测，独立程序只多出一个服务、一份重复的秘密文件和一个部署角色。它无状态、流量很小（每次探测十几个小包）；
- **端点由信令服务器在登录时下发**（2026-10-19 改，signaling.md `welcome` 的 `probe`，`keys` 与 `probe` 事件）：E1、E2 是这台服务器自己的两个端口，E3 是另一台在线、公网 IP 不同的服务器的第一个端口（按 `server_id` 取这台之后的下一台，各台服务器的客户端分散到不同的 B）。服务器从 Redis 的 `srv:` 记录得知其他服务器的探测地址和是否在线（每 5 秒），Redis 不可用时沿用最后一次的；端点变了就推送 `probe` 事件，客户端重新测一次。原来端点写在签名的服务器列表里：要在签名前把"另一台的地址"拼进每台服务器的条目（正式部署时漏拼过，客户端一直判断不出映射类型），改地址要重签列表，列表也不知道 B 是否还活着。经 Noise 认证的信令通道下发，与签名列表一样不能被篡改，而且探测本来就要等登录拿到密钥和票据之后才开始；
- **认证**：请求与响应都是整包认证加密（6.2），请求还携带信令服务器签发的票据（6.4）。服务器对未认证的请求不作任何回应，不会被滥用，也不会暴露服务类型；设备只采信通过认证的响应，防止伪造响应导致误判；
- **限流**：令牌桶，每个 `id`（票据中）平均每秒 20 个请求、每个源 IP 平均每秒 200 个（同一 CGNAT 公网 IP 后面可能有很多设备，按 IP 限得太紧会误伤），突发量均为每秒速率的 2 倍；超出的静默丢弃。突发量是必要的：一次完整探测要发 3 + K 个请求再加重传，实测用固定的一秒窗口时，K = 16 的探测会被截掉一部分；
- **只有一台机器时**（早期阶段，或另一台下线时）：只能得到 E1、E2，可以区分 EIM 与 APDM，无法区分 ADM；见 4.2 的降级处理。

### 4.2 探测步骤

设备用**同一个 socket** 依次向 E1、E2、E3 发送 Binding 请求（每个请求最多重发 3 次，间隔 200/400/800 ms），得到映射地址 M1、M2、M3：

| 观察结果 | 结论 |
|---|---|
| M1 = M2 = M3 | EIM |
| M1 = M2 ≠ M3 | ADM |
| M1 ≠ M2 | APDM |
| 映射端口 = 本地端口 | 保持端口 |
| 没有 E3（只部署了一台）或 E3 无响应 | M1 ≠ M2 时仍判为 APDM；M1 = M2 时画像记为 `UNKNOWN`，按难侧处理 |

**公网 IP 不一致**：M3 的 IP 通常应与 M1 相同。若不同，说明 CGNAT 对不同目标使用了不同的公网 IP（非"成对"地址池），这种 NAT 按难侧处理，且打洞时对端喷包的目标 IP 不确定，暴力打洞（S3）不适用，直接走中转。

**端口分配方式**：再新建 K 个 socket（默认 K = 8），在 200 ms 内依次向 E1 发请求，记录映射端口序列：

- 相邻差值恒定（例如 +1、+2）→ 顺序分配，记录步长；
- 全部落在一个较小的区间内 → 可能是端口块，记录区间 [min, max]，多次探测后逐步修正；
- 无规律 → 随机分配。

**过滤行为**：需要服务器从另一个地址回复（RFC 5780 CHANGE-REQUEST），在两台机器之间实现需要协作转发。它不影响策略选择，因此不探测；以后若需要诊断，可以让服务器 A 通过服务器之间的连接请求服务器 B 代为回复。

**公网 IPv4 检测**：若映射地址等于本机某个网卡地址，说明设备直接有公网地址（无 NAT），画像标为 `open`。

### 4.3 NAT 画像

```c
typedef struct npf_nat_profile {
    uint8_t  mapping;        /* EIM / ADM / APDM / UNKNOWN */
    uint8_t  allocation;     /* PRESERVE / SEQUENTIAL / BLOCK / RANDOM / UNKNOWN */
    int16_t  seq_delta;      /* 顺序分配的步长 */
    uint16_t block_lo, block_hi;   /* 端口块区间（观测值） */
    uint8_t  open;           /* 有公网地址、无 NAT */
    uint8_t  has_ipv6;       /* 有全局 IPv6 地址 */
    uint8_t  upnp, pcp;      /* 端口映射协议可用 */
    uint32_t measured_at;    /* 探测时间 */
} npf_nat_profile;
```

- 设备启动、网卡地址变化、WebSocket 重连后的公网 IP 变化时重新探测；此外每 30 分钟探测一次；
- 画像随设备上线信息上报给服务器，服务器可以做统计，并在会话建立时直接下发给对端，省去一次往返。

### 4.4 实现与实测（2026-10-03）

- **代码**：设备端 `src/crypto/siv.c`（SIV 封装）、`src/ice/bind.c`（报文编解码）、`src/ice/natprobe.c`（探测与判定，仅 IPv4；节点在事件循环上运行 `npf_natprobe_start`，主 socket 上探测服务器的应答由节点的数据报分发交给它；调试工具用同步的 `npf_natprobe_run`）；调试工具 `client/tools/npf-natprobe`；服务器端 `server/internal/natprobe` 与独立程序 `server/cmd/npf-probe`（`serve` / `key` / `ticket` / `gen-secrets`）。C 与 Go 的加密实现共用一组已知答案（含跨语言向量）；
- **端口分配的区间按环形计算**：实测阿里云 NAT 网关的映射端口分布在 [约 60000, 65535] ∪ [1024, 约 10000]，是跨过 65535 的一整段。区间取"覆盖全部样本的最小环形区间"，`block_lo > block_hi` 表示跨越；
- **多 IP 主机要按 IP 分别监听**：监听通配地址时，内核可能用另一个地址作为回复的源地址，设备会因"回复来源与请求目标不一致"而丢弃。云主机通常只有一个地址，不受影响；
- **实测**（两台探测服务器 A、B，UDP 9910 / 9911）：

| 设备 | 网络 | M1 / M2 / M3 | 端口分配 | 画像 |
|---|---|---|---|---|
| 主机 1 | 云服务器，经云厂商的 NAT 网关 | 三个端点映射各不相同 | 16 个新 socket 的端口集中在 [约 60000, 约 9800]（跨 65535） | APDM + RANDOM |
| 主机 2 | 云服务器，自有公网地址 | 相同，且等于本地端口 | 全部保持本地端口 | EIM + PRESERVE |
| 主机 3 | 家庭宽带的 NAT 后 | 相同，且等于本地端口 | 全部保持本地端口 | EIM + PRESERVE |
| 本机 | WSL2 + Clash TUN | 无响应 | — | UDP 被代理阻断（AnLiu 测试中的已知情况） |

  主机 1 与主机 2 / 3 之间正好对应 7.4 的 S3 场景（一侧 EIM、一侧难侧），可以作为暴力打洞的实测环境。

## 5. 候选

| 类型 | 来源 | 优先级 |
|---|---|---|
| `host6` | 本机全局 IPv6 地址 | 最高：通常只需在防火墙上打洞 |
| `mapped` | UPnP IGD / NAT-PMP / PCP 在路由器上建立的端口映射 | 高：相当于公网地址 |
| `host4` | 本机私网 IPv4 地址（同一局域网或同一 NAT 下直连） | 高 |
| `srflx` | 打洞所用 socket 向探测服务器请求得到的公网映射地址 | 中 |
| `pred` | 按画像预测出的端口（顺序分配时为映射端口 + k × 步长） | 低 |

说明：

- **端口映射**：设备端启动时尝试 PCP → NAT-PMP（**不支持 UPnP**，见下），成功后定期续期（租期 1 小时，提前 10 分钟续期），退出时删除。NAS 大多在家庭路由器后面，这一项往往直接解决问题。已实现于 `ice/portmap.c`：PCP（RFC 6887）与 NAT-PMP（RFC 6886），都向默认网关 UDP 5351 发送，先试 PCP（较新、直接返回外部地址、支持 IPv6）再退回 NAT-PMP；网关从 `/proc/net/route` 读取。工具 `client/tools/npf-portmap`；
- **只收集必要的 host 地址**：排除回环、链路本地、docker/虚拟网卡（按网卡名与地址段过滤，可配置）；
- 候选中的地址经信令发给对端，对端能看到本端的内网地址。这是 ICE 的通常做法；有顾虑时可以只发送私网地址的哈希，由对端判断是否可能同网段，作为可选项。

## 6. 报文格式

打洞相关的 UDP 报文有两类：设备与探测服务器之间的**地址探测报文**（取代标准 STUN），设备与设备之间的**打洞探测报文**。两类报文与 AnLiu 数据报共用同一个 UDP socket，采用同一种封装：**整包认证加密，线上没有任何明文字段、固定长度或固定端口**。

### 6.1 借鉴 STUN 的什么，改掉什么

标准 STUN 的报文头是明文的：前两位固定为 0，第 4~7 字节是固定的 magic cookie `0x2112A442`，默认端口 3478，报文长度按 4 字节对齐。一条规则就能识别并屏蔽全部 STUN 流量。本协议保留 STUN 的机制，改掉它的线上形态：

| STUN 的设计 | 本协议 |
|---|---|
| 请求 / 响应模型，Binding 请求返回"服务器看到的源地址" | **保留** |
| 96 位随机事务 ID，响应原样带回，用于匹配请求与重传 | **保留** |
| 从收到请求的端口回复，客户端据此区分端点 | **保留** |
| 重传：200/400/800 ms 指数退避 | **保留** |
| MESSAGE-INTEGRITY（HMAC）防伪造 | 改为整包认证加密（6.2），同时提供完整性与机密性 |
| XOR-MAPPED-ADDRESS：地址与 magic cookie 异或，防止中间设备（ALG）改写报文中的 IP | 不再需要：地址位于密文中，中间设备看不到也改不了 |
| 明文报文头、magic cookie、TLV 属性 | 去掉：密文之外只有 12 字节看似随机的 tag |
| 报文长度 4 字节对齐、常见长度集中在 20~100 字节 | 随机填充，长度在区间内均匀分布（6.3） |
| 固定端口 3478 / 5349 | 端口由服务器下发，可以随时更换（6.7） |

### 6.2 通用封装

与 AnLiu 相同的 SIV 构造（ChaCha20 + SipHash-2-4，12 字节 tag），但使用独立的密钥派生标签，确保三类报文在密码学上互不混淆：

```
wire = tag(12) || ChaCha20(k_enc[dir], nonce = tag, P)
tag  = SipHash-2-4-128(k_mac[dir], P)[0..11]

P    = type(1) | flags(1) | body_len(2) | txid(12) | ts_ms(4) | body | pad
```

| 字段 | 说明 |
|---|---|
| `type` | 报文类型，见 6.4、6.5 |
| `flags` | 保留，发送时置 0 |
| `body_len` | `body` 的长度；其后到报文末尾都是填充 |
| `txid` | 96 位随机事务 ID（与 STUN 相同），响应原样带回 |
| `ts_ms` | 发送方的毫秒时钟，用于计算 RTT，服务器用它做时间窗检查 |
| `pad` | 随机字节 |

**编码**：整数一律小端序（与 AnLiu 一致），IP 地址按网络字节序原样存放。`type` 编号：`BIND_REQ` = 1、`BIND_RESP` = 2、`PROBE` = 3、`PROBE_ACK` = 4、`NOMINATE` = 5、`NOMINATE_ACK` = 6；UDP 中转使用 `RELAY_BIND` = 7、`RELAY_BIND_ACK` = 8、`RELAY_DATA` = 9（`RELAY_DATA` 用紧凑报文头，见 [data-channel.md](../protocol/data-channel.md) 9.2）。KDF 标签（12 字节，作为派生块的 ChaCha20 nonce）：地址探测为 `NPF-PROBE-v1`，打洞探测为 `NPF-PUNCH-v1`，提名为 `NPF-NOMIN-v1`，中转绑定为 `NPF-RBIND-v1`，中转数据为 `NPF-RELAY-v1`。

**方向密钥**：沿用 AnLiu 的做法，按发送方向派生两套密钥（请求方向 / 响应方向，或打洞的主叫 / 被叫方向）。把请求原样反射回请求方会因为密钥方向不匹配而认证失败，攻击者无法用抓到的请求冒充响应。

**需要 AnLiu 导出加密原语**（目前是 `anliu.c` 内部的静态函数），或在 `src/crypto` 中实现一份相同的构造。

认证失败的报文**静默丢弃，不作任何回应**。这对探测服务器同样适用：未认证的请求得不到任何响应，主动探测者无法确认端口上运行的是什么服务。

### 6.3 长度

- 每个报文的总长度在该类型的区间内**均匀随机**（见 6.4、6.5），不做对齐；
- 地址探测请求**不短于**对应的响应：服务器响应的长度不超过它收到的请求，避免被用作 UDP 反射放大攻击的放大器；
- 服务器可以通过下发配置调整各类型的长度区间。

### 6.4 地址探测报文（设备 ↔ 探测服务器）

| type | 方向 | body |
|---|---|---|
| `BIND_REQ` | 设备 → 服务器 | `ticket` |
| `BIND_RESP` | 服务器 → 设备 | `family(1) | port(2) | addr(4 或 16)` 服务器看到的源地址；`srv_time_ms(8)` 服务器时间 |

长度区间：`BIND_REQ` 为 [96, 200] 字节，`BIND_RESP` 为 [64, 请求长度]。

`BIND_RESP` 的 `txid` 与 `ts_ms` 都**原样带回请求中的值**：设备用 `txid` 匹配请求，用 `ts_ms` 计算 RTT（每次重发都重新加密、带新的 `ts_ms`，因此 RTT 不受重传影响）。

**密钥**：所有探测服务器共享一组 `probe_key`，每天轮换：`probe_key = HMAC-SHA256(probe_master, "npf-probe-key-v1" | day)`，`day` 为 UTC 天数（Unix 秒 / 86400，4 字节小端）。服务器只需配置 `probe_master`，无需每天下发新密钥。设备经 WSS 从信令服务器获得当前与下一个 `probe_key`。密文之外没有密钥编号，服务器依次用当前密钥和上一个密钥尝试验证（轮换交替期内最多两次）。

**票据（ticket）**：`probe_key` 由所有设备共享，只能证明"持有固件的一方"。为了能按设备限流、吊销，请求中还携带信令服务器签发的票据：

```
ticket = id(8) | expire(4) | mac(16)
mac    = HMAC-SHA256(ticket_secret, id | expire)[0..15]
id     = 设备号或 client_id（见 security.md 第 6、8 节）
```

`ticket_secret` 只在服务器端（信令服务器与探测服务器共享），票据有效期 24 小时，设备随 `probe_key` 一起获取。探测服务器验证票据**无需查询任何状态**，并按 `id` 与源 IP 两个维度限流。

**时间窗**：服务器拒绝 `ts_ms` 与自身时间相差超过 60 秒的请求（设备首次探测前先用 WSS 上服务器下发的时间校准偏移）。`srv_time_ms` 也用于第 9 节的同步开始。

**重放**：攻击者重放抓到的请求（即使伪造源地址），只会让服务器向该源地址发送一个不长于请求的响应，没有放大效果；加上按目标 IP 的限流，无法被用于反射攻击。

### 6.5 打洞探测报文（设备 ↔ 设备）

打洞报文使用两把密钥，封装方式都与 6.2 相同（各方向密钥按 6.2 从基础密钥派生）：

- **`punch_key`**：会话建立时服务器生成的随机 32 字节，通过 WSS 下发给双方，保护 `PROBE` / `PROBE_ACK`。这样不必等 E2E 握手完成就能开始打洞。服务器知道它不影响数据安全：数据由 AnLiu 加密，AnLiu 的会话密钥由两端端到端协商（Noise），服务器不知道；
- **`nominate_key`**：由两端的 E2E 握手派生（[security.md](security.md) 9.5），服务器不知道，保护 `NOMINATE` / `NOMINATE_ACK`。服务器即使伪造探测报文，也无法让双方提名一条错误的路径。

| type | body |
|---|---|
| `PROBE` | `session_id(8) | sock_idx(2)` |
| `PROBE_ACK` | `session_id(8) | sock_idx(2) | family(1) | port(2) | addr(4 或 16)` 我看到的你的源地址，用于发现对端反射地址 |
| `NOMINATE` / `NOMINATE_ACK` | `session_id(8)` |

- `session_id`：打洞会话 ID，用于在同一 socket 上区分多个并发打洞会话；
- `sock_idx`：发送方的 socket 编号（暴力打洞时标识是哪个 socket）；
- 长度区间：[64, 256] 字节。

### 6.6 同一 socket 上的分发

同一 socket 上收到的 UDP 报文都是"12 字节 tag + 密文"，按上下文决定尝试顺序：

1. 本 socket 有发往该源地址的未完成 `BIND_REQ`：先用 `probe_key` 验证；源地址是 UDP 中转服务器：先用该中转分配的 `alloc_key` 验证（data-channel.md 9.2），成功后取出 AnLiu 数据报交给 AnLiu；
2. 打洞进行中（路径尚未移交 AnLiu）：先用 `punch_key` 验证，再用 `nominate_key`（E2E 握手完成后才有），都失败再交给 AnLiu；
3. 路径已移交：先交给 AnLiu（`anl_peek_conv` / `anl_input`），失败再用 `punch_key` 验证（对端可能还在发迟到的探测报文）；
4. 都失败：丢弃并计数（`rx_auth_fail`）。

按上下文排序后，绝大多数报文一次验证就能命中；最坏情况下一个报文做三次 SipHash + ChaCha20，1400 字节约 3~6 µs，对 NAS 的报文速率可以接受。

### 6.7 其他抗屏蔽措施

报文格式只解决"按内容识别"。其余可被利用的特征及对策：

| 特征 | 对策 |
|---|---|
| 固定端口 | 探测服务器的端口由服务器下发，每个节点可以监听多个端口，随时更换；不使用 3478、19302 等 STUN 常见端口 |
| 服务器 IP | 多个探测节点，列表经签名下发（与信令服务器列表相同的机制），被封的节点从列表中剔除并补充新节点 |
| 报文长度 | 均匀随机，见 6.3 |
| 主动探测 | 服务器对未认证报文不作任何回应 |
| 时序 | 地址探测本身是低频、少量的报文，不做处理；打洞阶段的高频发包无法隐藏，只能靠限速（第 8 节）降低显著性 |

**局限**：整包随机、没有任何可识别结构，本身也可能成为一种特征。已有研究表明，部分审查系统会针对"完全加密、无法识别协议"的流量做启发式屏蔽（公开研究主要针对 TCP，对 UDP 的处理尚不清楚）。本协议无法消除这一风险，兜底方案是独立 WSS 连接上的 WS 中转（与普通 HTTPS 流量无法区分，见 [data-channel.md](../protocol/data-channel.md) 第 10 节），UDP 被阻断时服务照常可用。

## 7. 策略

### 7.1 决策表

按双方画像选择策略，可以并行执行多个策略。本端 A、对端 B：

| A \ B | open / mapped | EIM | ADM/APDM 顺序分配 | ADM/APDM 端口块 | ADM/APDM 随机 |
|---|---|---|---|---|---|
| **open / mapped** | 直连 | 直连（B 主动） | 直连（B 主动） | 直连（B 主动） | 直连（B 主动） |
| **EIM** | | S1 同时打洞 | S2 端口预测 | S3 生日悖论（缩小范围） | S3 生日悖论 |
| **ADM/APDM 顺序分配** | | | S2 双向预测（尝试） | 中转 | 中转 |
| **ADM/APDM 端口块** | | | | 中转 | 中转 |
| **ADM/APDM 随机** | | | | | 中转 |

另外：

- **S0 IPv6**：双方都有 `host6` 时，与上表并行执行，优先级最高；
- **同一公网 IP**：双方 `srflx` 的 IP 相同，说明在同一个 NAT 后面，优先尝试 `host4` 直连；
- 画像为 `UNKNOWN` 的一侧按"ADM/APDM 随机"处理。

### 7.2 S1：同时打洞（双方都是 EIM）

双方同时向对方的所有候选发送 `PROBE`，间隔 50 ms，持续 2 秒；之后每 200 ms 一次，直到超时（默认 5 秒）。由于双方都是 EIM，各自的映射在第一次发包后就固定了，对方的过滤规则也会因为本端先发过包而放行。

### 7.3 S2：端口预测（对方是顺序分配）

难侧 B 在打洞开始时先向探测服务器发一次请求，得到最新的映射端口 p0，经信令告诉 A；随后 B 用新 socket 向 A 发包，这个新映射的端口大概率是 p0 + δ、p0 + 2δ、……（期间可能被 B 所在网络的其他连接占用几个）。A 向 [p0 + δ, p0 + W·δ] 范围（默认 W = 32）喷包。

"双向预测"（两侧都是顺序分配）：两侧同时按对方的预测端口喷包，窗口各 32，成功率取决于两侧网络的其他流量，属于"尝试一下，失败走中转"。

**预测落空后改全范围**（2026-10-15）：同一 NAT 向不同目标分配的端口可能不连续（手机移动卡 APDM：向一台服务器的两个端口给了 45986、45987，向另一台给了 22489），按探测服务器那边算出的范围（S2 的 `pred`，或 BLOCK 的端口段）喷射就会全部落空。服务器记下带范围的那一轮，它失败后，这个会话以后的轮次都不带范围（普通 S3，喷射全部端口）。另外，UDP 中转在打洞期间绑不上时，打洞失败后先再试一次 UDP 中转，还不行才退到 WebSocket 中转（WS 中转上的会话以后不能再打洞）。

实现（2026-10-06）：不在打洞开始时另做一次请求和信令往返，而是用 NAT 探测时最后观测到的映射端口加步长作为 `pred` 候选随候选一起发出；服务器给 `strategy: "S2"`，执行上就是 S3：难侧开 N 个新 socket，易侧向 `[pred, pred + 4N·δ]` 喷射（留出期间其他连接占用的端口）。探测时间离呼叫越久，预测越偏，范围放宽到 4N 就是为此；双向预测未实现。

### 7.4 S3：生日悖论暴力打洞（一侧 EIM，一侧难侧）

设 A 为易侧（EIM），B 为难侧。

1. **B（难侧）** 开 N 个 socket（默认 N = 256），每个 socket 向 A 的 `srflx` 地址（固定端口）发 `PROBE`。每个 socket 都会在 B 的 NAT 上创建一个新映射，公网端口未知；
2. **A（易侧）** 用同一个 socket（A 是 EIM，映射固定）向 B 的公网 IP 上的随机端口喷 `PROBE`，总数 M；
3. A 的某个探测包命中 B 的某个映射端口时：
   - 该映射是 B 的 socket k 发往 A 时创建的，B 的 NAT 允许 A 的地址进入（过滤规则满足），于是 B 的 socket k 收到 `PROBE`；
   - B 的 socket k 回 `PROBE_ACK`。此时 A 已经向这个端口发过包，A 的 NAT 也放行，于是 A 收到应答，双向打通；
4. B 关闭其余 N − 1 个 socket。

命中概率（端口空间约 64512 个）：

```
P(成功) ≈ 1 − exp(−N·M / 64512)
```

| N（难侧 socket 数） | M（易侧探测数） | 成功率 |
|---|---|---|
| 256 | 174 | ≈ 50% |
| 256 | 512 | ≈ 87% |
| 256 | 1024 | ≈ 98% |
| 128 | 1024 | ≈ 87% |

**端口块缩小范围**：如果 B 的画像是端口块 [lo, hi]，A 只在这个区间内喷包，端口空间从 64512 缩小到 (hi − lo + 1)，同样的 M 成功率大幅提高。例如区间为 2048 个端口时，N = 64、M = 256 就能达到约 99.97%。

**发送节奏**（默认值，均可配置）：

| 参数 | 默认 | 说明 |
|---|---|---|
| 难侧 socket 数 N | 256 | 受 fd 上限与 CGNAT 端口配额约束，见 8 节 |
| 难侧重发 | 每个 socket 每 1 秒重发一次 | 保持映射、弥补丢包 |
| 易侧喷包速率 | 200 包/秒 | 约 5 秒发完 1024 个 |
| 易侧总数 M | 1024 | 端口块时取 min(1024, 区间大小) |
| 超时 | 8 秒 | |

**端口选择**：易侧按随机排列遍历候选端口，不重复发送同一端口；跳过 1024 以下端口。

### 7.5 低 TTL 预热（可选）

在 S1/S3 中，先发送的一侧的包到达对方 NAT 时，对方可能还没有建立映射，这些包会被丢弃；部分 NAT 对"未请求的入站包"有惩罚行为（例如回 ICMP、临时拉黑源地址）。可选的做法是：前几轮探测包把 IP TTL 设为较小值（例如 3~5，可按 traceroute 结果调整），让它们只在本端 NAT 上创建映射、在到达对方 NAT 之前被丢弃；等对方预热完成（由服务器同步时间点决定）后，再用正常 TTL 发送。默认关闭，由统计数据决定是否启用。

## 8. 资源与安全约束

| 约束 | 默认 | 原因 |
|---|---|---|
| 单次打洞的 socket 数 | ≤ 256 | 文件描述符；CGNAT 通常给每个用户 512~4096 个端口，开太多会耗尽配额，影响用户的其他连接 |
| 全局并发打洞会话 | ≤ 4 | NAS 可能同时被多个客户端访问 |
| 单次打洞发包总数 | ≤ 2000 | 避免被识别为端口扫描 |
| 发包速率 | ≤ 200 包/秒 | 同上；家用路由器处理新建映射的能力有限 |
| 同一对端的重试 | 失败后 10 秒、30 秒、1、2 分钟，之后每 3 分钟，一个会话最多 10 轮（signaling.md） | 对称型 NAT 的环境短时间内不会变化 |
| 主叫一方同时进行的难侧打洞 | 1 个，socket 不到应得的一半时也不打 | 难侧每个 socket 在运营商 NAT 上占一个端口。2026-10-15 手机（移动卡，APDM，每个用户约 500 个端口）：两个难侧打洞同时进行（512 个）时，新的 UDP 目标全部不通——中转绑不上、NAT 探测没有回应，会话掉到 WS 中转，探测失败还让节点以为没有 UDP。现在这一轮让出去，前一个打洞结束、交还端口后立即要新一轮（不计入 10 轮）；改后同一张卡 8 台设备的 UDP 中转全部绑上，30 秒内 7 台直连 |
| 两个难侧打洞之间 | 间隔 15 秒（主叫一方）；等着的会话中有连接的先打 | 难侧打洞的 socket 关了，运营商 NAT 还要过一阵才回收它们占的端口，紧接着再打一轮会叠在上面；间隔期间会话照常走中转。有页面在用的会话优先，没有连接的排在后面（2026-10-15） |
| 按需连接设备 | 手机 App：`peer_idle` 180 秒；电脑、NAS：0（一直连接） | 端口主要花在打洞上：已保存的设备一直连着时，应用启动、网络切换、挂起恢复都要把每台设备重新打一遍。按需时不用的设备不建会话、不打洞、不保活：用到它的转发时才建（连接先等着，最多 30 秒），最后一个连接结束 `peer_idle` 秒后断开；`npf node wake` 提前建（控制台打开设备详情、资源列表没听到过时）。有 `-R` 映射的设备一直连接（对方随时可能用）。优点：省端口、省电、省流量，网络切换只重连在用的；不足：第一次打开页面要等会话（先走中转，约 1～2 秒），设备发布的资源只在连着时更新 |
| 打洞期间中转绑不上 | 等打洞结束再试（最多 15 秒），仍不行才用 WS 中转 | 同上：端口被打洞占着时绑不上，打洞结束后立即能绑 |
| NAT 探测没有回应 | 5 秒、20 秒、1 分钟、3 分钟后再测；再测有回应时，这期间走 WS 中转的主叫会话结束、重连（走 UDP） | 同上：一次失败曾让手机一个小时都以为没有 UDP；2026-10-15 应用重启后第一次探测没有回应，七个会话全部直接走 WS 中转（没有 UDP 时不打洞、不试 UDP 中转）并一直留在那里 |
| 暴力打洞开关 | 服务器可按设备/地区下发关闭 | 出现运营商投诉或路由器异常时可远程关闭 |

- **CGNAT 配额保护**：难侧新建 socket 时，若连续多次探测到的映射端口与已有映射重复，或向探测服务器的请求开始失败，说明配额吃紧，立即停止新建；
- **打洞成功后立即关闭多余的 socket**，让 NAT 尽早回收映射；
- 探测包认证失败时静默丢弃，不回应任何未认证的包，避免被主动探测识别。

## 9. 同步与信令

打洞相关的信令消息的字段定义见 [signaling.md](../protocol/signaling.md) 的"呼叫与端到端连接"一节：

| 消息 | 方向 | 内容 |
|---|---|---|
| `nat_report` | 设备 → 服务器 | NAT 画像（上线时、变化时、周期探测后上报） |
| `call` / `incoming` 应答 | 主叫 → 服务器；被叫 → 服务器 | 各自的画像与候选，与 E2E 握手消息一起发送 |
| `punch_start` | 服务器 → 双方 | 所选策略、角色（主叫为控制方）、易侧 / 难侧、`punch_key`、开始时刻 `start_at` |
| `punch_result` | 双方 → 服务器 | 结果、选中的路径、耗时、发包数（用于统计） |
| `punch_request` | 主叫 → 服务器 → 被叫 | 退避时间到或网络变化后，请求新一轮打洞 |

**同步开始**：`punch_start` 中给出**服务器时间的绝对时刻** `start_at`，取"当前时间 + 两侧单向时延的较大值 + 100 ms 余量"。双方用登录时的 `welcome.time` 与 `BIND_RESP` 中的服务器时间校准各自的时钟偏差，在 `start_at` 开始发包，误差在几十毫秒内。不用"按 RTT 推迟发送"的办法，是因为双方可能连在不同的服务器上，任何一台服务器都不知道两侧的 RTT。

对 S3 来说，难侧应当比易侧**稍早**开始（默认提前 100 ms），先把映射建立起来。

**主机防火墙**（2026-10-06 实测）：macOS 应用防火墙对不在允许列表中的程序，若一个 UDP 流的第一个报文是对方主动发来的，会封住这个流（双向）几十秒。所以这类主机必须先发：防火墙开启时节点提前 300 ms 开始发探测（`punch_lead_ms`）。对方在自己开始前收到的探测直接丢弃。打洞要等端到端密钥就绪才能开始，而口令配对（三条握手消息，最后一条由主叫发出）的被叫拿到密钥时往往已过开始时间：2026-10-06 实网组合测试中一台 Linux 主机呼叫一台 Mac（被叫，跨服务器）5 次全部失败，Mac 收到 `punch_start` 后约 200 ms 才完成握手，Linux 主机的探测先到，流被封住（Mac 收到 0 个，Linux 主机收到 192 个）。现在有防火墙的节点收到 `punch_start` 时立即向对方各候选发两次 1 字节报文，先建立出方向的流，再按计划打洞；对方节点静默丢弃这种报文。双方都在这类防火墙后面、又在同一局域网时，同步误差大于单向时延，仍可能互相封住，靠重新打洞或在防火墙中放行解决。

## 10. 选定路径与移交 AnLiu

### 10.1 选定

- 某个候选对在**双向**都收到过对方的探测（收到 `PROBE_ACK`，或者双方各自收到过对方的 `PROBE`）即为可用；
- **主叫为控制方**：第一个可用候选对出现后，再等待 200 ms 看是否有更高优先级的候选对（例如 IPv6 或 `mapped`），然后发送 `NOMINATE`；被叫回 `NOMINATE_ACK` 后双方确定路径。提名报文用 `nominate_key` 加密（6.5），如果此时 E2E 握手还没完成，主叫等握手完成再提名（握手经服务器只需 1 个往返，通常早于打洞完成）；握手失败则放弃打洞；
- 优先级：`host6` > `mapped` > `host4` > `srflx` > `pred`/暴力打洞；同级按 RTT 选择。

### 10.2 移交

1. 选定路径的 socket 从打洞模块移交给隧道层，本端地址与对端地址固定下来；
2. 已经跑在 UDP 中转上的 AnLiu 连接（`anl_t`，conv 不变）把 output 回调的目标改为新路径，**需要 AnLiu 提供路径切换接口**（重置 BBR 的带宽、RTT 估计，见评估建议）。匿名客户端没有中转（[security.md](security.md) D6），此时 AnLiu 连接在路径选定后才创建，直接跑在 P2P 路径上，也就没有第 3 步；
3. UDP 中转保留 30 秒作为热备，期间中转上仍到达的数据报照常交给 AnLiu（AnLiu 按序号去重），之后释放；
4. 当前走的是 WS 中转时（UDP 原本不通，网络变化后才可能打通），不做迁移：AnLiu 连接此时才创建，新的子链路走 P2P，WS 中转上的子链路传完后关闭（[data-channel.md](../protocol/data-channel.md) 第 3 节）。

### 10.3 保活与失效检测

- 用 AnLiu 的 `keepalive_ms` 保活，默认 15 秒（国内部分移动网络的 UDP 映射 30 秒内过期）；NAT 探测阶段若测到映射寿命，按"寿命 / 2"设置；
- 直连失效分两步（2026-10-05 按真实网络测试修订，详见 [data-channel.md](../protocol/data-channel.md) 第 3 节）：有未确认的数据、却 `max(3 秒, 2 × RTO)` 收不到对端任何报文 → **疑似失效**，之后每个数据报同时经直连和中转发送（中转已释放时先重新申请）；10 秒内直连又收到报文就恢复只走直连，否则放弃直连、留在中转上，主叫按退避策略重新打洞（UDP 中转上的会话才重新打洞，连第一轮最多 10 次，signaling.md "punch_result 与重试"）。没有中转可退（匿名主叫）时，主叫在放弃直连的同时立即请求新一轮打洞；
- 设备网络变化（地址变化、网卡切换）→ 立即切回中转，重新探测画像并重新打洞。

## 11. 模块划分与接口

```
src/
├── ice/                    候选与探测
│   ├── bind.c              地址探测客户端：BIND_REQ / BIND_RESP、重传、票据（6.4）
│   ├── natprobe.c          NAT 探测（4.x）
│   ├── candidates.c        候选收集（host4 / host6，已实现）
│   └── portmap.c           PCP / NAT-PMP（不含 UPnP），已实现
├── punch/                  打洞执行
│   ├── punch.c             会话、状态机、选定与移交
│   ├── strategy.c          决策表与各策略的发包计划
│   └── packet.c            报文封装与编解码（6.2、6.5）
└── platform/               socket、事件循环、定时器
```

**接口草案**（与 AnLiu 一样不直接拥有事件循环：socket 由平台层创建，时钟由调用方驱动）：

```c
typedef struct npf_punch npf_punch_t;

typedef struct npf_punch_cb {
    /* 需要一个新的 UDP socket（暴力打洞时会被调用多次）；返回 socket 编号，< 0 表示失败 */
    int  (*open_socket)(void *user, int family);
    void (*close_socket)(void *user, int sock_idx);
    int  (*send)(void *user, int sock_idx, const struct sockaddr *to, const void *buf, int len, int ttl);
    /* 打洞结束：成功时给出选中的 socket 与对端地址，失败时 sock_idx < 0 */
    void (*done)(void *user, int sock_idx, const struct sockaddr *peer, const npf_punch_stats *st);
} npf_punch_cb;

npf_punch_t *npf_punch_create(const npf_punch_config *cfg, const npf_punch_cb *cb, void *user);
int   npf_punch_start(npf_punch_t *p, const npf_punch_plan *plan);   /* 来自 punch.start */
int   npf_punch_input(npf_punch_t *p, int sock_idx, const struct sockaddr *from,
                      const void *buf, int len);  /* 认证失败返回 NPF_EAUTH，交给 AnLiu */
void  npf_punch_update(npf_punch_t *p, uint32_t now_ms);
uint32_t npf_punch_check(const npf_punch_t *p, uint32_t now_ms);    /* 下一次需要调用 update 的时刻 */
void  npf_punch_release(npf_punch_t *p);
```

这样打洞逻辑可以在模拟网络中做确定性测试，与 AnLiu 的测试方式一致。

## 12. 测试

### 12.1 NAT 模拟（`tests/natlab`）

Linux 内核 NAT 的行为不能完整覆盖上面的分类（MASQUERADE 默认尽量保持端口，`--random-fully` 可以模拟随机分配，但没有干净的 EIM + EIF 实现）。因此分两层：

1. **用户态 NAT 模拟器**（Go，放在 `tools/`）：在 network namespace 之间转发 UDP，映射、过滤、端口分配方式、端口块大小、映射寿命、丢包与时延均可配置。用于确定性地覆盖决策表的每一格；
2. **内核 NAT**：network namespace + nftables，验证在真实协议栈上的行为（`--random-fully`、端口保持、conntrack 超时）。

### 12.2 验收指标

| 场景 | 指标 |
|---|---|
| EIM × EIM | 成功率 > 99%，中位耗时 < 1 秒 |
| EIM × APDM 随机（N=256、M=1024） | 成功率 > 95%，中位耗时 < 6 秒 |
| EIM × APDM 端口块 2048 | 成功率 > 99% |
| APDM 随机 × APDM 随机 | 不尝试，直接留在中转，耗时 0 |
| 打洞过程中中转数据 | 不中断，切换时无数据丢失（AnLiu 层面） |

### 12.3 真实网络

家宽（电信、联通、移动）、4G/5G、公司网络、CGNAT 的组合，长期收集 `punch.result` 统计。

### 12.4 跨服务器实测（2026-10-04）

- **代码**：打洞模块 `src/punch/punch.c`（S1 同时打洞、S3 生日悖论暴力打洞，同步 poll 实现，仅 IPv4）；测试会合服务器 `server/internal/rendezvous` + `server/cmd/npf-punchd`；测试工具 `client/tools/npf-punch`。S1 先在本机回环联通，再在真实服务器间测试；
- **会合通道**：测试机只开放 UDP 9800–9999，TCP 被过滤，`npf-punchd`（TCP 9920）连不通。因此测试工具增加了 `--manual` 模式：画像与 srflx 已知时直接用命令行下发打洞计划，由本机经 SSH 驱动两端，不经会合服务器。正式环境的会合走 WSS，不受此限；
- **实测结果**（探测服务器 E1、E2 在一台服务器上，E3 在另一台）：

| 组合 | 策略 | 结果 | 耗时 | 说明 |
|---|---|---|---|---|
| 主机 2 × 主机 3（均 EIM） | S1 | 成功 | ~0.23 s | 直连 RTT 12 ms |
| 主机 4 × 主机 5（均 EIM，同机房） | S1 | 成功 | — | RTT < 1 ms |
| 主机 6 × 主机 4（均 EIM，异地） | S1 | 成功 | — | RTT 100 ms |
| 主机 3（EIM）× 主机 1（APDM 随机） | S3 | 成功 | 1.0 / 2.5 s | 喷包 182 / 468 个命中主机 1 的 256 个映射之一 |
| 主机 2（EIM）× 主机 1（APDM 随机） | S3 | 成功 | 0.9 s | 喷包 142 个命中，直连 RTT 7 ms |

  S3 验证了暴力打洞穿透对称型 NAT（主机 1 在云厂商的 NAT 网关后，APDM + 随机端口）：难侧开 256 个 socket 向易侧 srflx 发包，易侧向难侧公网 IP 的随机端口喷 1024 个 PROBE，命中其中一个映射即打通，命中数与生日公式一致（N=256 时期望约 252 个喷包首次命中）；
- **耗时受 SSH 启动偏差影响**：`--manual` 模式两端由两条 SSH 并行启动，偏差可达数秒，双方持续重传直到对齐，因此"耗时"一列偏大，不代表协议本身的延迟。正式环境由会合服务器按 RTT 同步开始（第 9 节），没有这个偏差。

### 12.5 端口映射与 IPv6（2026-10-04）

- **PCP / NAT-PMP**：报文编解码有已知答案测试（`tests/unit`，PCP MAP 60 字节、NAT-PMP MAP 12/16 字节的构造与解析，含错误码拒绝）。本机网关（WSL）不支持 5351，实测走到"无 PCP/NAT-PMP 响应"的优雅失败路径；云主机的网关也不应答 5351，因此真实命中需在支持的家用路由器上验证（待办）；
- **IPv6**：打洞模块 `punch.c` 已改为 family-agnostic（`sockaddr_storage`），S0/S1 支持 IPv6；S3 暴力打洞仍限 IPv4（依赖 NAT 端口行为，IPv6 无 NAT）。候选收集 `ice/candidates.c` 的 `npf_gather_host6` / `host4` 提供本机地址。**所有测试机都没有全局 IPv6**，无法做跨机实测；已在本机用 `::1` 回环验证 S1 over IPv6 打通（双方提名成功，地址为 v6）。真实 IPv6 穿透（家宽双栈，开放对端防火墙针孔）待有 v6 环境时验证。

### 12.6 打洞增强的接入（2026-10-06）

- 节点另开 IPv6 主 socket，`host6` 候选用它的端口；双方都有 `host6` 时服务器给 S1，向 IPv6 候选的探测从 IPv6 socket 发出，应答在收到的 socket 上发；本机用 `::1` 验证（`punch.sh`），真实 IPv6 仍待双栈环境；
- PCP / NAT-PMP 由节点在工作线程中请求（阻塞调用不进事件循环），结果作为 `mapped` 候选；路由器外部地址是私网 / CGNAT 地址时不用；服务器把有映射的一侧当作易侧（S1 而不是 S3）；本机替身网关验证了 PCP、NAT-PMP 退回与停止时删除；
- S2 见 7.3 末尾。

## 13. 待定问题

1. **AnLiu 的改动**：导出 SIV 加密原语（或在 NPF 中实现一份）；增加路径切换接口。需要在 AnLiu 仓库中实现；
2. **探测节点部署**：至少两台不同 IP 的机器；节点的健康检查；多地域部署时的就近选择规则。探测节点随签名的服务器列表下发与更新（[security.md](security.md) 7.5）；
3. **N 和 M 的默认值**：需要真实网络数据；CGNAT 端口配额是最大的不确定因素；
4. **IPv6 的防火墙打洞**：家用路由器的 IPv6 防火墙默认拒绝入站，也需要双方同时发包，按 S1 处理即可，但需要实测；
5. **移动端客户端**：手机在 Wi-Fi 与蜂窝网络之间切换时的重新打洞频率与耗电。
6. **全加密流量的可识别性**：6.7 所述的"完全随机本身就是特征"的风险需要在国内真实网络上长期观察（对比地址探测、打洞、AnLiu 数据三类流量被干扰的比例），必要时再考虑模仿某种常见 UDP 协议的外形。
