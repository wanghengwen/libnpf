## 1. 目标与非目标

**目标**

1. 在两端都能访问 UDP 的前提下，尽可能提高直连成功率，尤其是"一侧对称型 NAT"的情况；
2. 线上没有固定协议特征：地址探测与打洞探测的报文全部加密、长度随机，不使用标准 STUN 报文（第 6 节）；
3. 打洞与中转并行：会话先经服务器中转开始传数据，打洞在后台进行，成功后无缝切换，失败不影响可用性；
4. 设备端保持轻量：单线程事件循环，不引入额外依赖；
5. 可观测：每次打洞尝试都上报 NAT 类型组合、所用策略、耗时与结果，用数据调参。

**非目标**

- 兼容标准 ICE（RFC 8445）或与 WebRTC 互通；
- TCP 打洞（成功率低，收益不值得复杂度）；
- 两端都是随机端口分配的对称型 NAT：这种情况直接走中转，不做尝试。

## 2. 术语：NAT 行为分类

按 RFC 4787 / RFC 5780，从三个维度描述 NAT，而不是"全锥 / 限制锥 / 端口限制锥 / 对称"四分类：

| 维度 | 取值 | 含义 |
|---|---|---|
| **映射行为** mapping | EIM（与目标无关） | 同一内部 socket 发往任何目标，都使用同一个公网 IP:端口 |
| | ADM（与目标地址有关） | 目标 IP 不同则映射不同 |
| | APDM（与目标地址和端口有关） | 目标 IP:端口 不同则映射不同，即通常说的"对称型" |
| **过滤行为** filtering | EIF | 映射建立后，任何外部地址都能发进来 |
| | ADF | 只接受本端发送过的目标 IP |
| | APDF | 只接受本端发送过的目标 IP:端口 |
| **端口分配** allocation | 保持端口 | 尽量让公网端口等于内部端口 |
| | 顺序分配 | 新映射的端口按固定步长递增（常见步长 1 或 2） |
| | 端口块 | CGNAT 给每个用户分配一段端口（常见 512~4096 个），在块内分配 |
| | 随机 | 在整个端口范围内随机分配 |

后文把映射行为为 EIM 的一侧称为**易侧（easy）**，映射行为为 ADM/APDM 的一侧称为**难侧（hard）**。决定打洞策略的主要是映射行为和端口分配方式，过滤行为只影响"谁先发包"。

## 4. NAT 探测

### 4.1 探测服务器

NAT 探测借鉴 STUN（RFC 8489）的 Binding 机制：设备发送请求，服务器在响应中返回它看到的源地址（公网映射地址）。报文不使用标准 STUN 格式，而是 6.4 定义的加密报文，避免被识别和屏蔽。探测服务器**自行实现**（Go，服务器端 `natprobe` 模块），不依赖第三方公共 STUN。

一台机器只有一个公网 IP，因此"不同 IP"要由**不同机器**提供。每台探测服务器在自己的 IP 上监听两个端口，探测时从两台机器中选出 3 个端点：

| 端点 | 位置 | 用途 |
|---|---|---|
| E1 = IP_A:P1 | 服务器 A | 基准 |
| E2 = IP_A:P2 | 服务器 A 的第二个端口 | 判断映射是否与目标端口有关 |
| E3 = IP_B:P1 | 服务器 B | 判断映射是否与目标地址有关 |

- **部署要求**：至少两台公网 IP 不同的机器运行探测服务。两台机器之间不需要任何协作，只要 IP 不同即可；可以是同一云厂商、同一地域的两台机器（时延相近，重传超时更好设置）；
- **部署形态**（2026-10-19 改）：`natprobe` 内嵌在 `npf-server` 中运行（`probe_listen`、`probe_public`），每台信令服务器同时是一台探测服务器，用的就是 `server.json` 里的 `probe_master`、`ticket_secret`。原来的独立程序 `npf-probe` 已删除：每台信令服务器本来都跑探测，独立程序只多出一个服务、一份重复的秘密文件和一个部署角色。它无状态、流量很小（每次探测十几个小包）；
- **端点由信令服务器在登录时下发**（2026-10-19 改，signaling.md `welcome` 的 `probe`，`keys` 与 `probe` 事件）：E1、E2 是这台服务器自己的两个端口，E3 是另一台在线、公网 IP 不同的服务器的第一个端口（按 `server_id` 取这台之后的下一台，各台服务器的客户端分散到不同的 B）。服务器从 Redis 的 `srv:` 记录得知其他服务器的探测地址和是否在线（每 5 秒），Redis 不可用时沿用最后一次的；端点变了就推送 `probe` 事件，客户端重新测一次。原来端点写在签名的服务器列表里：要在签名前把"另一台的地址"拼进每台服务器的条目（正式部署时漏拼过，客户端一直判断不出映射类型），改地址要重签列表，列表也不知道 B 是否还活着。经 Noise 认证的信令通道下发，与签名列表一样不能被篡改，而且探测本来就要等登录拿到密钥和票据之后才开始；
- **认证**：请求与响应都是整包认证加密（6.2），请求还携带信令服务器签发的票据（6.4）。服务器对未认证的请求不作任何回应，不会被滥用，也不会暴露服务类型；设备只采信通过认证的响应，防止伪造响应导致误判；
- **限流**：令牌桶，每个 `id`（票据中）平均每秒 20 个请求、每个源 IP 平均每秒 200 个（同一 CGNAT 公网 IP 后面可能有很多设备，按 IP 限得太紧会误伤），突发量均为每秒速率的 2 倍；超出的静默丢弃。突发量是必要的：一次完整探测要发 3 + K 个请求再加重传，实测用固定的一秒窗口时，K = 16 的探测会被截掉一部分；
- **只有一台机器时**（早期阶段，或另一台下线时）：只能得到 E1、E2，可以区分 EIM 与 APDM，无法区分 ADM；见 4.2 的降级处理。

### 4.2 探测步骤

设备用**同一个 socket** 依次向 E1、E2、E3 发送 Binding 请求（每个请求最多重发 3 次，间隔 200/400/800 ms），得到映射地址 M1、M2、M3：

| 观察结果 | 结论 |
|---|---|
| M1 = M2 = M3 | EIM |
| M1 = M2 ≠ M3 | ADM |
| M1 ≠ M2 | APDM |
| 映射端口 = 本地端口 | 保持端口 |
| 没有 E3（只部署了一台）或 E3 无响应 | M1 ≠ M2 时仍判为 APDM；M1 = M2 时画像记为 `UNKNOWN`，按难侧处理 |

**公网 IP 不一致**：M3 的 IP 通常应与 M1 相同。若不同，说明 CGNAT 对不同目标使用了不同的公网 IP（非"成对"地址池），这种 NAT 按难侧处理，且打洞时对端喷包的目标 IP 不确定，暴力打洞（S3）不适用，直接走中转。

**端口分配方式**：再新建 K 个 socket（节点 K = 4，`npf_natprobe` 的默认 8），在 15 ms 内依次向 E1 发请求，记录映射端口序列（原来在 200 ms 内：同一 NAT 后面的别的流量在每两个请求之间都占走端口时，最小的差值就不是步长。natlab `s2b-busy` 的 NAT 每秒被占 10 个端口，4 个请求相隔约 50 ms，约 6 % 的测量把步长 1 测成 2（UDP 信令同时在主 socket 上收发时请求实际相隔约 64 ms，约 10 %），S2B 按错的步长预测，每一轮都落空；2026-10-30 改为 15 ms）：

- 相邻差值都是 1~64 的正数（差值有 5 个以上时允许一个例外：分配到区间末尾折回），且最小的差值不超过 16 → 顺序分配，步长取最小的差值。不要求差值相同：同一 NAT 后面的其他流量会在两次探测之间占走端口（繁忙的 NAT 上步长 1 测出 +2、+4、+3），差值只会变大；端口块和随机分配的差值有正有负；
- 全部落在一个较小的区间内（不到 4096 个端口；主 socket 朝向 E1 的 IP 的映射 M1、M2 也算这个区间的样本）→ 可能是端口块，记录区间 [min, max]，多次探测后逐步修正；
- 无规律 → 随机分配。

**端口块的区间也用 M1、M2**（2026-10-30）：随机分配的 NAT 给的 4 个端口落在 4096 个以内的概率约千分之一（4 × (4096/64512)³），这时节点把随机分配测成端口块。natlab 一次完整的运行约有 23 次随机分配 NAT 的探测，约 2% 的运行因此有一个用例失败（`sym-cone`、`eif-sym`、`adf-sym`：例如 4 个端口 3108、2509、1638、1582，同一秒里 M1、M2 是 11786、20507）；natsim 的随机分配是均匀的（保留下来的 natlab 记录里 325 次探测的跨度分布与均匀抽样一致，只有不到 4096 的那一档多，而那几次正是让那次运行失败、记录才保留下来的）。主 socket 朝向 E1、E2（同一个 IP）的映射也是这个 NAT 在这次探测里给出的端口，端口块的 NAT 同样给在块内，所以算作区间的样本：APDM 多两个（M1 ≠ M2）、EIM / ADM 多一个，误判降到约 16 万分之一 / 1.2 万分之一（1 亿次模拟：5.7 × 10⁻⁶、7.8 × 10⁻⁵，原来 9.9 × 10⁻⁴），不多发一个包。M3 不算：有的运营商 NAT 朝向每个目标 IP 各给一块（natsim `--per-dest`，7.8）。与 15 ms 的发送间隔无关：随机分配不看时间，10-27 间隔还是 200 ms 时 `adf-sym` 也这样失败过一次。

**存疑时立即再测一次**（2026-10-29，8 小时 natsim 测试 RN-16）：顺序分配的节点（4 天里 58 次都测成 APDM + 顺序 + APDF）重启后的第一次探测测成了端口块（8 个端口），之后一小时它与另一个顺序分配的节点之间没有策略（7.1），37 次呼叫都走中转，而它们之前一直经 S2B 直连。原因是**还活着的旧映射**：新 socket 的本地端口恰好是刚关掉的一个 socket 的（上一个进程 25 秒前的探测用过它，也是发往 E1），NAT 沿用那个映射，给出的是更早的端口，插在序列中间，相邻差值有正有负，于是"在一个小区间里"成了端口块（natsim 的计数：这次探测只新建了 7 个映射，少的那个就是它）。重启后上一个进程刚探测过，这种碰撞才有机会（每次约 0.2%）。现在两种结果算存疑，节点立即再测一次、采用第二次的结果（`nat.c:probe_done`，与"没有回应时再测一次"共用一次机会；登录等的是第二次的结果）：

- 不是顺序分配，但去掉一个样本就是（样本至少 4 个：`natprobe.c` 的 `alloc_doubt`）；真正的小端口块偶尔也会这样（512 个端口的块约 2%），代价只是多测一次；
- 与上一次完整探测的分配方式不同，而公网 IP 没变（同一个 NAT：例如顺序分配跨过区间末尾时测成随机）。

第二次的样本来自新的随机本地端口，再碰上旧映射的概率又是约 0.2%。natlab `s2b-stale`（NL-41）：设备的 NAT 把第 3 个分配样本给成更早的端口（`natsim.py --stale`），改前设备报端口块、平台不安排打洞、一直走中转，改后再测一次得到顺序分配，S2B 直连。

**过滤行为**（2026-10-21）：两侧都是难侧时，能不能打通取决于过滤行为（7.5），所以要测。做法不需要服务器之间协作：端口分配测试的第一个有回应的 socket 留下来作为 F，它只向 E1 发过包，映射为 mF。主 socket（已经向 E2、E3 都发过包，它们的应答能进来）向 E2 和 E3 各发一个 `BOUNCE_REQ`（6.4），请它们从自己的地址给 mF 发一个 `BIND_RESP`：

| F 收到 | 结论 |
|---|---|
| E3 的（另一个 IP） | EIF：谁都能发进来 |
| 只有 E2 的（同一 IP 的另一个端口） | ADF：发过包的 IP 的任何端口都能发进来（没有 E3 时为"至少 ADF"） |
| 都没收到，但服务器确认收到了请求（主 socket 收到应答） | APDF：只有发过包的 IP:端口 |
| 服务器都没有确认 | UNKNOWN |

请求按 0、200、600、1400 ms 重发，直到 F 收到对应的应答（服务器的确认可能先到、而给 F 的那个丢了）；收到确认后最多再等 600 ms。整个 NAT 探测因此多一个往返左右（不是 EIF 时多 0.6 秒）。实测一台云服务器所在的云厂商 NAT 网关是 APDF：换端口发 8 个、换 IP 发 15 个，都没有进来。

**公网 IPv4 检测**：若映射地址等于本机某个网卡地址，说明设备直接有公网地址（无 NAT），画像标为 `open`。

### 4.3 NAT 画像

```c
typedef struct npf_nat_profile {
    uint8_t  mapping;        /* EIM / ADM / APDM / UNKNOWN */
    uint8_t  allocation;     /* PRESERVE / SEQUENTIAL / BLOCK / RANDOM / UNKNOWN */
    uint8_t  filtering;      /* EIF / ADF / APDF / UNKNOWN */
    int16_t  seq_delta;      /* 顺序分配的步长 */
    uint16_t block_lo, block_hi;   /* 端口块区间（观测值） */
    uint8_t  open;           /* 有公网地址、无 NAT */
    uint8_t  has_ipv6;       /* 有全局 IPv6 地址 */
    uint32_t measured_at;    /* 探测时间 */
} npf_nat_profile;
```

- **什么时候测**（按代码，2026-10-26 核对）：登录时；网络检查时（网卡地址变化、进程挂起后恢复：`node_network.c` 的网络检查，只测映射、端口分配沿用）；主 socket 重开时（同上）；平台下发的探测服务器变了时；没有回应时 5 秒、20 秒、1 分钟、3 分钟后再测。**没有周期性的重新探测**。有常驻中转绑定（2026-10-26，home-binding.md）的节点空闲时主 socket 上也有保活（中转在节点静默 T 后 ping，节点的应答从主 socket 发出），映射一直有效；平台按中转看到的备用分配的地址 R 给出它的 srflx（4.5）。没有绑定的（`home_bind = off`、托管客户端、匿名客户端）空闲时主 socket 上没有任何 UDP 流量，空闲一段时间后映射可能已经过期；呼叫时的核对 2026-10-27 已去掉，它们用登录时探测的结果（4.5）；
- 画像随设备上线信息上报给服务器，服务器可以做统计，并在会话建立时直接下发给对端，省去一次往返。

### 4.4 实现与实测（2026-10-03）

- **代码**：设备端 `src/crypto/siv.c`（SIV 封装）、`src/ice/bind.c`（报文编解码）、`src/ice/natprobe.c`（探测与判定，仅 IPv4；节点在事件循环上运行 `npf_natprobe_start`，主 socket 上探测服务器的应答由节点的数据报分发交给它；调试工具用阻塞的 `npf_natprobe_run`，它在自己的事件循环上跑同一个探测）；探测服务器在平台一侧，两侧的加密实现共用一组已知答案（含跨语言向量）；
- **端口分配的区间按环形计算**：实测阿里云 NAT 网关的映射端口分布在 [约 60000, 65535] ∪ [1024, 约 10000]，是跨过 65535 的一整段。区间取"覆盖全部样本的最小环形区间"，`block_lo > block_hi` 表示跨越；
- **多 IP 主机**：监听通配地址时，内核按路由选回复的源地址，可能不是设备发往的那个，设备会因"回复来源与请求目标不一致"而丢弃。原来要按 IP 分别监听；2026-10-30 起探测服务器、中转与 UDP 信令在通配地址上按每个请求的目的地址指定回复的源地址（Linux 的 `IP_PKTINFO`），通配地址也可以用；
- **实测**（两台探测服务器 A、B，UDP 9910 / 9911）：

| 设备 | 网络 | M1 / M2 / M3 | 端口分配 | 画像 |
|---|---|---|---|---|
| 主机 1 | 云服务器，经云厂商的 NAT 网关 | 三个端点映射各不相同 | 16 个新 socket 的端口集中在 [约 60000, 约 9800]（跨 65535） | APDM + RANDOM |
| 主机 2 | 云服务器，自有公网地址 | 相同，且等于本地端口 | 全部保持本地端口 | EIM + PRESERVE |
| 主机 3 | 家庭宽带的 NAT 后 | 相同，且等于本地端口 | 全部保持本地端口 | EIM + PRESERVE |
| 本机 | WSL2 + Clash TUN | 无响应 | — | UDP 被代理阻断（AnLiu 测试中的已知情况） |

  主机 1 与主机 2 / 3 之间正好对应 7.4 的 S3 场景（一侧 EIM、一侧难侧），可以作为暴力打洞的实测环境。

### 4.5 srflx 从哪来：中转看到的地址（2026-10-27）

**问题**（8 小时 natsim 测试 RN-16）：画像和 `srflx` 只在上面那些时刻测量，平台按节点报的缓存数据安排每一轮。端口不保持的 NAT（EIM + 随机分配，典型的运营商 NAT）在节点空闲时让映射过期，下一个映射换了端口；节点仍然报旧的 `srflx`，S1 两边都打不通。

**做法**（2026-10-27，用户决定，推翻 home-binding.md 的 U7）：节点的 UDP 中转分配都从主 socket 绑定，中转看到的绑定源地址 **R**（cookie 验证过）就是主 socket 朝向平台的映射：备用分配的 R 由中转发起的保活一直刷新（home-binding.md），每呼叫分配的 R 在呼叫开始时绑定（主叫拿到 `call` 的应答就绑，被叫在 `incoming` 时），通常在第一轮之前就知道。平台**自己**拿 R 当这一侧的 `srflx` / 公网 IP（`server/internal/signaling/relayaddr.go`；先用呼叫这一侧的分配，没有绑好时用节点现在的新鲜备用分配）：

- **EIM**（含公网 `open`）：`srflx` 就是 R（替换节点报的，没有就加上），`pub_ip` 是 R 的 IP；
- **ADM / APDM**：只用 R 的 IP：`pub_ip` 是它，`srflx` 的 IP 换成它、端口照旧（朝向对方的端口本来就不同）；`ip_varies`（运营商不成对的地址池）时不用；
- R 用于 `incoming`、`call_accepted` 里转给对方的画像与候选、每一轮的计划、学到的端口段的键；它是这一侧"见到"的 IP（H-1，security.md 11.1），按它喷包不需要另外验证；
- **呼叫中 R 来了或变了**（每呼叫分配在一轮计划之后才绑好，或中转收到 cookie 验证过、`kseq` 更新的、来自新地址的 `RELAY_BIND`）：平台自己处理，节点什么也不发；绑好的 R 和节点报的一样时什么也不做。EIM 一侧的新 `srflx` 发给正在打洞的对方（`punch_info{call_id, round, cand}`，signaling.md），平台的调度器同时收到"有新候选"（第 9 节：有一轮在进行时并入它，退避等待中立即开始一轮）；之后的计划都用新的 R。主叫在别的服务器上时（多服务器，P4）由它的服务器在转交呼叫时带上 R，变了再发一条服务器之间的 `caller_r`；
- **收到的一方**：这一轮正在进行时，把地址加入它的探测目标（`npf_punch_add_peer`：从此和其他候选一起探测；S3 难侧的 socket 改向它发；已有的不重复，最多 16 个），相当于 ICE 中补来的远端候选加入正在运行的检查；这一轮还没开始时记下，开始时加入；
- **没有绑定的 UDP 中转分配的一侧**（匿名客户端：没有中转，D6；WS 中转上的；分配还没绑好时的第一轮）：用登录时（及网络变化后）探测的 `srflx`，呼叫时不再核对。匿名客户端的映射空闲过期时它的 `srflx` 就是旧的：这是去掉呼叫时核对后唯一的退步；
- **去掉的**（2026-10-26 的呼叫时核对）：主叫发出 `call`、被叫应答 `incoming` 后，节点在主 socket 上只向 E1 发一个 `BIND_REQ` 核对映射（25 秒内不重复），变了就 `nat_report` 并向对方补发 `punch_info{cand}`，平台检查它是不是这一侧"见到"的 IP 再转发，被叫的在接受之前先留着。现在节点不发 `cand`，平台也不转发节点发的；
- **natlab**：`stale`（双方 EIM + 随机分配 + APDF、映射寿命 40 秒，登录 50 秒后呼叫，有备用分配）：保活让映射一直有效，约 0.03 秒直连；`stale-nospare`（寿命 20 秒、30 秒后呼叫、没有备用分配）：登录时的 `srflx` 已过期，平台用每呼叫分配的 R，约 0.02 秒直连（原来的呼叫时核对约 0.4 秒）；
- **没有处理的**：S2 的预测端口 `pred`（顺序分配时"上次的映射端口 + 步长"）是登录时的，空闲后同样过时；端口块（BLOCK）的范围是 NAT 的性质，不受影响；主叫在另一台服务器上、没有备用分配时，它在那台服务器上的每呼叫分配的 R 目前不传过来（用节点报的）。

## 5. 候选

| 类型 | 来源 | 优先级 |
|---|---|---|
| `host6` | 本机全局 IPv6 地址 | 最高：通常只需在防火墙上打洞 |
| `mapped` | PCP / NAT-PMP 在路由器上建立的端口映射 | 高：相当于公网地址 |
| `host4` | 本机私网 IPv4 地址（同一局域网或同一 NAT 下直连） | 高 |
| `srflx` | 打洞所用 socket 向探测服务器请求得到的公网映射地址 | 中 |
| `pred` | 按画像预测出的端口（顺序分配时为映射端口 + k × 步长） | 低 |

说明：

- **端口映射**：设备端启动时尝试 PCP → NAT-PMP（为什么没有 UPnP 见 5.1），成功后定期续期（租期 1 小时，提前 10 分钟续期），退出时删除；换了网络（默认网关或本机通往它的地址变了，2026-10-26）重新申请。NAS 大多在家庭路由器后面，这一项往往直接解决问题。已实现于 `src/ice/portmap.c`：PCP（RFC 6887）与 NAT-PMP（RFC 6886），都向默认网关 UDP 5351 发送，先试 PCP（较新、直接返回外部地址、支持 IPv6）再退回 NAT-PMP；网关在 Linux 上从 `/proc/net/route` 读取，macOS 查路由表，Windows 用 `GetBestRoute`，iOS、Android 不知道网关（不尝试）。网关怎么应答的（映射可用 / 外部地址不是公网 / 没有应答 / 不知道网关 / 关闭）随 NAT 画像的 `pm` 上报平台，供穿透统计（signaling.md `nat`）；
- **只收集必要的 host 地址**：排除回环、链路本地、docker/虚拟网卡（按网卡名与地址段过滤，可配置）；
- 候选中的地址经信令发给对端，对端能看到本端的内网地址。这是 ICE 的通常做法；有顾虑时可以只发送私网地址的哈希，由对端判断是否可能同网段，作为可选项。

### 5.1 不支持 UPnP IGD

UPnP IGD 映射不做（2026-10-26 决定，同日做过的"只检测、不映射"也删掉了）：它要 SSDP 发现、HTTP 取设备描述、解析 XML、SOAP 控制，代码比 PCP / NAT-PMP 大得多（只检测就有约 450 行、8 KB 目标代码），还要解析局域网设备发来的 HTTP / XML（历来 UPnP 栈漏洞多，SSRF 之类的问题也出在这一步）；而没有数据表明它值得：有多少端点的网关是 IGD、WAN 地址又是公网，并不知道。libnpf 要保持小，所以只有 PCP / NAT-PMP。

## 6. 报文格式

打洞相关的 UDP 报文有两类：设备与探测服务器之间的**地址探测报文**（取代标准 STUN），设备与设备之间的**打洞探测报文**。两类报文与 AnLiu 数据报共用同一个 UDP socket，采用同一种封装：**整包认证加密，线上没有任何明文字段、固定长度或固定端口**。

### 6.1 借鉴 STUN 的什么，改掉什么

标准 STUN 的报文头是明文的：前两位固定为 0，第 4~7 字节是固定的 magic cookie `0x2112A442`，默认端口 3478，报文长度按 4 字节对齐。一条规则就能识别并屏蔽全部 STUN 流量。本协议保留 STUN 的机制，改掉它的线上形态：

| STUN 的设计 | 本协议 |
|---|---|
| 请求 / 响应模型，Binding 请求返回"服务器看到的源地址" | **保留** |
| 96 位随机事务 ID，响应原样带回，用于匹配请求与重传 | **保留** |
| 从收到请求的端口回复，客户端据此区分端点 | **保留** |
| 重传：200/400/800 ms 指数退避 | **保留** |
| MESSAGE-INTEGRITY（HMAC）防伪造 | 改为整包认证加密（6.2），同时提供完整性与机密性 |
| XOR-MAPPED-ADDRESS：地址与 magic cookie 异或，防止中间设备（ALG）改写报文中的 IP | 不再需要：地址位于密文中，中间设备看不到也改不了 |
| 明文报文头、magic cookie、TLV 属性 | 去掉：密文之外只有 12 字节看似随机的 tag |
| 报文长度 4 字节对齐、常见长度集中在 20~100 字节 | 随机填充，长度在区间内均匀分布（6.3） |
| 固定端口 3478 / 5349 | 端口由服务器下发，可以随时更换（6.7） |

### 6.2 通用封装

与 AnLiu 相同的 SIV 构造（ChaCha20 + SipHash-2-4，12 字节 tag），但使用独立的密钥派生标签，确保三类报文在密码学上互不混淆：

```
wire = tag(12) || ChaCha20(k_enc[dir], nonce = tag, P)
tag  = SipHash-2-4-128(k_mac[dir], P)[0..11]

P    = type(1) | flags(1) | body_len(2) | txid(12) | ts_ms(4) | body | pad
```

| 字段 | 说明 |
|---|---|
| `type` | 报文类型，见 6.4、6.5 |
| `flags` | 保留，发送时置 0 |
| `body_len` | `body` 的长度；其后到报文末尾都是填充 |
| `txid` | 96 位随机事务 ID（与 STUN 相同），响应原样带回 |
| `ts_ms` | 发送方的毫秒时钟，用于计算 RTT，服务器用它做时间窗检查 |
| `pad` | 随机字节 |

**编码**：整数一律小端序（与 AnLiu 一致），IP 地址按网络字节序原样存放。`type` 编号：`BIND_REQ` = 1、`BIND_RESP` = 2、`PROBE` = 3、`PROBE_ACK` = 4、`NOMINATE` = 5、`NOMINATE_ACK` = 6；UDP 中转使用 `RELAY_BIND` = 7、`RELAY_BIND_ACK` = 8、`RELAY_DATA` = 9（`RELAY_DATA` 不用这里的封装：16 字节的报文头只由 SipHash-2-4-64 认证，AnLiu 数据报原样跟在后面，见 [data-channel.md](../protocol/data-channel.md) 9.2）。KDF 标签（12 字节，作为派生块的 ChaCha20 nonce）：地址探测为 `NPF-PROBE-v1`，打洞探测为 `NPF-PUNCH-v1`，提名为 `NPF-NOMIN-v1`，中转的控制报文（绑定、应答、ping，用分配的 `alloc_key`）为 `NPF-RELAY-v1`，中转的 `RELAY_DATA` 的 SipHash 密钥为 `NPF-RDATA-v2`；UDP 信令的握手（`SIG_HELLO` = 11、`SIG_HELLO_ACK` = 12、`SIG_COOKIE` = 13）为 `NPF-SIGHS-v1`，基础密钥是服务器的 Noise 静态公钥（[信令协议](../protocol/signaling.md)"UDP 承载"）；设备发往中转的控制报文前面另有 4 字节明文的分配提示，`RELAY_DATA` 带 3 字节掩码的提示，见 data-channel.md 9。

**方向密钥**：沿用 AnLiu 的做法，按发送方向派生两套密钥（请求方向 / 响应方向，或打洞的主叫 / 被叫方向）。把请求原样反射回请求方会因为密钥方向不匹配而认证失败，攻击者无法用抓到的请求冒充响应。

**需要 AnLiu 导出加密原语**（目前是 `anliu.c` 内部的静态函数），或在 `src/crypto` 中实现一份相同的构造。

认证失败的报文**静默丢弃，不作任何回应**。这对探测服务器同样适用：未认证的请求得不到任何响应，主动探测者无法确认端口上运行的是什么服务。

### 6.3 长度

- 每个报文的总长度在该类型的区间内**均匀随机**（见 6.4、6.5），不做对齐；
- 地址探测请求**不短于**对应的响应：服务器响应的长度不超过它收到的请求，避免被用作 UDP 反射放大攻击的放大器；
- 服务器可以通过下发配置调整各类型的长度区间。

### 6.4 地址探测报文（设备 ↔ 探测服务器）

| type | 方向 | body |
|---|---|---|
| `BIND_REQ` | 设备 → 服务器 | `ticket` |
| `BIND_RESP` | 服务器 → 设备 | `family(1) | port(2) | addr(4 或 16)` 服务器看到的源地址；`srv_time_ms(8)` 服务器时间 |
| `BOUNCE_REQ`（type 7） | 设备 → 服务器 | `ticket | family(1) = 4 | port(2) | addr(4) | txid(12)`：过滤行为测试（4.2），请服务器给 `addr:port` 发一个 `txid` 为这个值的 `BIND_RESP`（内容是 `addr:port` 本身） |

长度区间：`BIND_REQ`、`BOUNCE_REQ` 为 [96, 200] 字节（之外的不解密、直接丢弃），`BIND_RESP` 为 [47, 请求长度]（回应 `BOUNCE_REQ` 的两个包各自可以短于 64 字节）。

服务器对 `BOUNCE_REQ` 回两个包：给请求方一个普通的 `BIND_RESP`（确认），给目标一个 `BIND_RESP`，都从收到请求的那个 socket 发出，两个合计不长于请求。目标的 IP 必须与请求的源 IP 相同：只能让服务器回复请求方自己的另一个映射，不能用来向第三方反射，也没有放大（伪造源地址的请求得到的字节不多于发出的）。

`BIND_RESP` 的 `txid` 与 `ts_ms` 都**原样带回请求中的值**：设备用 `txid` 匹配请求，用 `ts_ms` 计算 RTT（每次重发都重新加密、带新的 `ts_ms`，因此 RTT 不受重传影响）。

**密钥**：所有探测服务器共享一组 `probe_key`，每天轮换：`probe_key = HMAC-SHA256(probe_master, "npf-probe-key-v1" | day)`，`day` 为 UTC 天数（Unix 秒 / 86400，4 字节小端）。服务器只需配置 `probe_master`，无需每天下发新密钥。设备经 WSS 从信令服务器获得当前与下一个 `probe_key`。密文之外没有密钥编号，服务器依次用当前密钥和上一个密钥尝试验证（轮换交替期内最多两次）。

**票据（ticket）**：`probe_key` 由所有设备共享，只能证明"持有固件的一方"。为了能按设备限流、吊销，请求中还携带信令服务器签发的票据：

```
ticket = id(8) | expire(4) | mac(16)
mac    = HMAC-SHA256(ticket_secret, id | expire)[0..15]
id     = 设备号或 client_id（见 security.md 第 6、8 节）
```

`ticket_secret` 只在服务器端（信令服务器与探测服务器共享），票据有效期 24 小时，设备随 `probe_key` 一起获取。探测服务器验证票据**无需查询任何状态**，并按 `id` 与源 IP 两个维度限流。

**时间窗**：服务器拒绝 `ts_ms` 与自身时间相差超过 60 秒的请求（设备首次探测前先用 WSS 上服务器下发的时间校准偏移）。`srv_time_ms` 也用于第 9 节的同步开始。

**重放**：攻击者重放抓到的请求（即使伪造源地址），只会让服务器向该源地址发送一个不长于请求的响应，没有放大效果；加上按目标 IP 的限流，无法被用于反射攻击。

### 6.5 打洞探测报文（设备 ↔ 设备）

打洞报文使用两把密钥，封装方式都与 6.2 相同（各方向密钥按 6.2 从基础密钥派生）：

- **`punch_key`**：会话建立时服务器生成的随机 32 字节，通过 WSS 下发给双方，保护 `PROBE` / `PROBE_ACK`。这样不必等 E2E 握手完成就能开始打洞。服务器知道它不影响数据安全：数据由 AnLiu 加密，AnLiu 的会话密钥由两端端到端协商（Noise），服务器不知道；
- **`nominate_key`**：由两端的 E2E 握手派生（[security.md](security.md) 9.5），服务器不知道，保护 `NOMINATE` / `NOMINATE_ACK`。服务器即使伪造探测报文，也无法让双方提名一条错误的路径。

| type | body |
|---|---|
| `PROBE` | `session_id(8) | sock_idx(2)` |
| `PROBE_ACK` | `session_id(8) | sock_idx(2) | family(1) | port(2) | addr(4 或 16)` 我看到的你的源地址，用于发现对端反射地址 |
| `NOMINATE` / `NOMINATE_ACK` | `session_id(8)` |

- `session_id`：打洞会话 ID，用于在同一 socket 上区分多个并发打洞会话；
- `sock_idx`：发送方的 socket 编号（暴力打洞时标识是哪个 socket）；
- 长度区间：[64, 256] 字节。

### 6.6 同一 socket 上的分发

同一 socket 上收到的 UDP 报文除中转的 `RELAY_DATA` 外都是"12 字节 tag + 密文"，按上下文决定尝试顺序：

1. 本 socket 有发往该源地址的未完成 `BIND_REQ`：先用 `probe_key` 验证；`RELAY_DATA`（data-channel.md 9.2）：去掉掩码的 3 字节提示找到源地址那台中转上的分配，SipHash 验证报文头，成功后把其后的 AnLiu 数据报交给 AnLiu；中转的控制报文用该中转分配的 `alloc_key` 验证；
2. 打洞进行中（路径尚未移交 AnLiu）：先用 `punch_key` 验证，再用 `nominate_key`（E2E 握手完成后才有），都失败再交给 AnLiu；
3. 路径已移交：先交给 AnLiu（`anl_peek_conv` / `anl_input`），失败再用 `punch_key` 验证（对端可能还在发迟到的探测报文）；
4. 都失败：丢弃并计数（`rx_auth_fail`）。

按上下文排序后，绝大多数报文一次验证就能命中；最坏情况下一个报文做三次 SipHash + ChaCha20，1400 字节约 3~6 µs，对 NAS 的报文速率可以接受。

### 6.7 其他抗屏蔽措施

报文格式只解决"按内容识别"。其余可被利用的特征及对策：

| 特征 | 对策 |
|---|---|
| 固定端口 | 探测服务器的端口由服务器下发，每个节点可以监听多个端口，随时更换；不使用 3478、19302 等 STUN 常见端口 |
| 服务器 IP | 多个探测节点，列表经签名下发（与信令服务器列表相同的机制），被封的节点从列表中剔除并补充新节点 |
| 报文长度 | 均匀随机，见 6.3 |
| 主动探测 | 服务器对未认证报文不作任何回应 |
| 时序 | 地址探测本身是低频、少量的报文，不做处理；打洞阶段的高频发包无法隐藏，只能靠限速（第 8 节）降低显著性 |

**局限**：整包随机、没有任何可识别结构，本身也可能成为一种特征。已有研究表明，部分审查系统会针对"完全加密、无法识别协议"的流量做启发式屏蔽（公开研究主要针对 TCP，对 UDP 的处理尚不清楚）。本协议无法消除这一风险，兜底方案是独立 WSS 连接上的 WS 中转（与普通 HTTPS 流量无法区分，见 [data-channel.md](../protocol/data-channel.md) 第 10 节），UDP 被阻断时服务照常可用。

### 7.1 决策表

按双方画像选择策略，可以并行执行多个策略。本端 A、对端 B：

| A \ B | open / mapped | EIM | ADM/APDM 顺序分配 | ADM/APDM 端口块 | ADM/APDM 随机 |
|---|---|---|---|---|---|
| **open / mapped** | 直连 | 直连（B 主动） | 直连（B 主动） | 直连（B 主动） | 直连（B 主动） |
| **EIM** | | S1 同时打洞 | S2 端口预测（A 的过滤为 EIF / ADF 时 S1） | S3 生日悖论（缩小范围；同上） | S3 生日悖论（同上） |
| **ADM/APDM 顺序分配** | | | S4，否则 S2B 双向预测 | S4，否则中转 | S4，否则中转 |
| **ADM/APDM 端口块** | | | | S4，否则中转 | S4，否则中转 |
| **ADM/APDM 随机** | | | | | S4，否则中转 |

**按过滤选 S1**（2026-10-26）：一侧易（EIM、无 NAT 或有路由器映射）、一侧难时，易侧的过滤让难侧主 socket 的探测进来就用 S1：过滤为 EIF（谁都能发进来）；ADF（易侧 S1 向难侧的 `srflx` 发过包，难侧 IP 就能进来，要求难侧不是 `ip_varies`）；无 NAT 或有映射（相当于 EIF）。难侧从主 socket 发往易侧 `srflx` 的探测在难侧 NAT 上建立朝向易侧的映射 m，易侧回 `PROBE_ACK` 到探测的来源 m 并回探（对端反射地址、触发检查），双向打通；难侧不开 socket、不占 NAT 端口，易侧不喷包。过滤是对探测服务器测的，若对端的行为不同（这一轮什么也没收到，3 秒后报告失败，第 9 节），这个呼叫以后都改用表中的策略，平台立即开始下一轮（第 9 节）。过滤只用探测服务器测到的（7.8：不再从轮次里学）。双难侧中一方过滤为 EIF 时同样给 S1（另一方从主 socket 发往它的 `srflx` 就进得来，回包走同一映射，与 S4 的前提相同），失败后改 S4。

双难侧（2026-10-21）：

- **S4**（7.5）：任一方的过滤是 EIF 或 ADF（4.2）时可用，与端口分配无关，优先；
- **S2B**（7.6）：双方都是顺序分配（步长 1~16）；
- **中转**：双方的过滤行为都测出来了（APDF）、又没有上面的条件时（两侧都是随机端口或端口块；端口块原来的 S5 已去掉，7.7），平台不安排打洞（`punch_start` 带 `skip: no_strategy`，signaling.md）。原因是两侧都随机分配端口、只认发过包的 IP:端口时，A 的一个包要打到 B 的某个映射上，而这个映射恰好是 B 发往 A 那个包的源端口时建立的，双方的端口都由 NAT 随机给出，谁也预先不知道：期望命中数 ≈ (A 发的包数 × B 发的包数) / (A 的端口范围 × B 的端口范围)。实测一个云 NAT 网关的端口范围约 1.25 万个，两台这样的 NAT 之间各发 1000 个包，成功率约 0.5%，还要各占 1000 个映射；拉长时间也没用（命中要求两边的映射同时活着，成功率随时间线性增长，每秒 10 个包时平均要二十个小时）。一侧顺序分配、一侧端口块（或随机）也是这样：顺序的一侧可以预测，端口块的一侧朝向它的映射仍是块内随机的，S2B 要两侧都能预测。所以一次测错的端口块不在平台这里补救（例如按节点以前的画像照旧给 S2B），而是节点在测量存疑时立即再测（4.2）；过滤行为未知（旧节点）时照旧给 S1；
- 双方在之前几轮里看到的对方端口段（7.8）修正喷包的范围，不改变策略。

另外：

- **S0 IPv6**：双方都有 `host6` 时，与上表并行执行，优先级最高（2026-10-26 起真正并行：IPv4 照上表规划，IPv6 候选在每一种策略中都从 IPv6 socket 按 S1 的节奏探测，提名时优先，10.1；原来双方都有 `host6` 时只给 S1，IPv6 被防火墙挡住、IPv4 又需要 S3 的组合 10 轮都失败）；
- **同一公网 IP**：双方 `srflx` 的 IP 相同，说明在同一个 NAT 后面，优先尝试 `host4` 直连；
- 画像为 `UNKNOWN` 的一侧按"ADM/APDM 随机"处理。

### 7.2 S1：同时打洞（双方都是 EIM）

双方同时向对方的所有候选发送 `PROBE`，间隔 50 ms，持续 2 秒；之后每 200 ms 一次，直到超时（8 秒；对方什么都没来时 3 秒结束，第 9 节）。由于双方都是 EIM，各自的映射在第一次发包后就固定了，对方的过滤规则也会因为本端先发过包而放行。

### 7.3 S2：端口预测（对方是顺序分配）

难侧 B 在打洞开始时先向探测服务器发一次请求，得到最新的映射端口 p0，经信令告诉 A；随后 B 用新 socket 向 A 发包，这个新映射的端口大概率是 p0 + δ、p0 + 2δ、……（期间可能被 B 所在网络的其他连接占用几个）。A 向 [p0 + δ, p0 + W·δ] 范围（默认 W = 32）喷包。

"双向预测"（两侧都是顺序分配）见 7.6。

**预测落空后改全范围**（2026-10-15）：同一 NAT 向不同目标分配的端口可能不连续（手机移动卡 APDM：向一台服务器的两个端口给了 45986、45987，向另一台给了 22489），按探测服务器那边算出的范围（S2 的 `pred`，或 BLOCK 的端口段）喷射就会全部落空。服务器记下带范围的那一轮，它失败后，这个会话以后的轮次都不带范围（普通 S3，喷射全部端口）。另外，UDP 中转在打洞期间绑不上时，打洞失败后先再试一次 UDP 中转，还不行才退到 WebSocket 中转（WS 中转上的会话以后不能再打洞）。落空的那一轮失败后，平台知道下一轮（S3，喷全部端口）不同，经 `punch_request` 的队列立即开始它（2 秒的最小间隔，2026-10-26），不再等主叫 10 秒的退避：8 小时测试中 442 次慢的呼叫有 202 次是这样（S2 失败、10 秒后的 S3 才打通，约 19 秒直连）；natlab `s2-miss`（预测之后 NAT 的端口被别的连接占去 3000 个）改前 19.6–20.4 秒、改后 9.3–9.7 秒直连（各 3 次；第一轮 8 秒超时，第二轮约 1.4 秒）。

实现（2026-10-06）：不在打洞开始时另做一次请求和信令往返，而是用 NAT 探测时最后观测到的映射端口加步长作为 `pred` 候选随候选一起发出；服务器给 `strategy: "S2"`，执行上就是 S3：难侧开 N 个新 socket，易侧向 `[pred, pred + 4N·δ]` 喷射（留出期间其他连接占用的端口）。探测时间离呼叫越久，预测越偏，范围放宽到 4N 就是为此。

**每一轮现测**（2026-10-26，回到上面的设计）：`pred` 是登录时的，几分钟后就偏出范围（8 小时测试中 a↔f 的 202 次慢呼叫都是 S2 第一轮落空）。现在 S2 的难侧在开始时从第一个新 socket 向 E1 发 `BIND_REQ`（与 S2B 相同的零件，200/400/800/1600 ms 重发），得到 q0 后经 `punch_info{port}` 告诉易侧；其余 socket 照常开，顺序 NAT 给它们 q0 之后的端口。易侧在收到之前按 `pred` 的范围喷（没有 `pred` 时喷全部端口；顺序分配而没有 `pred` 的现在也给 S2），收到后依次喷 q0 + k·δ（k = 1…3N，再 0…−N：测之前已经发出的几个 socket），然后喷全部端口直到 M 用完。没有探测服务器时不测，照旧按 `pred`。这一轮失败后下一轮照旧是全范围的 S3。

### 7.4 S3：生日悖论暴力打洞（一侧 EIM，一侧难侧）

设 A 为易侧（EIM），B 为难侧。

1. **B（难侧）** 开 N 个 socket（默认 N = 256），每个 socket 向 A 的 `srflx` 地址（固定端口）发 `PROBE`。每个 socket 都会在 B 的 NAT 上创建一个新映射，公网端口未知；
2. **A（易侧）** 用同一个 socket（A 是 EIM，映射固定）向 B 的公网 IP 上的随机端口喷 `PROBE`，总数 M；
3. A 的某个探测包命中 B 的某个映射端口时：
   - 该映射是 B 的 socket k 发往 A 时创建的，B 的 NAT 允许 A 的地址进入（过滤规则满足），于是 B 的 socket k 收到 `PROBE`；
   - B 的 socket k 回 `PROBE_ACK`。此时 A 已经向这个端口发过包，A 的 NAT 也放行，于是 A 收到应答，双向打通；
4. B 关闭其余 N − 1 个 socket。

命中概率（端口空间约 64512 个）：

```
P(成功) ≈ 1 − exp(−N·M / 64512)
```

| N（难侧 socket 数） | M（易侧探测数） | 成功率 |
|---|---|---|
| 256 | 174 | ≈ 50% |
| 256 | 512 | ≈ 87% |
| 256 | 1024 | ≈ 98% |
| 128 | 1024 | ≈ 87% |

**端口块缩小范围**：如果 B 的画像是端口块 [lo, hi]，A 只在这个区间内喷包，端口空间从 64512 缩小到 (hi − lo + 1)，同样的 M 成功率大幅提高。例如区间为 2048 个端口时，N = 64、M = 256 就能达到约 99.97%。

**发送节奏**（默认值，均可配置）：

| 参数 | 默认 | 说明 |
|---|---|---|
| 难侧 socket 数 N | 256 | 受 fd 上限与 CGNAT 端口配额约束，见 8 节 |
| 难侧重发 | 每个 socket 每 1 秒重发一次 | 保持映射、弥补丢包 |
| 易侧喷包速率 | 200 包/秒 | 约 10 秒发完 2000 个 |
| 易侧总数 M | 2000（2026-10-26，原 1024） | 端口块时至少扫遍（放宽后的）块一次，最多 2000；S4 喷包方是端口块时不超过块的一半 |
| 超时 | 150 ms + M / 速率 + 1.5 秒（2026-10-26，原固定 8 秒） | 喷包结束后再等 1.5 秒（难侧每秒重发，最后的喷包可能先于映射到达）：M = 2000 时 11.65 秒，M = 1024 时 6.8 秒 |

喷包打中就停，所以多出的 976 个只在本来要失败的轮次里发出：N = 256 时一轮的失败率从 1.7% 降到 0.04%（公式），难侧的 socket 数不变（CGNAT 配额不受影响）。

**端口选择**：易侧按随机排列遍历候选端口，不重复发送同一端口；跳过 1024 以下端口。

**开 socket 的一方是端口块时**（S3 的难侧、S4 的接收方，2026-10-21）：只开块大小的 1/8（最少 16、最多 256），喷包至少把整个（放宽后的）块扫一遍（最多 2000 个）。块不大时，扫遍整个块就一定打中其中的映射，socket 多开无益；而这些映射在这一轮之后还要在 NAT 上留到超时（一分钟左右），期间同一用户新的 UDP 流拿不到端口。实测一个 200 个端口的块：接收方开一半时，下一个会话的 NAT 探测整整一分钟没有回应，会话退到 WS 中转后再切回 UDP。

### 7.5 S4：难侧喷包、对方开 socket 接收（一方的过滤是 EIF / ADF）

设 B 的过滤是 EIF 或 ADF（接收方），A 是任意难侧（喷包方）。执行上就是 S3，只是"易侧"换成了难侧 A：

1. **B** 开 N 个新 socket，各向 A 的 `srflx` 发 `PROBE`：每个都在 B 的 NAT 上建立一个映射 b_j，并让 A 的 IP 能发进来（ADF 不看端口，所以 A 的映射是哪个端口无所谓）；
2. **A** 用主 socket 向 B 的公网 IP 的端口喷 `PROBE`。A 是 APDM 时，每个包发往一个新目标，都在 A 的 NAT 上新建一个映射 a_x；
3. A 的包打中某个 b_j 时，B 的过滤放行（来自 A 的 IP），socket j 回 `PROBE_ACK` 到 (A_IP, a_x)。被过滤放行的入站包在 b_j 上建立了与 (A_IP, a_x) 的会话，回包从 b_j 发出，正是 a_x 当初发往的地址，A 的 NAT 也放行，双向打通。

命中率与 S3 相同：P ≈ 1 − exp(−N·M / B 的端口范围)，B 是端口块时只喷这一块（放宽后，7.7）。代价：A 是 APDM 时喷 M 个包就占 M 个映射；A 的端口是一块（运营商的配额）时，平台把 M 限制在块的一半以内。两方都能接收时，端口块更小的一方接收（喷包方占映射），否则被叫接收。

依赖的一点：B 的 NAT 对过滤放进来的会话，回包仍从同一个映射发出（基于连接跟踪的 NAT 都是这样）。如果某种 NAT 给这个回包另开一个映射，S4 就打不通，统计数据里会显出来。

### 7.6 S2B：双向预测（双方都是顺序分配）

难点在于"分配给新目标的下一个端口"只有当时才知道：NAT 探测时测到的端口可能是几分钟前的，期间网络里的其他连接已经占了很多。所以每一轮开始时现测：

1. 双方在 `start_at` 各开一个新 socket P，向 E1 发 `BIND_REQ`，得到它的映射端口 p0（A）、q0（B），经平台告诉对方（`punch_info`，signaling.md）；
2. 之后 P 每发往一个新目标，NAT 分配 p0 + δ、p0 + 2δ……（其间被别的连接占去的几个记为偏移 sA、sB）；
3. 收到对方的端口后，双方分 4 遍、每遍 W = 32 个目标发 `PROBE`：主叫在第 r 遍按**升序**发往 q0 + (rW + k + 1)·δB（k = 0…W−1），被叫按**降序**发往 p0 + (rW + W − m)·δA（m = 0…W−1）；已经发过的目标每秒重发一次（同一目标沿用已有的映射，不再分配），弥补先到的包被对方 NAT 丢弃。

主叫的第 k 个和被叫的第 m 个对上，要求 k − m = sB 且 k + m + 1 = W − sA，即 2k = W − 1 + sB − sA：sA + sB < W 且奇偶合适时有解。W 是偶数，所以要求 sA + sB 为奇数。为了让每一遍都换一次奇偶，主叫在每一遍之前先发一个 `BIND_REQ`（"垫片"，多占一个映射，sA 加 1），每次发往一个新目标：第 r 遍发往 E2 的端口 + r（那里没有服务，不会有回应；APDM 对已发过的目标沿用原来的映射，发往同一个目标就不占新端口）。第 r 遍之前垫了 r + 1 个，于是第 r 遍要求到那时别人在双方 NAT 上占去的端口合计与 r 同奇偶；一轮 4 遍都对不上，要求测端口到第 0 遍之间（几毫秒到一个信令往返）以及之后每两遍之间（300 ms）都恰好被占去奇数个。没有别的连接时第 0 遍就能打通。只要合计少于约 30 个，一轮就能打通；每侧最多占 4W + 5 个映射（含测端口的一个）。

**垫片的修正**（2026-10-27）：原来垫片只在第 1、3 遍之前、两次都发往 E2：第二次沿用第一次的映射，不占新端口，第 3 遍的奇偶与第 1、2 遍相同。于是第 0 遍永远对不上（sA = sB = 0），被叫一侧在第 0、1 遍之间被占去奇数个、之后不再变时整轮失败：每侧每秒被占 2 个时约 0.35 × 0.65 × 0.65 ≈ 15%，natlab 的 `s2b` 实测 60 次中 7–8 次第一轮失败。按上面的条件（被占的个数按泊松分布，一段时间 t 里为奇数的概率是 (1 − e^(−2λt)) / 2）：每秒被占 2 个、测端口到第 0 遍几毫秒时，一轮失败的概率由约 15% 降到约 0.004 × 0.35³，可以忽略；测端口到第 0 遍隔 150 ms 时由约 11% 降到约 1%；每秒被占 10 个时两者都约 6%（每段奇偶各半，垫片帮不上忙，要靠下一轮重测）。

实测（用户态 NAT 模拟器，12.1）：双方顺序分配、各自每秒被别的连接占 10 个端口时，3 次中 2 次第一轮打通，另一次第二轮打通。真实网络（一侧在家庭宽带路由器后再加一层模拟的顺序 NAT，另一侧在云主机上模拟，2026-10-21）：6 次全部打通，4 次在第一轮，其余在第二、第四轮；失败的轮次都是对方的顺序分配在一个只有 200 个端口的范围里回绕，或跨过了被其他程序占用的端口。

局限：顺序分配的 NAT 如果只在一个小的端口块里循环（运营商给每个用户一块、块内顺序分配），一轮跨过块的末尾时预测就会落空；目前画像只能是"顺序"或"端口块"之一，不能两者兼有，要靠下一轮从块的前部重新开始。

**失败的一轮立即再来**（2026-10-26）：S2B 每一轮开始时都重测双方的端口，第二轮是一次新的尝试，不是同一计划的重复，所以失败后平台即使计划没变也立即开始下一轮（这一轮真正结束时；提前报告的失败不会用同样的计划替换仍在进行的一轮；仍受 2 秒间隔与 10 轮上限，第 9 节），不等 10 秒的退避；双方端口都已知、4 遍发完后 2.2 秒（两次重发）仍一个探测都没收到时提前报告失败（这一轮照旧跑完，第 9 节）。每个呼叫多占一轮的映射（每侧 130 个）。

### 7.7 S5（已去掉，2026-10-27）

两侧都是小端口块时原来有 S5：双方各用一个新 socket，每秒 4 个包向对方块里的随机端口喷，持续 5 分钟，两块各 512 个端口时平均约 4.5 分钟打通（natlab 里 15 分钟内也常有打不通的：2026-10-26 改前 2 次中 1 次、改后 3 次中 1 次）。它一轮就占 5 分钟、每侧同时活着约 120 个映射，用到它的组合（两侧都是运营商的小端口块）又少，为它要有单独的执行器、计划、长轮次的特殊处理（提前报告不能打断它）。去掉后这样的组合与两个随机端口的对称 NAT 一样不打洞（`skip: no_strategy`），只走中转。

### 7.8 从前几轮学习

一个会话最多打 10 轮，每一轮都能看到对方 NAT **朝向本方**的真实行为，比探测服务器测到的（朝向探测服务器）更准。节点在 `punch_result` 里报告 `seen`：收到的对方探测的源端口（最多 16 个），即对方朝向本方的映射。

平台据此：`seen` 的端口落在不到 4096 个的一段里时，对方 NAT 朝向本方的端口就是这一段（例如某运营商 NAT 对不同目标给的端口不在同一段：对一台服务器给 45986、45987，对另一台给 22489），之后向对方喷包只喷这一段（略为放宽）。至少要两个端口，只有一个时分不出是一段还是随机分配；但对方 NAT 被探测服务器测为端口块、而这个端口在那一块（喷包的范围）之外时，一个就够：朝向本方的块在别处、就在它周围（前后各约 512 个，盖住含它的 512 个端口的块）。一轮在第一次打通时就结束，通常只看到打通的那一个端口（2026-10-30 natlab 全部用例的 62 次报告中 60 次只有一个），原来要两个，下一次呼叫多半学不到。这是看到的而不是猜的，所以猜测的范围落空后改喷全部端口（7.3）时，它仍然保留。它在平台的内存里按"公网 IP | 映射方式 | 端口分配 > 对方的公网 IP"保存一天，同样两个公网地址之间的下一次呼叫一开始就用上。

**过滤不再从轮次里学**（2026-10-27）：原来节点还报告 `unsolicited`（来自本方从没发过包的端口的探测个数），平台据此把本方的过滤按 ADF 算。可 NAT 的过滤状态在映射存活期间一直放行早先发过包的端口：对方的新 socket 恰好拿到这样的端口时它的探测能进来，却说明不了过滤是 ADF（RN-16 第 3 次中 a 被这样误学成 ADF，之后它的呼叫每次先打一轮注定失败的 S1，慢约 3 秒；为此加过"最近发过包的 IP"表与失败后忘掉，都已一并去掉）。现在过滤只用探测服务器测到的；按它给的 S1 失败后仍立即改用表中的策略（7.1）。

### 7.9 低 TTL 预热（可选）

在 S1/S3 中，先发送的一侧的包到达对方 NAT 时，对方可能还没有建立映射，这些包会被丢弃；部分 NAT 对"未请求的入站包"有惩罚行为（例如回 ICMP、临时拉黑源地址）。可选的做法是：前几轮探测包把 IP TTL 设为较小值（例如 3~5，可按 traceroute 结果调整），让它们只在本端 NAT 上创建映射、在到达对方 NAT 之前被丢弃；等对方预热完成（由服务器同步时间点决定）后，再用正常 TTL 发送。默认关闭，由统计数据决定是否启用。

## 8. 资源与安全约束

| 约束 | 默认 | 原因 |
|---|---|---|
| 单次打洞的 socket 数 | ≤ 256 | 文件描述符；CGNAT 通常给每个用户 512~4096 个端口，开太多会耗尽配额，影响用户的其他连接 |
| 全局并发打洞会话 | ≤ 4 | NAS 可能同时被多个客户端访问 |
| 单次打洞发包总数 | ≤ 2000 | 避免被识别为端口扫描 |
| 难侧喷包（S4）、S2B 占的映射 | S4 喷包方是端口块时 M ≤ 块的一半；S2B 每侧 ≤ 4W + 5（133） | APDM 的一方每发往一个新目标就占一个映射；S2B 每秒重发一次已发过的目标（不再新占） |
| 发包速率 | ≤ 200 包/秒 | 同上；家用路由器处理新建映射的能力有限 |
| 同一对端的重试 | 平台安排（第 9 节）：失败后 10 秒、30 秒、1、2 分钟，之后每 3 分钟，一个会话最多 10 轮；失败的一轮让计划变了（7.1、7.3、7.8）或这一轮是 S2B 时下一轮立即开始（向被叫要画像至少隔 2 秒） | 对称型 NAT 的环境短时间内不会变化；计划变了的下一轮是新的尝试，不必等 |
| 主叫一方同时进行的难侧打洞 | 1 个，socket 不到应得的一半时也不打 | 难侧每个 socket 在运营商 NAT 上占一个端口。2026-10-15 手机（移动卡，APDM，每个用户约 500 个端口）：两个难侧打洞同时进行（512 个）时，新的 UDP 目标全部不通——中转绑不上、NAT 探测没有回应，会话掉到 WS 中转，探测失败还让节点以为没有 UDP。现在主叫让出这一轮（`punch_result{busy}`，不计入 10 轮），平台在前一个打洞结束后再发；改后同一张卡 8 台设备的 UDP 中转全部绑上，30 秒内 7 台直连 |
| 两个难侧打洞之间 | 主叫一方：看到端口紧张的迹象时间隔 15 秒，否则不间隔（2026-10-26）；由平台安排（2026-10-27） | 难侧打洞的 socket 关了，运营商 NAT 还要过一阵才回收它们占的端口，紧接着再打一轮会叠在上面；间隔期间会话照常走中转。间隔原来总是 15 秒，可 NAT 回收映射要到它的超时（通常 30–300 秒），15 秒并不能把端口还回来，"同时一个"才是 2026-10-15 那次修复的关键；没有配额的 NAT（家用路由器、云 NAT）上间隔只让排队的会话多等（8 小时测试中一个节点作主叫 P50 7.7 秒）。迹象（节点看到、在 `punch_result` 里报 `pressure`）：难侧打洞期间或结束后 1 分钟内中转绑不上、呼叫时核对或 NAT 探测没有回应（记 10 分钟）；手机平台目前没有可靠的蜂窝网络判断，没有单独的默认值。平台据此让这个主叫（它在这台平台上的所有呼叫）的难侧轮次间隔 15 秒；主叫让出的一轮（`punch_result{busy}`），平台让被叫结束它（`punch_info{stop}`），被叫不再白喷，2 秒后（或那个打洞结束时）再发 |
| 按需连接设备 | 手机 App：`peer_idle` 180 秒；电脑、NAS：0（一直连接） | 端口主要花在打洞上：已保存的设备一直连着时，应用启动、网络切换、挂起恢复都要把每台设备重新打一遍。按需时不用的设备不建会话、不打洞、不保活：用到它的转发时才建（连接先等着，最多 30 秒），最后一个连接结束 `peer_idle` 秒后断开；`npf node wake` 提前建（控制台打开设备详情、资源列表没听到过时）。有 `-R` 映射的设备一直连接（对方随时可能用）。优点：省端口、省电、省流量，网络切换只重连在用的；不足：第一次打开页面要等会话（先走中转，约 1～2 秒），设备发布的资源只在连着时更新 |
| 打洞期间中转绑不上 | 等打洞结束再试（最多 15 秒），仍不行才用 WS 中转 | 同上：端口被打洞占着时绑不上，打洞结束后立即能绑 |
| NAT 探测没有回应 | 立即再测一次，两次都没有回应才定为 udp = 0（2026-10-31：一次冷启动丢了一轮的报文，会话就走了 WS 中转；有 UDP 的节点第二轮照常很快，没有 UDP 的多等 2.2 秒）；之后 5、10、20、30 秒后再测，再往后每分钟一次，直到有回应（原来 5 秒、20 秒、1 分钟、3 分钟后就不再测）；再测有回应时，这期间走 WS 中转的会话回到 UDP 中转（`udp_back`：同一个 AnLiu 连接换载体，2026-10-28 起；之前是主叫结束会话、重连） | 同上：一次失败曾让手机一个小时都以为没有 UDP；2026-10-15 应用重启后第一次探测没有回应，七个会话全部直接走 WS 中转（没有 UDP 时不打洞、不试 UDP 中转）并一直留在那里 |
| 暴力打洞开关 | 服务器可按设备/地区下发关闭 | 出现运营商投诉或路由器异常时可远程关闭 |

- **CGNAT 配额保护**：难侧新建 socket 时，若连续多次探测到的映射端口与已有映射重复，或向探测服务器的请求开始失败，说明配额吃紧，立即停止新建；
- **打洞的目标地址**（2026-10-26）：对方自报的 `pub_ip` 与候选都要经过平台的检查才会被探测、被喷：平台只向它见过的 IP（信令源地址、中转绑定的源地址、备用分配的地址 R）喷包，未验证的 `pub_ip` 只有 S1；转给对方的候选按呼叫过滤，`punch_info` 由平台重新生成；节点自己也拒绝环回、组播、广播、平台端点等地址。详见 [security.md](security.md) 11.1；
- **打洞成功后立即关闭多余的 socket**，让 NAT 尽早回收映射；
- 探测包认证失败时静默丢弃，不回应任何未认证的包，避免被主动探测识别。

## 9. 同步与信令

打洞相关的信令消息的字段定义见 [signaling.md](../protocol/signaling.md) 的"呼叫与端到端连接"一节：

| 消息 | 方向 | 内容 |
|---|---|---|
| `nat_report` | 设备 → 服务器 | NAT 画像（上线时、每次探测后上报） |
| `call` / `incoming` 应答 | 主叫 → 服务器；被叫 → 服务器 | 各自的画像与候选，与 E2E 握手消息一起发送 |
| `punch_start` | 服务器 → 双方 | 所选策略（角色由会话定：主叫为控制方）、易侧 / 难侧、`punch_key`、开始时刻 `start_at`（S1 没有：收到即开始） |
| `punch_result` | 双方 → 服务器 | 结果、选中的路径、耗时、发包数（用于统计和安排下一轮）；提前报告的失败（`early`）、主叫让出的一轮（`busy`）、端口紧张的迹象（`pressure`） |
| `punch_request` | 服务器 → 被叫 | 下一轮之前要被叫的最新画像与候选 |
| `punch_update` | 任一方 → 服务器 | 网络变化后重新测过 NAT、第一次测出 NAT（呼叫发出时还没有候选）、直连失效（附最新画像与候选） |
| `punch_info` | 任一方 → 服务器 → 另一方；服务器 → 一方 | S2B 新 socket 的映射端口（7.6）；平台发的对方新 `srflx`（`cand`：它的中转分配绑定的地址来了或变了，4.5） |

**轮次由平台安排**（2026-10-27）：节点只执行平台发来的一轮、报告结果和本方的变化；下一轮什么时候开始、用什么计划、等多久都由平台决定（`server/internal/signaling/punchsched.go`，一个按事件给出等待时间的函数）：

| 事件 | 下一轮 |
|---|---|
| 接受（口令配对在 `handshake_done` 时） | 立即（第一轮用 `call`、`incoming` 应答里的画像与候选） |
| 一轮失败（这一轮结束时一方报告失败；超时后 10 秒仍没有结果也算） | 计划因此不同（7.1、7.3、7.8）或这一轮是 S2B：立即；否则退避 10 秒、30 秒、1、2 分钟，之后每 3 分钟 |
| 提前报告失败（`early`，这一轮还在进行） | 计划因此不同：立即（替换这一轮）；否则等这一轮结束 |
| 一方的新 `srflx`（它的中转分配绑定的地址来了或变了，平台自己看到，4.5） | 有一轮在进行时并入它；退避等待中：立即 |
| 主叫的难侧另有一轮在进行（同一主叫的别的呼叫，这台平台上） | 不发，等它结束（至多 2 秒再看）；不计入 10 轮 |
| 主叫让出这一轮（`busy`） | 2 秒后（或占着 socket 的打洞结束时），有端口紧张的迹象时还要过 15 秒的间隔；这个呼叫之后的轮次按难侧对待；不计入 10 轮 |
| 一方还没有候选 | 不发这一轮，2 秒后再向被叫要画像；不计入 10 轮 |
| 打通 | 不再安排，直到一方报告直连失效（`punch_update` `path_lost`）：立即，退避从头算 |
| 一方网络变化（`punch_update` `network`） | 退避从头算；没有在进行的一轮时立即；`no_strategy` 停下的也重新规划 |
| 双方都是难侧、没有可用策略 | 发 `skip: no_strategy`，不再安排（直到网络变化） |
| 改用 WS 中转 | 不再安排；UDP 恢复、回到 UDP 中转后重新安排（`udp_back`，2026-10-28），之前直连过的也一样 |
| 10 轮失败（另有至多 14 次让出、没有候选的） | 不再安排，会话留在中转上 |

每一轮开始前平台向被叫要最新的画像与候选（`punch_request`，同时只有一个，相隔至少 2 秒），主叫的由它的 `punch_update` 带来。原来节点（主叫）有自己的退避计时器，到时发 `punch_request` 要新一轮，平台在计划变了时又自己开始一轮，主叫让出的一轮要另发通知，新一轮还要取消主叫的退避、让出的不计数：两套调度要互相对齐，代码分在两边、各有一份重复的规则。现在这些都只在平台上。

**提前报告失败**（2026-10-26）：一轮里对方什么都没来（`PROBE`、`PROBE_ACK`、`NOMINATE` 一个都没有）时，S1 在开始后 3 秒（加入新候选后再等 2 秒）、S2B 在双方端口已知、4 遍发完 2.2 秒后，节点就向平台报告这一轮失败（`punch_result{early}`），计划变了的下一轮（按过滤给的 S1 失败后的 S3，S2B 的下一轮）就早开始；S3、S4、S2 的超时本来就按喷包时长算（7.4）。收到过任何东西就不报。**这一轮本身照旧跑到超时**：S1 收到即开始、没有共同的开始时刻，计划经负载重的链路晚到几秒的一方，它的探测在先开始的一方报告之后才来，照样回应、照样能提名（第一版在报告时就结束了这一轮：一方的计划晚到 4 秒时双方各自空跑 3 秒，从未同时在打，UDP 中转又不通时会话就此落到 WS 中转、再也不能直连：loopback.sh 的 LB-10）。同一轮之后成功，平台照常记下（报告过的失败不算定论）。UDP 中转不通、要等这一轮决定是否改用 WS 中转时，不提前报告（这一轮决定的不只是下一轮的计划）。

**S1 收到即开始**（2026-10-26）：像 ICE 那样，收到对方的候选（`punch_start`）就开始检查，靠重发而不是同步：S1（含 S0）的 `punch_start` 不带 `start_at`。先开始的一方的探测在对方开始之前被丢弃（对方 NAT 还没为它开门，节点也还没有这一轮），对方开始后它的探测穿过先开始一方的 NAT，先开始的一方回 `PROBE_ACK` 并立即回探（触发检查），晚开始的一方最多多等一个重发间隔（前 2 秒 50 ms）。省下的是同步开始的等待（两侧单向时延的较大值 + 150 ms）：natlab 的 `cone` 从发出呼叫到直连 505 ms → 240–310 ms（各 3 次）。其余策略（S3、S4、S2、S2B）仍按下面的办法同步开始：难侧的 socket、喷包与顺序端口的配合都依赖双方的时间。主机防火墙要求先发的一方（下文，`nat` 里带 `lead`）在场时 S1 也照旧同步。

**同步开始**：`punch_start` 中给出**服务器时间的绝对时刻** `start_at`，取"当前时间 + 两侧单向时延的较大值 + 100 ms 余量"。双方用登录时的 `welcome.time` 与 `BIND_RESP` 中的服务器时间校准各自的时钟偏差，在 `start_at` 开始发包，误差在几十毫秒内。不用"按 RTT 推迟发送"的办法，是因为双方可能连在不同的服务器上，任何一台服务器都不知道两侧的 RTT。

对 S3 来说，难侧应当比易侧**稍早**开始（默认提前 100 ms），先把映射建立起来。

**主机防火墙**（2026-10-06 实测）：macOS 应用防火墙对不在允许列表中的程序，若一个 UDP 流的第一个报文是对方主动发来的，会封住这个流（双向）几十秒。所以这类主机必须先发：防火墙开启时节点提前 300 ms 开始发探测（`punch_lead_ms`）。对方在自己开始前收到的探测直接丢弃。打洞要等端到端密钥就绪才能开始，而口令配对（三条握手消息，最后一条由主叫发出）的被叫拿到密钥时往往已过开始时间：2026-10-06 实网组合测试中一台 Linux 主机呼叫一台 Mac（被叫，跨服务器）5 次全部失败，Mac 收到 `punch_start` 后约 200 ms 才完成握手，Linux 主机的探测先到，流被封住（Mac 收到 0 个，Linux 主机收到 192 个）。现在有防火墙的节点收到 `punch_start` 时立即向对方各候选发两次 1 字节报文，先建立出方向的流，再按计划打洞；对方节点静默丢弃这种报文。这样的节点在 NAT 画像里报 `lead`，平台据此对 S1 也给 `start_at`（S1 收到即开始时，对方可能比它早收到 `punch_start`、探测先到）。双方都在这类防火墙后面、又在同一局域网时，同步误差大于单向时延，仍可能互相封住，靠重新打洞或在防火墙中放行解决。

## 10. 选定路径与移交 AnLiu

### 10.1 选定

- 某个候选对在**双向**都收到过对方的探测（收到 `PROBE_ACK`，或者双方各自收到过对方的 `PROBE`）即为可用；
- **主叫为控制方**：第一个可用候选对出现后，若还有更高优先级的候选对在探测（例如 IPv6、`mapped` 或同一局域网的 `host4`），最多等 200 ms，期间它通了就换成它（2026-10-26 实现；原来不论有没有都等 200 ms，而且等待期间也不换），没有就立即发送 `NOMINATE`；被叫回 `NOMINATE_ACK` 后双方确定路径。提名报文用 `nominate_key` 加密（6.5），如果此时 E2E 握手还没完成，主叫等握手完成再提名（握手经服务器只需 1 个往返，通常早于打洞完成）；握手失败则放弃打洞；
- **被叫为受控方**：收到 `NOMINATE` 就以它的来源为路径、回 `NOMINATE_ACK`，不要求这一对是自己验证过的，也不要求与自己验证过的同一 IP：主叫选的对被叫可能没验证过（被叫验证的是 IPv6、主叫提名的是 IPv4，或者提名来自对方的另一个出口、地址池 NAT 的另一个地址），只认同一 IP 的话这些轮次都要跑到超时。`NOMINATE` 用 `nominate_key` 加密、有防重放，只有对方发得出来；它的来源与 `PROBE`、`PROBE_ACK` 的一样先过入站的地址检查（[security.md](security.md) 11.1）；
- 优先级：`host6` > `mapped` > `host4` > `srflx` = `pred` = 暴力打洞与对端反射地址；同级先到先得。

### 10.2 移交

1. 选定路径的 socket 从打洞模块移交给隧道层，本端地址与对端地址固定下来；
2. 已经跑在 UDP 中转上的 AnLiu 连接（`anl_t`，conv 不变）把 output 回调的目标改为新路径，**需要 AnLiu 提供路径切换接口**（重置 BBR 的带宽、RTT 估计，见评估建议）。匿名客户端没有中转（[security.md](security.md) D6），此时 AnLiu 连接在路径选定后才创建，直接跑在 P2P 路径上，也就没有第 3 步；
3. UDP 中转保留 30 秒作为热备，期间中转上仍到达的数据报照常交给 AnLiu（AnLiu 按序号去重），之后释放；
4. WS 中转上不打洞。UDP 恢复（`udp_back`）后会话先回到 UDP 中转（同一个 AnLiu 连接，载体换回数据报），平台随后安排打洞，打通后按上面的步骤移到直连（2026-10-28 起；之前 WS 中转不跑 AnLiu，UDP 恢复时会话结束、重建，[data-channel.md](../protocol/data-channel.md) 第 3 节）。

### 10.3 保活与失效检测

- 用 AnLiu 的 `keepalive_ms` 保活，默认 15 秒（国内部分移动网络的 UDP 映射 30 秒内过期）；
- 映射寿命由备用分配的中转测出（2026-10-26，home-binding.md v0.5 第 5 节：保活由中转发起，节点静默 T 秒后 ping、节点应答；有应答 = 活过 T，三次都没有 = 过期；逐级 25 → 45 → 75 → 120 → 180 秒，二分一次，余量 0.8，10 – 150 秒；节点的应答说主 socket 向别处发过时不上调），不按网络保存，连接变了从头学；AnLiu 的 `keepalive_ms` 不变；
- 直连失效分两步（2026-10-05 按真实网络测试修订，详见 [data-channel.md](../protocol/data-channel.md) 第 3 节）：有未确认的数据、却 `max(3 秒, 2 × RTO)` 收不到对端任何报文（没有未确认的数据时 20 秒：对端的 AnLiu 保活 15 秒一次） → **疑似失效**，之后每个数据报同时经直连和中转发送（中转已释放时先重新申请），每 500 ms 发一个 `PATH_CHECK`；10 秒内收到匹配的 `PATH_ECHO`（经直连的一次往返，只收到对端的其他报文不算）就恢复只走直连，否则放弃直连、留在中转上，主叫按退避策略重新打洞（UDP 中转上的会话才重新打洞，连第一轮最多 10 次，signaling.md "punch_result 与重试"）。没有中转可退（匿名主叫）时，主叫在放弃直连的同时立即请求新一轮打洞。会话依赖的 UDP 中转、WS 中转按同一套规则判定（2026-10-28，data-channel.md 第 3 节"路径的健康"）：UDP 中转的阈值与直连相同（3 秒 / 2 × RTO、空闲 20 秒），WS 中转 30 秒没有任何帧；
- 设备网络变化（地址变化、网卡切换）→ 立即切回中转，重新探测画像并重新打洞。

**接口草案**（与 AnLiu 一样不直接拥有事件循环：socket 由平台层创建，时钟由调用方驱动）：

```c
typedef struct npf_punch npf_punch_t;

typedef struct npf_punch_cb {
    /* 需要一个新的 UDP socket（暴力打洞时会被调用多次）；返回 socket 编号，< 0 表示失败 */
    int  (*open_socket)(void *user, int family);
    void (*close_socket)(void *user, int sock_idx);
    int  (*send)(void *user, int sock_idx, const struct sockaddr *to, const void *buf, int len, int ttl);
    /* 打洞结束：成功时给出选中的 socket 与对端地址，失败时 sock_idx < 0 */
    void (*done)(void *user, int sock_idx, const struct sockaddr *peer, const npf_punch_stats *st);
} npf_punch_cb;

npf_punch_t *npf_punch_create(const npf_punch_config *cfg, const npf_punch_cb *cb, void *user);
int   npf_punch_start(npf_punch_t *p, const npf_punch_plan *plan);   /* 来自 punch.start */
int   npf_punch_input(npf_punch_t *p, int sock_idx, const struct sockaddr *from,
                      const void *buf, int len);  /* 认证失败返回 NPF_EAUTH，交给 AnLiu */
void  npf_punch_update(npf_punch_t *p, uint32_t now_ms);
uint32_t npf_punch_check(const npf_punch_t *p, uint32_t now_ms);    /* 下一次需要调用 update 的时刻 */
void  npf_punch_release(npf_punch_t *p);
```

这样打洞逻辑可以在模拟网络中做确定性测试，与 AnLiu 的测试方式一致。

## 12. 测试

### 12.1 NAT 模拟

Linux 内核 NAT 的行为不能完整覆盖上面的分类（MASQUERADE 默认尽量保持端口，`--random-fully` 可以模拟随机分配，但没有干净的 EIM + EIF 实现）。因此分两层：

1. **用户态 NAT 模拟器**（2026-10-21 实现，平台仓库的测试中，Python）：主机在自己的 network namespace 里，默认路由指向一个 TUN 设备，模拟器读出它的 UDP 数据报，从自己在公网地址上的 socket（一个映射一个）发出，回来的经过滤再写回 TUN。映射（EIM / ADM / APDM）、过滤（EIF / ADF / APDF）、端口分配（保持 / 顺序 / 随机）、端口范围（端口块）、每个目标 IP 一段端口、别的连接占端口的速率、映射数上限（运营商的配额）、映射寿命都可以设定；过滤放进来的入站包在同一映射上建立会话（回包从同一端口发出）。决策表的各格都有用例：S1、S3、过滤测试、S4（两个方向）、S2B（有其他流量时）、S5、从前几轮学习、双 APDF 不打洞；
2. **内核 NAT**：network namespace + nftables，验证在真实协议栈上的行为（`--random-fully`、端口保持、conntrack 超时）。

### 12.2 验收指标

| 场景 | 指标 |
|---|---|
| EIM × EIM | 成功率 > 99%，中位耗时 < 1 秒 |
| EIM × APDM 随机（N=256、M=1024） | 成功率 > 95%，中位耗时 < 6 秒 |
| EIM × APDM 端口块 2048 | 成功率 > 99% |
| APDM 随机 × APDM 随机，双方 APDF | 不尝试，直接留在中转，耗时 0 |

| 顺序 × 顺序（S2B），各自每秒被占 10 个端口 | 两轮内打通；实验室中 3 次里 2 次第一轮、1 次第二轮 |

### 12.3 真实网络

家宽（电信、联通、移动）、4G/5G、公司网络、CGNAT 的组合，长期收集 `punch.result` 统计。

### 12.4 跨服务器实测（2026-10-04）

- **代码**（当时）：打洞模块 `src/punch/punch.c`（2026-10-27 去掉，工具改用 `punch_ev.c`；S1 同时打洞、S3 生日悖论暴力打洞，同步 poll 实现，仅 IPv4）；跨服务器测试时用平台一侧的测试会合服务器和打洞测试工具。S1 先在本机回环联通，再在真实服务器间测试；
- **会合通道**：测试机只开放 UDP 9800–9999，TCP 被过滤，`npf-punchd`（TCP 9920）连不通。因此测试工具增加了 `--manual` 模式：画像与 srflx 已知时直接用命令行下发打洞计划，由本机经 SSH 驱动两端，不经会合服务器。正式环境的会合走 WSS，不受此限；
- **实测结果**（探测服务器 E1、E2 在一台服务器上，E3 在另一台）：

| 组合 | 策略 | 结果 | 耗时 | 说明 |
|---|---|---|---|---|
| 主机 2 × 主机 3（均 EIM） | S1 | 成功 | ~0.23 s | 直连 RTT 12 ms |
| 主机 4 × 主机 5（均 EIM，同机房） | S1 | 成功 | — | RTT < 1 ms |
| 主机 6 × 主机 4（均 EIM，异地） | S1 | 成功 | — | RTT 100 ms |
| 主机 3（EIM）× 主机 1（APDM 随机） | S3 | 成功 | 1.0 / 2.5 s | 喷包 182 / 468 个命中主机 1 的 256 个映射之一 |
| 主机 2（EIM）× 主机 1（APDM 随机） | S3 | 成功 | 0.9 s | 喷包 142 个命中，直连 RTT 7 ms |

  S3 验证了暴力打洞穿透对称型 NAT（主机 1 在云厂商的 NAT 网关后，APDM + 随机端口）：难侧开 256 个 socket 向易侧 srflx 发包，易侧向难侧公网 IP 的随机端口喷 1024 个 PROBE，命中其中一个映射即打通，命中数与生日公式一致（N=256 时期望约 252 个喷包首次命中）；
- **耗时受 SSH 启动偏差影响**：`--manual` 模式两端由两条 SSH 并行启动，偏差可达数秒，双方持续重传直到对齐，因此"耗时"一列偏大，不代表协议本身的延迟。正式环境由会合服务器按 RTT 同步开始（第 9 节），没有这个偏差。

### 12.5 端口映射与 IPv6（2026-10-04）

- **PCP / NAT-PMP**：报文编解码有已知答案测试（`tests/unit`，PCP MAP 60 字节、NAT-PMP MAP 12/16 字节的构造与解析，含错误码拒绝）。本机网关（WSL）不支持 5351，实测走到"无 PCP/NAT-PMP 响应"的优雅失败路径；云主机的网关也不应答 5351，因此真实命中需在支持的家用路由器上验证（待办）；
- **IPv6**：打洞模块（当时的 `punch.c`，现在的 `punch_ev.c`）已改为 family-agnostic（`sockaddr_storage`），S0/S1 支持 IPv6；S3 暴力打洞仍限 IPv4（依赖 NAT 端口行为，IPv6 无 NAT）。候选收集 `ice/candidates.c` 的 `npf_gather_host`（`AF_INET6` / `AF_INET`）提供本机地址。**所有测试机都没有全局 IPv6**，无法做跨机实测；已在本机用 `::1` 回环验证 S1 over IPv6 打通（双方提名成功，地址为 v6）。真实 IPv6 穿透（家宽双栈，开放对端防火墙针孔）待有 v6 环境时验证。

### 12.6 打洞增强的接入（2026-10-06）

- 节点另开 IPv6 主 socket，`host6` 候选用它的端口；双方都有 `host6` 时服务器给 S1，向 IPv6 候选的探测从 IPv6 socket 发出，应答在收到的 socket 上发；本机用 `::1` 验证（`punch.sh`），真实 IPv6 仍待双栈环境；
- PCP / NAT-PMP 由节点在工作线程中请求（阻塞调用不进事件循环），结果作为 `mapped` 候选；路由器外部地址是私网 / CGNAT 地址时不用；服务器把有映射的一侧当作易侧（S1 而不是 S3）；本机替身网关验证了 PCP、NAT-PMP 退回与停止时删除；
- S2 见 7.3 末尾。

### 12.7 打洞优化的实测（natlab，2026-10-26）

## 13. 待定问题

1. **AnLiu 的改动**：导出 SIV 加密原语（或在 NPF 中实现一份）；增加路径切换接口。需要在 AnLiu 仓库中实现；
2. **探测节点部署**：至少两台不同 IP 的机器；节点的健康检查；多地域部署时的就近选择规则。探测节点随签名的服务器列表下发与更新（[security.md](security.md) 7.5）；
3. **N 和 M 的默认值**：需要真实网络数据；CGNAT 端口配额是最大的不确定因素；
4. **IPv6 的防火墙打洞**：家用路由器的 IPv6 防火墙默认拒绝入站，也需要双方同时发包，按 S1 处理即可，但需要实测；
5. **移动端客户端**：手机在 Wi-Fi 与蜂窝网络之间切换时的重新打洞频率与耗电。
6. **全加密流量的可识别性**：6.7 所述的"完全随机本身就是特征"的风险需要在国内真实网络上长期观察（对比地址探测、打洞、AnLiu 数据三类流量被干扰的比例），必要时再考虑模仿某种常见 UDP 协议的外形。
