# 安全设计

状态：草案 v0.25。更新日期：2026-10-22。变更记录见文末。本文是身份、认证与加密的设计；与实现的出入记在平台的实现说明里。

本文描述 NPF 的身份、认证与加密设计：设备凭什么登录服务器、设备身份如何分配和恢复、用户用什么编号找到设备、客户端与设备之间的数据如何做到服务器不可知。打洞报文的加密格式见 [nat-traversal.md](nat-traversal.md) 第 6 节，本文不重复。

---

## 1. 需求与对应章节

| # | 需求 | 章节 |
|---|---|---|
| R1 | 设备必须持有服务器签发的凭证才能登录；凭证交给设备厂家，形式可以是一串 Base64 字符串 | 3、4 |
| R2 | 设备凭厂商凭证获取自己的身份；身份保存在设备内，或者设备启动时凭一串编号重新分配到同一个身份 | 5 |
| R3 | 用户用唯一的数字编号标识设备，便于输入 | 6 |
| R4 | 客户端与设备之间交换的数据，服务器不可知 | 8、9 |
| R5 | 设备与服务器之间用 WebSocket；P2P 建立之前经服务器中转 | 7、10 |

**非目标**

- 隐藏元数据：服务器知道谁在什么时间连了谁、流量多大（见 9.7）；
- 设备被攻破（root 权限被拿到）之后的安全：此时设备密钥、NAS 数据都已暴露，不在本文范围；
- 浏览器客户端：浏览器跑不了 AnLiu 和本文的握手，如果将来需要，另行设计。

**吸取 pangolin 的教训**：pangolin 的数据加密密钥就是会话 CID，由服务器分配，服务器可以解密全部数据；AES-CBC 使用固定 IV；TURN 凭据硬编码在固件里。NPF 的会话密钥只由两端的 DH 产生，服务器全程不经手。

| D14 | 服务器列表连不上服务器时的外部更新渠道**同时使用 DoH 查询 TXT 记录与 HTTPS 静态文件** | 7.5 |

## 2. 威胁模型

| 攻击者 | 能力 | 本设计的防护 |
|---|---|---|
| A1 网络攻击者（含审查设备、终止 TLS 的 CDN） | 窃听、篡改、丢弃、重放、屏蔽路径上的流量 | 外层 TLS 伪装；WebSocket 内 Noise 握手做双向认证并加密信令（7.2）；数据端到端加密（9） |
| A2 服务器（诚实但好奇） | 看到经它中转的所有数据，按协议办事 | 数据只以 AnLiu 密文或 WS 中转的端到端记录经过服务器，密钥由两端 DH 产生（9、10） |
| A2' 服务器（主动作恶或被攻破） | 可以签发假证书、冒充设备或客户端、篡改握手 | 首次配对用服务器无法伪造的信任来源（扫码或 PAKE 口令，9.2），之后固定对端公钥；"托管信任"模式明确不防此类攻击 |
| A3 固件提取者 | 从固件里拿到型号凭证（一型一密） | 配额、限速、序列号白名单、吊销（4.1）；已配对的客户端能发现身份被顶替（9.6） |
| A4 恶意客户端 | 知道设备号，尝试爆破访问口令、骚扰设备 | 服务器闸门 + 被叫闸门两道授权（8.3）；PAKE 每次只能猜一次，失败锁定 |
| A5 冒牌服务器 | DNS 劫持、伪造服务器列表 | 服务器列表由根密钥链签名、带版本号防回滚；设备只和持有列表中服务器静态私钥的一方完成握手（7.2） |

结论：要在 A2' 面前也保证 R4，客户端对设备公钥的信任**不能只来自服务器**。所以首次配对要借助一个服务器拿不到的秘密（屏幕上的二维码或用户输入的口令）；如果用户选择"托管信任"（直接信任服务器签发的设备证书），体验最好，但服务器可以做中间人，界面上要说清楚。

## 3. 身份与密钥体系

### 3.1 总览

```
NPF 根密钥（离线保管，Ed25519；固件内置 2 把根公钥，便于轮换）
├── 厂商凭证签发密钥 ──→ 型号凭证（一型一密，每个厂商/型号一份）
├── 设备证书签发密钥（在线，auth 服务，放在 KMS/HSM）──→ 设备证书、客户端证书
└── 服务器列表签名密钥 ──→ 服务器列表（含每台服务器的身份公钥）
                             └── 服务器身份密钥（每台服务器一把）

服务器内部：ticket_secret、probe_key（见打洞文档 6.4）、服务器之间 mTLS 的内部 CA

设备身份密钥：设备本地生成，或由一机一密凭证派生（第 4、5 节）
客户端身份密钥：客户端本地生成（第 8 节）
会话密钥：每次连接由客户端与设备 Noise 握手产生，只存在于两端（第 9 节）
```

| 密钥 | 算法 | 持有者 | 用途 | 轮换 |
|---|---|---|---|---|
| 根密钥 | Ed25519 | 离线机器，多人分片保管 | 只签中间密钥 | 极少；固件内置两把，一把备用 |
| 厂商凭证签发密钥 | Ed25519 | 离线或半离线 | 签型号凭证 | 每年 |
| 设备证书签发密钥 | Ed25519 | auth 服务（KMS/HSM） | 签设备证书、客户端证书 | 每年，旧密钥签的证书继续有效到过期 |
| 服务器列表签名密钥 | Ed25519 | 运维离线签发 | 签服务器列表 | 每年 |
| 服务器身份密钥 | X25519 | 每台服务器（CDN 接入点由其后的源站共享一把） | WebSocket 内 Noise 握手的服务器静态密钥 | 随时，更新服务器列表即可 |
| 设备身份密钥 | Ed25519 + X25519 | 设备 | 登录服务器；E2E 握手的静态密钥 | 设备重置时（一型一密）或永不（一机一密） |
| 客户端身份密钥 | Ed25519 + X25519 | 客户端 | 登录服务器；E2E 握手的静态密钥 | 重装时 |
| 会话密钥 | X25519 临时密钥 → ChaCha20-Poly1305 / AnLiu PSK | 客户端与设备 | 本次连接 | 每次连接 |

每个身份的两把密钥（签名用 Ed25519、DH 用 X25519）由同一个 32 字节 `seed` 按不同标签派生，只需要保存 `seed`：

```
sign_sk = KDF(seed, "npf sign v1")      → Ed25519 私钥种子
dh_sk   = KDF(seed, "npf dh v1")        → X25519 私钥
KDF     = BLAKE2b-256(key = seed, msg = 标签)
```

### 3.2 证书格式

不用 X.509：解析代码大、历史漏洞多，而证书的签发方和校验方都是我们自己。NPF 证书是定长字段 + TLV 扩展的紧凑二进制格式（小端序）：

```
cert = ver(1)=1 | type(1) | issuer_key_id(4) | serial(8) | subject(8)
     | not_before(4) | not_after(4) | ext_len(2) | ext(ext_len)
     | sign_pub(32) | dh_pub(32) | sig(64)

sig           = Ed25519(签发密钥, "npf-cert-v1" | sig 之前的全部字节)
issuer_key_id = BLAKE2b(签发公钥)[0..3]
时间          = Unix 秒
```

扩展是 TLV（`type(1) | len(1) | value`，整数小端）：1 `key_gen`（u32）、2 `vendor_id`（u32）、3 `product_id`（u32）、4 `account_id`（u64）、5 `perms`（u16，位 n 表示可签发 type n 的证书，位 8 可签服务器列表，位 9 可签 grant）、6 `hosted`（u8）、7 `quota`（u32，型号凭证的注册总量，0 不限；厂家证书中为该厂家每个型号最多能设的值）、8 `rate`（u16，型号凭证每小时注册数，0 不限；厂家证书中同上为上限）、9 `flags`（u8，型号凭证；位 0 要求序列号白名单）、10 `reg`（u64，型号凭证：平台登记该型号时生成的登记号）。已知类型长度不对时整张证书无效，未知类型跳过。

| type | 名称 | subject | 签发者 | 扩展 |
|---|---|---|---|---|
| 1 | 中间证书 | 用途编号 | 根密钥 | 允许签发的证书类型 |
| 2 | 型号证书（一型一密的型号凭证） | vendor_id(4) \| product_id(4) | 该厂家的厂家证书（type 6） | vendor_id、product_id、配额、速率、是否要求序列号白名单 |
| 3 | 设备证书 | 设备号 | 设备证书签发密钥 | key_gen（密钥代数，见 5.3）、vendor_id、product_id |
| 4 | 服务器证书 | server_id | 服务器列表签名密钥 | **不再使用**（D16）：服务器公钥直接写在签名列表中，见 7.5；编号保留 |
| 5 | 客户端证书 | client_id | 设备证书签发密钥 | account_id |
| 6 | 厂家证书 | vendor_id | NPF 厂家签发证书（type 1，只能签 type 6） | vendor_id、`perms`（可签 type 2）、型号配额与速率的上限 |

没有 DH 公钥的证书（type 1、2、6），`dh_pub` 填全 0。证书链一般两级（根 → 中间 → 叶子），中间证书随叶子证书一起发送；一型一密的型号证书是四级：根 → NPF 厂家签发证书 → 厂家证书 → 型号证书（4.1）。

**谁校验什么**：服务器保存所有签发公钥，校验型号凭证、设备证书和客户端证书；设备和客户端内置根公钥，校验服务器列表；客户端只在"托管信任"模式下校验设备证书（9.2）。吊销状态都由服务器查自己的数据库，设备端不需要吊销列表。

## 4. 厂商凭证（R1）

凭证交给设备厂家，由厂家写入固件或产线烧录。借鉴 IoT 平台（如阿里云 IoT）的做法，支持两种模式，由厂商按产品情况选：

| | 一型一密（型号凭证） | 一机一密（设备凭证） |
|---|---|---|
| 形式 | 每个型号一串字符串，所有设备相同，写进固件 | 每台设备一串字符串，产线逐台烧录 |
| 被提取后的影响 | 攻击者可以注册任意多个假设备（受配额限制） | 只影响那一台设备 |
| 设备身份丢失后 | 按序列号 + 硬件指纹重新分配原设备号，但密钥会变（5.3） | 重新派生出完全相同的身份，什么都不变 |
| 设备号 | 首次注册时分配 | 生成凭证时预分配，可以印在标签 / 二维码上 |
| 产线成本 | 无 | 需要逐台烧录，并把设备号印在标签上 |
| 适合 | 软件包形式分发（如 NAS 套件中心的应用）、没有产线流程的厂商 | 自有硬件、有产线的厂商；没有可写存储的设备 |

**决定（D1，2026-10-05 修订）**：两种模式第一版都实现。厂商有产线、要出厂预写设备号时用一机一密（5.6）；以软件包形式分发、没有产线流程时用一型一密。

### 4.1 型号凭证（一型一密）

型号凭证由**厂家自己签发**（2026-10-09 用户要求），证书链为：

```
NPF 根（离线）
 └ NPF 厂家签发证书（type 1，只能签 type 6；私钥离线，NPF 保管）
    └ 厂家证书（type 6，subject = vendor_id；私钥由厂家生成并保管，NPF 只拿到公钥）
       └ 型号证书（type 2，subject = vendor_id | product_id << 32；厂家签发，NPF 不参与）
          └ 设备证书（type 3，设备注册时由服务器签发）
```

```
凭证字符串 = "NPFV2." + base64url(厂家证书 | 型号证书 | model_seed(32) | chk(4))
chk        = BLAKE2b(前面全部字节)[0..3]      ; 发现抄写、截断错误
```

约 530 个字符。`model_seed` 派生出型号的签名私钥，型号证书里是对应的公钥。设备端**只在注册（5.2）时使用**这份凭证，把两张证书发给服务器，用型号私钥签名，证明"我是该型号的正规固件"；日常登录用的是设备自己的密钥。

- **签发流程**：厂家用 `npf-vendor keygen` 生成厂家密钥，把公钥交给 NPF（NPF 打电话给厂家档案里的联系人核对公钥指纹）；NPF 用离线的厂家签发密钥 `npf-admin vendor issue` 签发厂家证书交回。**每个型号先在平台登记**（2026-10-17）：平台分配型号号、生成登记码，厂家用 `npf-vendor model -reg 登记码` 签发型号凭证（型号证书带登记号，扩展 10），再把凭证的公开部分交给平台绑定（`npf-admin vendor bind`）。NPF 从不经手厂家私钥和型号私钥；
- **注册以平台登记为准**：设备注册时，服务器校验证书链的签名（不看厂家证书、型号证书的有效期），再要求型号已登记、未停用、未过登记的有效期，且这张型号证书已绑定、未吊销；配额、每小时注册数、白名单以登记为准（型号证书里也有时取较小的）。厂家证书的有效期管的是能不能签发和绑定新型号：绑定时厂家证书必须有效、未吊销，所以过期的厂家证书签不出能用的新型号；
- **厂家证书约束型号**：型号证书的厂家号必须与厂家证书相同，有效期不超过厂家证书；厂家证书可以规定每个型号的注册总量与每小时注册数的上限（扩展 7、8），有上限时型号必须设置且不超过它；
- **吊销**：可以吊销绑定的某张型号证书（用它的设备不能再注册），也可以吊销厂家证书（它不能再绑定新的型号证书，已绑定的型号照常注册）；停用登记则这个型号都不能再注册。都不影响已经注册的设备。

型号凭证写在固件里，迟早会被提取出来（A3）。防护措施：

- **配额**：每份型号凭证有注册总量上限和每小时注册速率上限，超出拒绝并告警；
- **序列号白名单（可选）**：厂商把出货的序列号列表上传到厂商后台，只有名单内的序列号能注册。这一项做到了，就基本等同于一机一密的安全性；
- **吊销**：凭证泄露后厂家签发新凭证、绑定到同一登记，再吊销旧的那张，新固件使用新凭证；厂家密钥泄露时吊销厂家证书，厂家生成新密钥后由 NPF 重新签发，已绑定的型号不受影响。吊销**不影响**已经注册的设备（它们用的是自己的密钥）；
- **异常检测**：注册被拒按原因计数；有设备拿没有绑定过的型号证书注册时，几乎可以断定厂家私钥泄露，管理界面报警。同一序列号反复注册、同一 IP 大量注册、注册后从不在线等，也进入告警。

### 4.2 设备凭证（一机一密）

```
凭证字符串 = "NPFD1." + base64url(vendor_id(4) | product_id(4) | 设备号(8) | seed(32) | chk(4))
```

约 70 个字符，可以写入出厂分区、U-Boot 环境变量、OTP 等只读位置。`seed` 就是设备身份密钥的种子（3.1），设备每次启动都能从它派生出同一对密钥。设备凭证与默认口令一起构成出厂数据（5.6）。

**批量生成**用平台提供的凭证工具 `npf-cred`，两种方式：

1. **厂商自己生成（推荐）**：厂商在自己的机器上运行 `npf-cred gen`，得到凭证字符串列表（留在厂商）和公钥列表，只把公钥列表上传到 NPF 厂商后台，后台为每个公钥分配设备号并回传。NPF 从不经手设备秘密；
2. **NPF 生成**：后台生成并导出凭证 CSV，只保留派生出的公钥，不保存 `seed`。

服务器端对每台设备只存 `(设备号, vendor_id, product_id, sign_pub, dh_pub, 状态)`。一机一密的设备不需要注册步骤，第一次登录（7.2）就是激活：`login` 中不带设备证书，服务器用握手得到的静态公钥与预存的 `dh_pub` 比对，一致即激活，并在 `welcome` 中签发设备证书。

**默认口令也在这一步生成**：`npf-cred gen` 同时为每台设备随机生成默认口令（规则见 5.5），与凭证字符串一起留在厂商，**不上传**给 NPF。

## 5. 设备身份的获取与恢复（R2）

### 5.1 设备身份的内容

| 字段 | 说明 |
|---|---|
| 设备号 | 8 字节，第 6 节 |
| `seed` | 32 字节，派生设备的签名密钥与 DH 密钥 |
| 设备证书 | type 3，服务器签发，有效期 1 年，登录时自动续签 |
| `key_gen` | 密钥代数，同一设备号每换一次密钥加 1 |
| 默认口令 | 出厂数据中的口令（一机一密），或首次注册成功时本地生成（一型一密）；不可修改（5.5） |
| 当前口令 | 配对时实际使用的口令，初始等于默认口令；可以修改，可以恢复为默认口令（5.5） |

一型一密的设备把身份保存在身份文件（实现中为 `identity`，内容是 Base64url 的 `seed`；路径可配置，放在 NAS 的持久化卷上），权限 0600，写入时先写临时文件、`fsync`，再 `rename`，防止断电损坏。一机一密的设备从出厂数据得到 `seed`、设备号和默认口令，只需要在可写存储中保存设备证书的缓存、当前口令、授权列表等本地状态（实现中为 `state.json`，写法同上）；它们丢失时，证书在下次登录时重新签发，当前口令回到默认口令。

### 5.2 首次注册（一型一密）

```
设备                                                   服务器
 │ 生成 seed，派生 sign_pub / dh_pub
 │ WSS 连接，Noise_XK 握手（7.2），设备静态密钥 = dh_pub
 │ enroll {vendor_cert, serial, hw_fp, sign_pub,
 │         sig_v = Ed25519(vendor_key, T),
 │         sig_d = Ed25519(device_sign_key, T)} ─────────►   （握手后的第一条消息）
 │                          T = "npf-enroll-v1" | h | serial | hw_fp | sign_pub
 │                          h = Noise 握手哈希
 │                                                     校验型号凭证链、吊销、配额、速率、白名单
 │                                                     否则查 (vendor_id, serial) 是否已有记录 → 5.3
 │                                                     分配设备号，签发设备证书（key_gen = 1）
 │ ◄──────────── enrolled {设备号, device_cert}
 │ 原子写入 identity.bin
 │ 继续按 7.2 登录（同一条连接，无需重连）
```

实现（2026-10-06，2026-10-09 改为厂家证书链）：`T` 的确切编码见 signaling.md 的 `enroll`（`h` 为 64 字节的 BLAKE2b 握手哈希，`serial` 前加 1 字节长度）。设备在 `enroll` 中发送厂家证书与型号证书（`model_chain`），服务器用 PKI 目录中的 NPF 厂家签发证书（`vendor.cert`，私钥 `vendor.key` 与根密钥一样离线保管）校验厂家证书，再用厂家证书校验型号证书（4.1）。**硬件指纹由多项组成**（2026-10-09）：每一项单独哈希 `BLAKE2b(key = model_seed, "npf hwfp v2" | 种类 | 0 | 值)[0..15]`（`model_seed` 充当厂家盐），设备把各项的种类与哈希发给平台。默认的项：物理网卡 MAC（排序后作为一项，`mac`；只用出厂烧录的全局地址，系统生成的本地管理地址——Wi-Fi 私有地址、网桥、虚拟机——会变，只在没有全局地址时才用）、板载 eMMC 的 CID（`emmc`，只取类型为 MMC 的焊接存储，不取 SD 卡）、DMI 系统 UUID 或主板序列号（`board`）、SoC 序列号（`soc`，设备树或 `/proc/cpuinfo`）；读不到或是厂家占位值（如 "To be filled by O.E.M."、全 0）的项不用；**数据盘（硬盘、SSD）的序列号与容量不用**：用户会换盘、扩容。什么都没有时用机器 ID（`mid`，重装系统会变）。厂家可以用 `hw_info = 值1|值2|值3` 自己给出各项（`v1`、`v2`…）。**序列号**由厂家配置（`serial` / `serial_file`）；没有时设备用物理网卡中最小的 MAC 地址（`mac-001132aabbcc`），没有网卡地址时用机器 ID 的哈希（`mid-…`），产线不必逐台写入。

两个签名分工不同：`sig_v` 证明"是该型号的正规固件"，`sig_d` 证明"持有这把签名密钥"；`dh_pub` 的持有已由 Noise 握手本身证明。签名内容包含握手哈希 `h`，每次握手都不同，抓包重放或转发到别的连接都无效。

- `serial`：厂商定义的设备序列号（通常印在机身标签上，不是秘密）；没有时由设备从网卡地址生成（见下）；
- `hw_fp`：硬件指纹，`BLAKE2b(厂商盐 | 厂商定义的硬件信息)`，硬件信息由厂商选，例如 eMMC CID + CPU 序列号 + 主板序列号。这些信息只能在设备本地读到，远程攻击者不容易知道，但也不是强秘密；

### 5.3 身份丢失后重新分配

身份丢失的情况：恢复出厂设置、重装系统、换硬盘、只读文件系统上的设备每次启动都"失忆"。

**一机一密**（含出厂预写的设备，5.6）：从出厂数据重新派生，设备号、密钥和默认口令完全不变，客户端无感知；当前口令回到默认口令。**没有可写存储的设备应当使用一机一密。**

**一型一密，设备号由服务器分配**：设备生成新 `seed` 后按 5.2 重新注册，服务器按 `(vendor_id, serial)` 找到原记录，再按下表处理：

| 情况 | 处理 |
|---|---|
| 没有记录 | 分配新设备号 |
| 有记录，硬件指纹的多数项相同，原身份已离线 5 分钟以上 | **把原设备号重新分配给它**，换成新公钥，`key_gen + 1`，吊销旧证书，通知设备属主 |
| 有记录，硬件指纹的多数项相同，原身份正在线 | 拒绝，按疑似克隆告警 |
| 有记录，硬件指纹的多数项不同 | 拒绝；属主在管理后台"释放设备号"后才能作为新设备注册 |

**多数项**：与平台记录的各项比较，相同的项数超过记录项数的一半即为同一硬件（3 项中 2 项、1 项中 1 项）。分母用**记录的项数**，设备少报几项不会更容易通过（只报一个公开的 MAC 冒认不了有 3 项记录的设备）。认回后记录换成这次的各项，以后再换一个部件仍能认回。

**为什么不直接用硬件指纹派生密钥**（那样一型一密也能做到密钥不变）：硬件指纹不是强秘密，一旦被人猜到或读到，攻击者就能派生出完全相同的密钥，冒充设备且**任何人都察觉不到**。现在的做法是：即使攻击者满足了重新分配的条件、顶替了设备号，他拿到的也是一把新密钥，已配对的客户端会发现"设备身份已变更"并拒绝自动连接（9.6），属主也会收到通知。

### 5.4 克隆检测

同一设备号、同一把密钥在两个地方登录，说明身份文件被复制了。处理：后登录的连接替换先登录的（正常的断线重连也是这种情况）；如果一小时内来回替换超过 10 次，判定为克隆，冻结该设备号并通知属主。

被替换的连接先收到 `replaced` 事件（signaling.md）再被关闭。节点据此不再立即重连：等 10 秒，之后每次翻倍，最长 5 分钟（上一次在线超过 2 分钟时从 10 秒重新算），并在日志里说明"这个身份在别处登录了"。否则同一身份的两个进程（同一台机器上的两份，或复制到另一台机器的身份文件）每秒互相顶替一次，一直不停，期间的会话随时被打断，日志里只看到反复的登录（2026-10-21 测试中两个遗留的测试进程这样持续了一个小时）。同一台机器上，npf 程序在运行时给身份加锁（设备的 `state` 文件旁、或身份目录里的 `.lock`），第二个进程立即退出并说明原因。


### 5.5 访问口令：默认口令与当前口令（D2、D20）

访问口令就是用户配对时输入的配对码，**只保存在设备本地**，从不发给服务器。设备分开保存两个值：

| | 来源 | 保存位置 | 能否修改 |
|---|---|---|---|
| **默认口令** | 一机一密：出厂数据中的口令（5.6），印在标签上；一型一密：首次注册成功时本地随机生成 | 一机一密在只读的出厂分区（实现中为配置文件的 `password`）；一型一密在身份文件 | 不能 |
| **当前口令** | 初始等于默认口令 | 可写存储（实现中为 `state.json`），权限 0600 | 能修改，能恢复为默认口令 |

配对（9.3）时使用的是**当前口令**。

- **默认口令每台设备不同，随机生成**：8 位，字符集为去掉易混淆字符（0/O、1/I/L）的 32 个大写字母和数字，约 40 位熵，显示为 `K7QM-3XRT`。**不允许全型号共用一个默认口令**（如 `admin`、`123456`）：设备号是公开的，共用口令等于没有口令；这也是 ETSI EN 303 645 等 IoT 安全规范的明确要求；
- **修改口令**：管理员在 NAS 管理界面或控制台（`npf passwd`）修改。新口令至少 8 位；
- **恢复默认值**：管理员在 NAS 管理界面或控制台（`npf passwd --reset`）把当前口令恢复为默认口令。用户忘记修改后的口令时，可以凭标签上的默认口令（一机一密）或在本地查看默认口令（一型一密）重新配对；
- **修改或恢复时可以选择"同时移除所有已配对的客户端"**，默认不移除：已配对的客户端靠固定下来的公钥认证，不再用口令。怀疑口令泄露时应当勾选；
- **只能在本地修改**（D21）：修改和恢复都要求能访问 NAS 管理界面或设备控制台。口令不经过服务器，服务器无法修改或重置；客户端也不能远程修改，即使是所有者经端到端通道也不行。这样，所有者的客户端或账户被盗用时，攻击者也改不掉设备的口令；
- **在哪里看**：NAS 管理界面的 NPF 页面、`npf show` 命令显示当前口令；默认口令另外显示，并注明当前口令是否已被修改。厂商也可以把它显示在设备的屏幕或 App 上；
- **当前口令丢失**（可写存储损坏、一机一密设备恢复出厂设置）：回到默认口令；
- **身份重新分配（5.3）时**：一型一密且没有出厂数据的设备生成新的默认口令，旧口令作废；
- **口令失败锁定**：按设备计数（8.3），修改或恢复口令时清零。

40 位熵足够：PAKE 使攻击者只能在线逐个尝试，而设备每连续失败 5 次锁定 15 分钟且时间递增（8.3），在线穷举不可行。

### 5.6 出厂预写（一机一密，D10）

为方便生产，厂商可以在出厂时把设备号和默认口令写进设备，并印在机身标签或包装上（设备号 + 默认口令 + 二维码），用户开箱即可使用。**出厂预写统一采用一机一密**：出厂数据就是 4.2 的设备凭证加默认口令。

```
出厂数据 = 设备凭证字符串（"NPFD1."，4.2，含设备号与 seed） + 默认口令
```

**生成**：厂商用 `npf-cred gen` 在本地批量生成：每台设备的 `seed`（派生设备密钥）和默认口令都随机生成，留在厂商；只把公钥列表上传到 NPF 厂商后台，后台为每个公钥分配一个随机的设备号（不是连续号段，理由同第 6 节）并回传。NPF 只保存公钥，**既不知道设备密钥，也不知道默认口令**（R4）。

**写入设备**：出厂数据写在只读的出厂分区（或 U-Boot 环境变量、OTP 等），恢复出厂设置不会清除。设备号和默认口令印在标签上；`seed` 不印，只存在设备里。

**首次使用**：不需要注册步骤，第一次登录即激活（4.2）。

**恢复出厂设置后**：从出厂数据重新派生，设备号、密钥、默认口令都不变，已配对的客户端无感知；当前口令回到默认口令，本地授权列表按厂商的恢复出厂策略处理（建议清空，用户用标签上的默认口令重新配对）。

**与一型一密的对比**：原方案中出厂预写只写设备号和激活码，设备密钥仍在首次注册时生成，恢复出厂设置后密钥会变、已配对的客户端会看到"设备身份已变更"。改为一机一密后，产线成本几乎不变（同样是逐台写入一串数据），这个问题不再存在，也不再需要激活码。

## 6. 设备号（R3）

**格式**（D8）：9 位十进制数字 = 8 位随机数（首位 1–9）+ 1 位 Damm 校验位。显示为 `123 456 789`，输入时忽略空格和短横线。

- **随机分配而不是顺序递增**：顺序编号能被逐个枚举，也会暴露出货量；
- **校验位用 Damm 算法**：能发现所有的单个数字输错和相邻两位颠倒；Luhn 算法漏掉 `09 ↔ 90` 的颠倒。客户端在用户输完时本地校验，大部分输错不需要发请求就能提示；
- **容量**：9000 万个号码；分配时随机选取，与已有号码冲突就重选。设备数接近容量的一半时（约 4500 万台），随机选取的冲突率明显上升，届时再扩展位数（旧号码不变，新号码加长一位；长度不同即可区分新旧号码，校验算法不变）；
- **永不回收**：设备号被释放后也不再分配给别的设备，避免客户端把新设备误认为旧设备；
- **内部表示**：设备号就是设备的主键（uint64），打洞票据里的 ID 字段也用它（已同步修改 [nat-traversal.md](nat-traversal.md) 6.4）；
- **出厂预写**（D10）：厂商预先申请号码并写入设备，印在机身标签上（5.6）。

**设备号是公开的，不是秘密**。知道设备号只能"请求连接"，能否连上由第 8、9 节的授权决定。防止被用来扫描：

- 按设备号查询之前，客户端必须先完成 7.2 的握手与登录（匿名客户端也要，用客户端公钥登录）；
- 每个 `client_id`、每个源 IP 每小时最多查询 30 个不同的设备号；
- 对"不存在"和"无权访问"返回相同的结果，不泄露设备是否存在、是什么型号。

## 7. 设备与服务器之间（R5，上半部分）

### 7.1 传输层

- WebSocket over TLS 1.3（WSS），默认 443 端口，URL 路径由服务器列表下发；
- 设备端 TLS 库使用 mbedTLS 3.6 LTS，静态链接（D4，选型与实测见 12.2）；
- **设备不校验服务器的 TLS 证书，安全性也不依赖 TLS**（D5）。TLS 只起伪装作用：让流量看起来与普通 HTTPS 一样，并隐藏 URL 路径。双向认证和信令加密全部由 WebSocket 内的 Noise 握手完成（7.2）。好处是：
  - 设备不需要内置 CA 证书集合，不依赖 NAS 系统的证书库（很多 NAS 的证书库多年不更新），也不受证书过期、CA 吊销的影响；
  - 服务器可以使用任意证书，包括只有 IP 的自签名证书。域名被封锁时，服务器列表中的纯 IP 服务器照样可用；
  - **可以经 CDN 接入**：CDN 终止 TLS 后看到的只是 Noise 密文和 AnLiu 密文，既读不到内容，也无法冒充任何一方；
  - 主用服务器仍然建议使用公共 CA 签发的正规证书，这样从外部看与普通网站没有区别。

### 7.2 WebSocket 内的 Noise 握手与双向认证

WebSocket 升级完成后，设备与服务器做 `Noise_XK_25519_ChaChaPoly_BLAKE2b` 握手。WebSocket 上用 **binary 消息**：每条消息就是一条 Noise 握手消息，或一条 Noise 传输密文（其中是一个 JSON 信令对象），不再编码。2026-10-22 之前用的是 text 消息、内容为同样字节的无填充 Base64url；过渡期服务器对节点两种都收，并按节点第一条消息的形式回复，服务器之间只用 binary（[信令协议](../protocol/signaling.md)“参与方与承载”）：


```
prologue = "npf-ws-v1"

D → S   e, es          设备预先知道服务器静态公钥 rs（来自签名的服务器列表）
S ← D   e, ee          只有持有 rs 私钥的服务器才能正确回应
D → S   s, se          设备静态公钥（设备证书中的 dh_pub）加密传输，并以 DH 证明持有私钥

握手完成后，双方用 Noise 的传输密钥收发信令：
D → S   login   {设备号, device_cert, 本地服务器列表的 serial}     （首次注册时改为 enroll，见 5.2）
S → D   welcome {device_cert（新签或续签）, ticket, probe_key × 2, relay_day_key × 2,
                 探测端点（nat-traversal.md 4.1）, 服务器列表（仅当有更新的版本，7.5）, time}
字段定义见 signaling.md 的"接入与服务器列表"一节
```

- **服务器静态公钥从哪来**：签名的服务器列表中每个接入点直接带有 `dh_pub`，它就是 `rs`；列表的签名链到固件内置的根公钥（7.5）。原设计每个接入点另带一张服务器证书（type 4），列表签名已经担保了其中的公钥，单独的证书是多余的，已去掉（D16）。直连的接入点每台服务器一把；**CDN 接入点**由 CDN 背后的所有源站共享一把接入点密钥（CDN 会把连接分给哪台源站是不确定的）；
- **设备认证服务器**：第 2 条消息的认证依赖 `es`，冒充者没有服务器静态私钥，这条消息无法通过验证，设备随即断开。设备在此之前没有发送任何身份信息；
- **服务器认证设备**：握手结束时服务器得到设备静态公钥 `rs_dev`，检查设备证书中的 `dh_pub == rs_dev`、证书有效、未吊销、`key_gen` 等于数据库中的当前值。一机一密首次登录时直接用数据库中预存的公钥比对；
- **身份保密**：设备号、设备公钥都在服务器认证通过之后才加密发送，中间人或 CDN 看不到"这是哪台设备"；
- **重放**：每次握手双方都有新的临时密钥，录下的握手消息无法重放，不需要额外的随机数和时间戳；
- **前向安全**：服务器静态私钥日后泄露，也解不开以前录下的信令；
- **信令连接只承载信令**：数据中转不经过信令连接，而是走 UDP 中转或独立的 WS 中转连接（第 10 节），避免大流量数据阻塞信令；
- **设备时钟**：没有 RTC 的设备启动时时钟可能是 1970 年。设备时钟早于固件构建时间时，以固件构建时间作为当前时间的下限来检查证书有效期；登录成功后以 `welcome.time` 校准；
- **WebSocket 升级请求中不携带**设备号、令牌等任何身份信息。

客户端连接服务器的方式完全相同，`login` 中带客户端证书（注册账户）或只有客户端公钥（匿名，公钥就是握手中的静态公钥）。

登录不依赖服务器端会话状态：设备重连时可以登录服务器列表中的任意一台，由共享存储中的路由表记录它所在的服务器。同一设备的新连接替换旧连接（5.4），跨服务器时由新服务器通知旧服务器关闭旧连接。

### 7.3 保活与重连

- 设备每 25 秒发一次 WebSocket ping（保持 NAT 映射），服务器 60 秒收不到任何消息就断开；
- 断线重连采用指数退避加随机抖动（1 秒起，上限 60 秒），避免服务器重启后所有设备同时涌入；
- 当前服务器连续失败时按服务器列表换下一台（7.5）。

### 7.4 服务器之间

服务器之间用 WebSocket over mTLS 互连，证书由内部 CA 签发，与对外证书体系无关。mTLS 之内再做与设备相同的 Noise_XK（prologue `"npf-mesh-v1"`），双方的静态密钥就是签名服务器列表中的 `dh_pub`：主动连接方用列表中对方的公钥，接收方核对对方的公钥就是列表中该服务器（编号取自对方证书）的公钥。偷到某台服务器的 mTLS 证书而没有它的 Noise 私钥，或者不在签名列表中的服务器，都连不进来；信令同样以 Base64url 编码的 Noise 密文、text 消息传输。服务器之间**只转发信令，不转发数据**：一个会话的双方直接连到同一台中转服务器。路由、共享存储与中转服务器的选择属于平台的多服务器设计。

### 7.5 服务器列表

设备与客户端靠这份列表找到信令接入点、探测服务器和中转服务器，并取得它们的 Noise 静态公钥。列表由离线密钥签名，经多种渠道下发，任何渠道都不需要可信。信令消息的字段见 [signaling.md](../protocol/signaling.md) 的"接入与服务器列表"一节。

**格式**

```
blob    = ver(1)=1 | flags(1) | inter_len(2) | inter_cert | payload_len(4) | payload | sig(64)
sig     = Ed25519(列表签名密钥, "npf-serverlist-v1" | payload)
inter_cert = 中间证书（3.2 的 type 1），由根密钥签发，授权其签发服务器列表
payload = UTF-8 JSON
```

签名针对 payload 的**原始字节**，验签通过后再解析这些字节，不需要规范化 JSON，设备复用信令的 JSON 解析器（受信令的大小、深度等约束）。整个 blob 在传输时用 Base64url 编码，看上去是随机字节。

```json
{"serial": 1791100000, "issued": 1791100000, "expires": 1793692000, "full": true,
 "servers": [
   {"id": 17, "region": "cn-east", "prio": 1, "weight": 10, "kind": "direct",
    "ws": ["wss://a.example.com/x", "wss://203.0.113.5:443/x"],
    "dh_pub": "<32 字节，Base64url>",
    "relay": true},
   {"id": 100, "kind": "cdn", "prio": 2, "weight": 10, "ws": ["wss://cdn.example.net/y"], "dh_pub": "..."}
 ],
 "sources": {"doh": ["_n.example.com", "_n.example.org"],
             "https": ["https://bucket.oss.example/l.bin", "https://r2.example/l.bin"]}}
```

| 字段 | 说明 |
|---|---|
| `serial` | 单调递增的版本号，取发布时的 Unix 秒 |
| `issued`、`expires` | 签发时间与有效期（默认 30 天） |
| `full` | `false` 表示精简的种子列表（只含少数接入点，用于 DNS 渠道） |
| `servers[].id` | `server_id`，中转分配等处用它引用服务器 |
| `prio`、`weight` | 选择顺序：先按 `prio` 分组，组内按 `weight` 随机 |
| `kind` | `direct`（直连）或 `cdn`（CDN 接入点，源站共享一把 `dh_pub`，见 13.2） |
| `ws` | WSS 地址，同时给域名和纯 IP：域名被封时纯 IP 可用，IP 被封时 CDN 接入点可用 |
| `dh_pub` | Noise 静态公钥（7.2 的 `rs`） |
| `relay` | 是否提供中转 |
| `sources` | 外部更新渠道本身。渠道被封时，通过发布新列表更换渠道，不需要升级固件 |

大小上限：完整列表 64 KiB，种子列表 2 KiB。

**设备的接受条件**

1. 中间证书能用固件内置的根公钥验证，并且授权签发服务器列表；`sig` 能用中间证书中的公钥验证；
2. `serial` **大于**本地保存的版本（防回滚：不会被引回已经被封或已经下线的服务器）。完整列表与正在使用的种子列表比较时，`serial` **相同**也接受：同一次发布签发的两份列表 `serial` 相同（见下文发布流程第 2 步），完整列表应当替换种子列表；因此种子列表的 `serial` 不能大于同一次发布的完整列表；
3. 种子列表（`full = false`）只在本地没有完整列表、或本地列表中的服务器全部连不上时使用，不替换本地保存的完整列表。

接受后先写临时文件再 rename，原子替换本地保存的列表。固件内置的列表保留作为最后的退路；固件升级后，内置列表同样按 `serial` 比较。

**有效期**（D15）：过期的列表**仍可用于连接**。安全性不依赖有效期，冒牌服务器过不了 7.2 的 Noise 握手；有效期只用来提示列表陈旧：本地列表已过期时，设备在登录成功前就并行查询外部渠道。离线很久的设备如果只认未过期的列表，就可能再也连不上。设备时钟不可信时（例如没有 RTC），以固件构建时间作为当前时间的下限。

**下发渠道**

| 渠道 | 何时使用 | 说明 |
|---|---|---|
| 固件内置 | 首次启动、本地存储损坏 | 编译时打包当时最新的完整列表 |
| 登录比对 | 每次登录 | `login` 中带本地 `serial`，服务器有更新的版本时在 `welcome` 中附上 |
| 在线推送 | 发布新列表时 | 服务器向在线连接推送 `server_list`，在 10 分钟内随机打散 |
| DoH 查询 TXT 记录（D14） | 列表中的服务器全部连不上超过 10 分钟，或本地列表已过期 | 查询 `sources.doh` 中的域名，内容为种子列表 |
| HTTPS 静态文件（D14） | 同上，与 DoH 并行 | 下载 `sources.https` 中的文件，内容为完整列表 |

- **DoH**：按 RFC 8484 的 GET 方式（`/dns-query?dns=<DNS 报文的 Base64url>`），直接以 IP 访问多家公共 DoH 服务，不需要先解析域名：阿里 `223.5.5.5`、腾讯 `1.12.12.12`、Cloudflare `1.1.1.1`、Google `8.8.8.8`。TXT 记录的内容是种子列表 blob 的 Base64url，按 DNS 的规定切成多个不超过 255 字节的字符串，接收方顺序拼接；
- **HTTPS 静态文件**：放在国内与海外各一家对象存储（建议阿里云 OSS 与 Cloudflare R2），内容为完整列表的 blob；
- **两种外部渠道都不需要可信**：内容有签名，DoH 服务商、对象存储、中间人都篡改不了，最多是拿不到。因此下载时同样不校验 TLS 证书（D5），也不怕 DNS 污染；
- DoH 和静态文件的下载复用 WSS 的 TLS 与 HTTP 代码（一个最小的 HTTP/1.1 GET），不引入新的依赖；
- 外部渠道按指数退避重试（1 分钟起，上限 1 小时），各渠道之间随机顺序。

**发布流程**（运维）

1. 先部署并启动新服务器，再发布列表；
2. 用 `npf-admin serverlist`（种子列表加 `-txt` 输出 TXT 字符串）和离线的列表签名密钥签发完整列表与种子列表，`serial` 取当前 Unix 秒；
3. 更新所有服务器的配置（用于登录比对和在线推送）、DoH 的 TXT 记录、各个静态文件；
4. 从列表中移除的服务器继续运行至少 7 天，等在线设备基本都完成登录比对后再下线；
5. 即使没有变化，也每周重新签发一次，使在线设备的列表始终在有效期内。

**设备怎样使用列表**

- 按 `prio` 分组，组内按 `weight` 随机选择，同时向两个接入点发起连接，先完成 Noise 握手的留下，另一个关闭；
- 连接失败按 7.3 退避，依次换下一个；某个接入点在本地连续失败 3 次，降低其优先级 1 小时；
- 服务器可以在 `welcome` 中或用 `redirect` 事件让设备改连另一台（负载均衡、维护），**目标必须在签名列表中**，被攻破的服务器也只能把设备引到列表内的服务器；
- 客户端（App、桌面端）使用同一份列表、同一套机制。

## 8. 客户端身份与授权

### 8.1 客户端身份（D2）

- 客户端首次运行时本地生成 `seed`（同 3.1），它就是客户端的身份；`client_id = BLAKE2b(dh_pub)[0..7]`。用 DH 公钥而不是签名公钥派生，是因为服务器从 Noise 握手（7.2）只能得到 DH 公钥：匿名客户端不出示任何证书，服务器也要能算出它的 `client_id`。同一公式对节点同样适用，称为公钥指纹 `fp`，用于 8.3 的已配对列表；
- **匿名使用（默认）**：不需要注册账户。客户端连接服务器时用同样的 WSS + 7.2 的 Noise 握手，`login` 中不带证书，身份就是握手中的客户端静态公钥，服务器按 `client_id` 与源 IP 限流；
- **匿名客户端不能使用数据中转**（D6）：只经服务器交换信令和 E2E 握手消息，数据只走 P2P。打洞失败时连接失败，客户端提示"登录账户后可以使用中转"；
- **注册账户（可选）**：名字是昵称，不唯一、不用于登录。登录方式有三种：密码（以**已验证**的邮箱或手机号作登录名，至少一个；手机号第一版只支持 +86，短信验证后生效）、Google、微信扫码。Google 与微信首次登录自动注册。一个账户可以绑定多种登录方式，至少保留一种，不自动合并账户。登录后服务器签发客户端证书（type 5，绑定 `account_id` 与客户端公钥，有效期 30 天，自动续签），一个账户可以有多个客户端（手机、电脑）；
- **修改账户密码**：吊销该账户在其他客户端上的客户端证书并关闭它们的信令连接（它们需要重新登录），已经建立的数据会话不断开；
- **注销账户**：用户可以在客户端注销账户（需要再次验证密码或已绑定的登录方式）。平台解除该账户名下全部设备的所有者关系（设备变为没有所有者，等同于逐台解绑，8.2）、撤销它接受的全部分享、删除其公网映射与托管客户端、吊销其全部客户端证书，然后删除账户记录。该账户注册的控制台节点保留编号与证书，但没有所有者（8.5）。应用商店对带注册功能的应用普遍要求提供注销入口。

用户输入设备号和口令的流程（匿名或已登录都一样）：

```
客户端                      服务器                           设备
 │ call{设备号, 握手首条消息} ──► 服务器闸门（8.3）
 │                           ──► incoming{call_id, client_id, account_id?}
 │ ◄────── CPace + Noise 口令配对（9.3），经服务器中转 ──────► │ 被叫闸门：验证口令
 │ 固定设备公钥                                               │ 客户端公钥加入授权列表
 │ 之后：Noise IK 直接连接（9.4），不再需要口令
```

### 8.2 账户与设备信息（D2、D3）

用户注册账户后，可以把设备绑定到账户，服务器保存"我的设备"：

- **绑定方式**：已登录的客户端用设备号和口令配对成功后，先向平台申请一次性挑战，再经端到端通道请设备对绑定声明签名 `bind = Ed25519(device_key, "npf-bind-v1" | LE64(设备号) | LE32(key_gen) | LE64(account_id) | operation_id(16) | challenge(16) | LE64(expires))`，经客户端提交给服务器。服务器只接受设备签名、挑战匹配、未过期的绑定声明，**不能仅凭设备号就把设备加到账户下**。设备签署时只把该账户记为"待确认的所有者"，收到平台的确认（signaling.md 的 `bind_committed`）后才正式记录：客户端可以让设备签署任意 `account_id`，但平台只接受与请求账户一致的声明，设备不能凭客户端的声明就认定所有者；
- **服务器保存的设备信息**：设备号、备注名、厂商与型号、固件版本、在线状态与最后在线时间、绑定时间、设备公钥与 `key_gen`；不保存口令、不保存 NAS 上的任何数据；
- **托管信任（D3，默认开启）**：账户里其他已登录的客户端访问已绑定的设备时免口令：服务器下发设备证书（其中有设备公钥），同时签发访问授权 `grant`，二进制编码为 `ver(1)=1 | kind(1) | 编号(8) | 主叫 dh_pub(32) | account_id(8) | issued(4) | expires(4) | tlen(2) | targets | issuer_key_id(4) | sig(64)`，`sig = Ed25519(中间证书私钥, "npf-grant-v1" | sig 之前的全部字节)`，整数小端，`kind = 1`；托管客户端的 grant `kind = 2`、签名域为 `"npf-grant-hosted-v1"`，`targets` 为若干 `host_len(1) | host | port(2)`（8.4）。被叫用自己证书链中的中间证书验证；设备在握手中验证 `grant`（签名、设备号是自己、`dh_pub` 等于 IK 消息 1 中的主叫静态公钥、未过期、`issued` 晚于该账户最近一次撤销）后接纳该客户端。`grant` 的有效期为 **10 分钟**，主叫在每次呼叫前用信令 `grant_get` 取得被叫证书与 `grant`，不长期保存：这样撤销对新呼叫几乎立即生效，不依赖撤销通知是否送达设备。设备检查时间时允许 5 分钟的时钟偏差。这种方式信任服务器，风险见 9.2；
- **所有者**（D18）：每台设备只有一个所有者。设备没有所有者时，第一个完成绑定的账户成为所有者；设备已有所有者时，绑定请求被拒绝，其他账户只能通过分享成为访问者。配对口令只证明访问资格，不授予管理权。设备在本地记录所有者的 `account_id`，拒绝为其他账户签署绑定声明；
- **角色**：所有者可以连接、改备注、分享、撤销分享、解绑、创建公网映射（8.4）、允许某个访问者创建公网映射；访问者只能连接，得到所有者允许后也能在这台设备上创建公网映射（D24）；
- **分享**：所有者生成一次性邀请码（有效期 24 小时），被分享者登录后接受，成为访问者，同样走托管信任。用邀请码而不是按邮箱或手机号查找账户，不会泄露某个账户是否存在；
- **解绑**（即"删除设备"）：所有者在客户端解绑，或者设备管理员在 NAS 管理界面**重置所有者**。解绑后平台停止为该账户及其访问者签发 `grant`，并通知设备撤销（下一条）。解绑不注销设备身份，也不影响用口令配对过的客户端（它们在设备本地的授权列表中）；
- **撤销的生效**：解绑或撤销分享时，平台向设备发送撤销通知 `revoke{account_id, before}`：设备记下"该账户在 `before` 之前签发的 `grant` 一律无效"，并断开经该账户 `grant` 接入的会话；所有者解绑时通知中还带 `owner: true`，设备同时清除本地记录的所有者（否则下一个账户绑定时设备会拒绝签署）。设备离线时，通知在它下次登录后执行。因为 `grant` 只有 10 分钟有效期，撤销通知主要用于断开进行中的会话；设备只需为每个账户保存最近一次的 `before`。

### 8.3 两道授权闸门

| 闸门 | 位置 | 作用 | 能否被恶意服务器绕过 |
|---|---|---|---|
| 服务器闸门 | 服务器，建立会话之前 | 挡住滥用：限流、防骚扰、控制中转成本 | 能 |
| 被叫闸门 | 设备，E2E 握手时 | 最终决定谁能访问 | 不能 |

**服务器闸门**：因为设备号 + 口令就能访问（D2），任何客户端都可以请求会话，服务器闸门只负责限流：

- 每个设备：每分钟最多 10 个来自未配对客户端的会话请求（已配对的客户端不受此限）；设备处于口令锁定期间，服务器直接拒绝未配对客户端；
- 每个 `client_id`、每个源 IP：每小时最多尝试 30 个不同的设备号（与第 6 节的防扫描一致）；
- **匿名客户端**（D6、D7）：不能使用数据中转；每天最多配对 10 次，按 `client_id` 和源 IP 分别计数（`client_id` 可以随意重新生成，只按它计数挡不住攻击者），超出后当天拒绝其配对请求。已配对设备的日常连接（9.4）不计入配对次数；
- **注册账户**：中转流量计入该账户（10），配对次数不设每日上限，只受设备的口令锁定约束。

设备把已配对主叫的公钥指纹同步给服务器（信令 `paired_sync`，只有指纹 `fp = BLAKE2b(dh_pub)[0..7]`，没有秘密；登录后发一次完整列表，本地列表变化时再发），服务器据此区分"已配对"和"未配对"的请求：主叫连接的静态 DH 公钥就是 Noise 握手得到的 `rs`，服务器算出它的 `fp` 与列表比对即可，节点和纯客户端用同一个公式。列表存在中心数据库并缓存到共享存储，主叫所在的服务器也能查到。口令锁定状态同样由设备上报（`lock_report{locked_until}`）。

**被叫闸门**：在 E2E 握手中，满足以下任一条件才接纳：

1. 客户端静态公钥在本地授权列表中（已配对）；
2. 口令配对成功（9.3）；
3. 托管信任开启，且客户端出示了有效的 `grant`（8.2）。

本地授权列表以设备为准，管理员可以在 NAS 管理界面（控制台节点为控制台）查看、命名和删除；这些设置只能在本地修改（D21）。

列表只在握手时检查，所以删除一项（`unpair`、`passwd --clear`、本地改了状态文件）或关掉托管信任（`hosted_trust 0`）时，设备立即结束列表不再允许的会话：被删公钥的会话（包括配对后还开着的那次配对会话），关掉托管信任时所有凭授权进来的会话；并立即把新列表同步给服务器（`paired_sync`）。否则被移除的客户端只要不断开，就能一直用下去。

每个主叫公钥在一个设备上同时最多 4 个会话（多了回 `busy`），设备上所有会话由对端打开的子链路合计不超过描述符上限的一半、接收窗口合计不超过 256 MiB（超过的新子链路被拒，窗口不再增大）：一个已配对或持授权的访问者占不满设备的会话、描述符和内存。

**口令失败的限制**：每个设备连续失败 5 次锁定 15 分钟，之后每次失败锁定时间翻倍，上限 24 小时，配对成功或改口令后重新计数；锁定状态同步给服务器闸门。锁定按设备本地时钟设置和检查（不用平台下发的时间：设备时钟落后或平台给的时间超前都不能让锁定失效），上报时换算成平台时间；锁定开始时已在进行的配对，到第 3 步时再检查一次，不再给它们猜测的机会。锁定针对设备而不是客户端，攻击者换 IP、换客户端也绕不过去。代价是攻击者可以借此让合法用户暂时无法用口令配对；已配对的客户端和托管信任的客户端不受影响。

### 8.4 平台公网映射（托管客户端，D17）

frp 方式的访问：设备上的某个服务映射到平台服务器的一个公网端口，外部访问者不需要安装 NPF 客户端，直接连接这个端口即可。实现方式是在平台上运行一个**托管客户端**：

```
外部访问者 ──TCP──► 边缘服务器的公网端口
                    托管客户端（NPF 的 C 客户端，托管模式）
                      │ 每条连接一条子链路：SOCKS5 CONNECT 映射目标
                      │ 与设备之间是普通的 NPF 会话（托管信任，端到端加密到托管客户端为止）
                      ▼
                    设备 ──► NAS 上的目标服务
```

- **托管客户端就是 NPF 客户端**：运行在边缘服务器上的 `npf-hosted` 程序（基于 libnpf，与 `npf-server` 部署在同一台机器上）为每个有公网映射的账户运行一个 libnpf 实例，即该账户的托管客户端。它像普通客户端一样登录信令、呼叫设备、建立数据通道，用端口映射的方式（data-channel.md 第 7 节，只有 `-L` 方向）把公网端口上的连接转成子链路。Go 服务器不需要实现 AnLiu；
- **托管服务的身份**：`npf-hosted` 自己有一把密钥，以 `role = hosted` 登录；服务器只接受配置 `hosted_keys` 中列出的公钥。它登记公网地址与端口范围（signaling.md"托管服务"），只能登记和为自己的账户申请令牌，不能做其他任何事；
- **托管客户端的身份**：每个（账户, 托管服务）一个，密钥在边缘服务器上本地生成，不进数据库。第一次由托管服务向平台申请该账户的一次性令牌（5 分钟有效，HMAC，只在该账户在这个托管服务上有公网映射时签发），托管客户端凭令牌与自己的密钥证明换取客户端证书（type 5），证书绑定该账户的 `account_id`，扩展中标记 `hosted = 1`；之后用这张证书登录。它的连接只能做呼叫、拉取和上报自己的映射、取 `grant`、报告流量，不能修改账户、设备或分享：它持有账户的证书，而所在的机器面向互联网；
- **授权**：所有者能创建公网映射，所有者允许的访问者也能（D24，`share_set` 的 `public`；默认不允许）。访问者的映射计入它自己的套餐，由它自己账户的托管客户端执行；所有者收回允许或撤销该访问者时，平台删除它在这台设备上的公网映射并释放端口（已签发的 `grant` 最多再有效 10 分钟，端口当即关闭）。托管客户端用托管信任连接设备，平台为它签发的 `grant` 使用单独的域分隔 `"npf-grant-hosted-v1"`，并带上该设备上所有公网映射的目标列表。设备只允许托管客户端打开列表中的目标，其他 `CONNECT` 一律回 `REP = 02`。映射增删后平台签发新的 `grant`，托管客户端在隧道控制通道上用 `grant_update` 出示（signaling.md"隧道内控制消息"），设备验证后替换目标列表，不需要重建会话；
- **设备侧没有单独的开关**（D23）：是否把服务暴露到公网由所有者在客户端创建映射时自行决定；公网映射只依赖托管信任，托管信任关闭时不可用。托管客户端在设备本地的客户端列表中显示为"平台公网映射"，管理员可以随时撤销；
- **数据路径**：托管客户端在有公网 IP 的服务器上（画像为 `open`），设备向它打洞几乎总能成功，通常不经过中转；UDP 不通时走 WS 中转；
- **信任边界**：外部访问者不运行 NPF，数据必须在平台上解密后才能交给公网连接，**平台能看到经公网映射的全部数据**。这是公网访问的固有代价，信任关系与托管信任相同。客户端在创建映射时明确提示：服务将暴露在公网，任何人都能访问，建议目标服务自带认证与 HTTPS；
- **访问控制**（第一版）：可选的来源 IP 白名单；除此之外与 frp 相同，不做认证；
- **计费与限额**：经公网映射的流量计入所有者账户，由托管客户端计数并报告（`usage_report`），**全部计费，没有中转的免费前 15 秒**；托管客户端的呼叫若再经中转，中转字节只记录不重复计费。公网映射的个数、每个映射每个方向的速率、能否自选端口由账户的套餐决定（免费级没有公网映射，更高的级别可以自选端口），流量计入账户的月额度（signaling.md"流量额度"）；
- **运行位置**：创建时选定一个托管服务（优先该账户已经在用的，其次设备当时所在服务器上的），公网入口固定在那里。设备之后换到其他服务器时托管客户端不迁移，照常经跨服务器的呼叫路由连接设备。

### 8.5 节点模型（D19）

控制台方式下，"客户端"和"设备"是等价的：同一个 C 程序既能呼叫别人，也能被呼叫。为此按能否被呼叫划分参与方：

| 类别 | 例子 | 编号 | 身份与证书 | 能呼叫 | 能被呼叫 |
|---|---|---|---|---|---|
| **节点** | NAS 设备端；PC、服务器上的控制台客户端 | 9 位编号（第 6 节），NAS 设备与控制台节点共用同一个编号空间 | 节点证书（3.2 的 type 3） | 能 | 能 |
| 纯客户端 | 桌面 GUI、手机 App、匿名客户端 | 没有，只有 `client_id` | 客户端证书（type 5）或匿名 | 能 | 不能 |

- **角色按呼叫区分**：一次呼叫中，发起方为**主叫**（节点或纯客户端），被呼叫的节点为**被叫**。第 9 节的端到端加密、[data-channel.md](../protocol/data-channel.md) 的数据通道都按主叫 / 被叫定义；NAS 设备端也可以主动呼叫其他节点，例如 NAS 之间的备份；
- **被叫的授权与设备完全相同**：任何节点都有配对口令（本地生成）、本地授权列表、托管信任开关、所有者与分享、撤销（8.2、8.3）。控制台节点在控制台中显示配对口令和授权列表，相当于 NAS 管理界面；
- **编号的取得**：
  - NAS 设备端：凭厂商凭证注册（第 4、5 节），可以出厂预写；
  - 控制台节点：**必须先登录账户**，再以该账户注册编号（信令 `node_enroll`），节点自动归这个账户所有。没有登录账户的控制台程序不能注册，只能作为纯客户端去呼叫别人。这样，批量申请编号必须先有账户，并受每个账户的数量上限约束；
- **注销**：所有者可以注销控制台节点，平台吊销其节点证书，编号作废（与第 6 节一致，不再分配给别的节点）。NAS 设备端的身份由厂商凭证体系管理（第 5 节），不能这样注销；
- **账户会话**：控制台节点用节点身份登录，账户相关的操作（设备列表、注册编号等）需要连接上另有账户会话：平台为同一把密钥签发客户端证书（type 5），节点在 `login` 中与节点证书一起出示（signaling.md"接入与服务器列表"）。NAS 设备端没有账户会话，被攻破的 NAS 拿不到所有者账户的管理权限；
- **计费**：中转流量计入主叫的账户（第 10 节）。主叫是节点时，计入该节点所有者的账户；节点没有所有者时与匿名客户端相同，只能 P2P；
- 桌面 GUI 与手机 App 不做节点：手机无法长期在线等待被叫，后台保活也做不到。

## 9. 端到端加密（R4）

### 9.1 原则

主叫与被叫各自有一把静态 X25519 密钥（身份），每次连接再各自生成一把临时密钥，通过 Noise 握手算出会话密钥。握手消息经服务器中转，但服务器没有任何一方的私钥，算不出会话密钥。唯一的风险是服务器在首次连接时**冒充对方**（A2'），所以关键在于：主叫怎样确认"这把公钥确实属于我要呼叫的那个节点"。

### 9.2 首次配对：信任从哪来

| 方式 | 流程 | 防得住恶意服务器 | 状态 |
|---|---|---|---|
| **口令配对** | 用户输入编号 + 口令，双方跑 PAKE（9.3） | 能：口令从不经过服务器，服务器每次冒充只能猜一次口令 | 主要方式（D2） |
| **托管信任** | 已绑定账户的主叫凭服务器签发的设备证书和访问授权直接连接（8.2） | 不能：服务器可以签发假证书或假授权做中间人 | 默认开启（D3），被叫节点的管理员可以关闭 |
| **扫码配对** | NAS 管理界面显示二维码，内容为 `npf://pair?no=<编号>&fp=<被叫公钥指纹 16 字节>&code=<一次性配对码 16 字节>` | 能：被叫公钥指纹直接来自被叫节点的屏幕 | 可选，后续实现 |

托管信任默认开启是体验与安全的取舍：服务器（或攻破服务器的人）可以冒充被叫，诱使该账户的主叫连到假被叫上，也可以冒充账户的主叫访问被叫。NAS 管理界面中需要说明这一点，关闭后该被叫只接受口令配对过的主叫。**口令配对过的主叫在任何情况下都不依赖服务器的信任**：即使托管信任开启，主叫对已固定的被叫公钥也不接受服务器的替换（9.6）。

扫码配对中的配对码是 128 位随机数，熵足够，直接作为 Noise 的 PSK；口令配对中的口令熵低，必须先经过 PAKE。

### 9.3 口令配对

```
1. CPace（X25519 + Elligator2）
   输入：口令；sid = call_id | LE64(编号)
   G   = Elligator2(BLAKE2b-256("npf-cpace-v1" | len(口令) | 口令 | len(sid) | sid))
   Y   = X25519(y, G)，每方一条 32 字节消息
   ISK = BLAKE2b-256(key = X25519(y, Y_对方), "npf-cpace-isk-v1" | sid | Y_主叫 | Y_被叫)
   输出：ISK（口令一致时两端相同）                    经中转 1 个往返

2. Noise_XXpsk3_25519_ChaChaPoly_BLAKE2b
   psk = ISK；prologue = "npf-pair-v1" | sid
   交换并确认双方静态公钥                        经中转 1.5 个往返

3. 主叫记住"编号 → 被叫静态公钥"（固定下来）；
   被叫把主叫静态公钥加入本地授权列表，并把指纹同步给服务器闸门
```

**为什么不能直接把口令当成 Noise 的 PSK**：主动作恶的服务器可以冒充被叫和主叫完成 DH（它知道自己那一侧的所有临时密钥），然后拿着主叫发来的最后一条握手消息，离线逐个尝试口令，直到消息能解开为止。口令熵低，很快就能试出来。PAKE 的性质保证：不知道口令的一方每参与一次协议最多只能验证一个猜测，无法离线穷举。

扫码配对不需要第 1 步：以配对码作为 PSK 直接跑第 2 步，主叫再核对被叫静态公钥与二维码中的指纹是否一致。

### 9.4 日常连接

配对之后，主叫已经知道被叫的静态公钥，使用 `Noise_IK_25519_ChaChaPoly_BLAKE2b`，prologue = `"npf-conn-v1" | call_id | 编号`（`call_id` 由主叫生成，见 [signaling.md](../protocol/signaling.md)）：

- 第一条消息（主叫 → 被叫）携带主叫静态公钥（加密），被叫检查它是否在授权列表中，不在就拒绝；
- 1 个往返完成握手，可以和打洞信令并行进行。

### 9.5 会话密钥与 AnLiu

握手完成后，由 Noise 的 `Split()` 得到两把 32 字节密钥 `k1`、`k2`，派生 AnLiu 的参数：

```
anl_psk = BLAKE2b-256(key = k1 | k2, msg = "npf anliu psk v1")
conv    = LE32(BLAKE2b-256(key = k1 | k2, msg = "npf anliu conv v1")[0..3])，为 0 时取 1
role    : 主叫 ANL_ROLE_CLIENT，被叫 ANL_ROLE_SERVER
```

AnLiu 再由 `anl_psk` 派生出各方向的密钥，现有接口不需要改动。`conv` 在 AnLiu 数据报里以混淆（与认证标签异或）但不加密的形式携带，接收方据此找到连接再认证；P2P 路径上的观察者因此能把同一连接的数据报归到一起，但按五元组本来就能做到；UDP 中转路径上整个数据报在中转封装的加密里（第 10 节）。每次连接都用新的临时密钥，因此具有前向安全性：被叫或主叫的静态私钥日后泄露，也解不开以前录下的流量。

**不做中途换密钥**（D12）：AnLiu 规定单个 PSK 最多加密 2^40 个数据报（约 1.5 PB），超过后 tag 碰撞概率上升。NPF 每次连接都由握手产生新 PSK，NAS 的一条连接达不到这个量级。作为保险，一条连接两个方向合计的数据报数达到 2^36（约 96 TB）时，主叫重新握手建立新连接，AnLiu 不需要支持中途更换 PSK。

**打洞报文的密钥**（D9）分两把：

```
punch_key    : 服务器生成，经 WSS 下发（打洞文档 6.5），保护 PROBE / PROBE_ACK
nominate_key = BLAKE2b-256(key = k1 | k2, msg = "npf nominate v1")，保护 NOMINATE / NOMINATE_ACK
```

**WS 中转的记录密钥**（D13）：WS 中转不跑 AnLiu，子链路帧由两端另行加密，密钥同样只来自 `k1 | k2`，服务器算不出来：

```
k_ws[dir] = BLAKE2b-256(key = k1 | k2, msg = "npf ws tunnel v1" | dir | salt)    dir 为 "a2b"（主叫→被叫）/ "b2a"，salt 由发送方每轮新生成
```

记录格式、轮次与防重放见 [data-channel.md](../protocol/data-channel.md) 10.2。

- 探测报文用服务器下发的 `punch_key`，这样不必等 E2E 握手完成就能开始打洞；服务器知道它，最多只能伪造探测报文，让某个候选对看起来"可用"；
- 提名报文用两端自己协商的 `nominate_key`，服务器算不出来。即使服务器伪造了探测报文，也无法让双方提名一条错误的路径，路径选择完全由两端决定；
- 代价：提名要等 E2E 握手完成。握手经服务器只需 1 个往返（9.4），而打洞通常需要数百毫秒到数秒，一般不会因此变慢。

### 9.6 被叫身份变更

主叫发现被叫的公钥与固定下来的不一致（例如一型一密设备重置后换了密钥，5.3），处理方式与 SSH 的"主机密钥已变更"相同：

- 不自动连接，明确提示"被叫身份已变更，可能是对方节点被重置，也可能是有人冒充"；
- 用户重新配对（扫码或口令）后才更新固定的公钥；
- 只通过托管信任连接、从未口令配对过的主叫，如果服务器签发的新设备证书 `key_gen` 更大，可以自动接受，但仍然提示用户；口令配对过的主叫一律要求重新配对。
- 被叫重置后不认原来的配对，主叫用固定的公钥呼叫时被叫回 `unauthorized`：主叫不再重试，也不改用账户授权，提示重新配对（`pairing_lost`，2026-10-20）；用口令重新配对成功后新公钥替换旧的。

### 9.7 服务器能看到什么

| 能看到 | 看不到 |
|---|---|
| 编号、主叫账户、双方 IP 地址 | 传输的内容 |
| 连接的时间、时长、流量大小和时序 | NAS 的登录凭据、访问的文件 |
| 打洞的候选地址 | 访问口令、配对码（PAKE 不泄露口令） |
| 经公网映射（8.4）的全部数据：外部访问者不运行 NPF，数据在托管客户端上解密 | |
| 配对是否成功 | 会话密钥、被叫与主叫的私钥 |

### 9.8 直连（预共享密钥）

节点之间也可以不经平台直接连接（[data-channel.md](../protocol/data-channel.md) 第 13 节）。这时没有证书、没有服务器，信任只来自监听方设定的预共享密钥：

- 握手用 `Noise_NNpsk0`，psk 放在第一条消息之前，所以**第一条消息就需要密钥**：没有密钥的一方既不能让监听方回应，也无法从监听方得到任何可区分的报文，扫描者看不出端口上有服务。每次连接都用新的临时密钥，具有前向安全性；PSK 日后泄露，也解不开以前录下的流量，但持有 PSK 的人可以冒充任意一方（双方没有静态身份），所以 PSK 必须是高熵随机数（`npf genpsk` 生成 32 字节），不能用口令。
- 重放：同一个临时公钥 2 分钟内只建立一次会话，超过 2 分钟的消息 1 因时间戳过期被拒；重放者没有临时私钥，即使监听方回了消息 2，也算不出会话密钥。
- 资源：只有通过密钥验证的消息 1 才分配会话，每个来源 IP 限速，会话总数有上限。
- 直连会话的权限与托管信任相同，只能使用隧道（受目标策略限制），不能做绑定等管理操作。
- 密钥文件要求只有属主可读；节点同时登录平台时，直连与平台呼叫互不影响，平台看不到直连。

## 10. 中转路径（R5，下半部分）

P2P 建立之前（仅限注册账户的客户端，D6），数据经中转服务器传输。信令连接不承载数据（D13），中转有两种（协议细节见 [data-channel.md](../protocol/data-channel.md) 第 9、10 节）：

| 中转 | 何时使用 | 承载 | 端到端加密 | 服务器的认证 |
|---|---|---|---|---|
| **UDP 中转** | 默认 | AnLiu 数据报，外加中转封装（与打洞报文相同的 SIV 构造） | AnLiu | 每侧一把 `alloc_key`，按源地址认证，`seq` 防重放 |
| **WS 中转** | UDP 不通 | 独立的 WSS 连接，传输子链路帧，不跑 AnLiu | 两端另加 ChaCha20-Poly1305 记录（`k_ws`，9.5） | 连接内做与 7.2 相同的 Noise_XK 握手，按身份密钥绑定到分配 |

- **服务器不解析数据**：UDP 中转只验证并剥掉外层中转封装，里面的 AnLiu 数据报原样转发；WS 中转只看消息类型，记录原样转发。服务器篡改、注入、重放的数据会被 AnLiu 或记录层的认证拒绝，只能起到丢包或复位的效果；
- **为什么 WS 中转要另加密**：WS 中转不跑 AnLiu（避免 TCP 套 TCP），子链路帧如果直接放进 WebSocket，服务器和终止 TLS 的 CDN 就能看到全部数据。记录层的密钥只由两端的 E2E 握手派生，满足 R4；
- **中转分配**由平台在呼叫时生成，每侧单独一份 `relay_id` 和 `alloc_key`，经 Noise 加密的信令下发。`alloc_key` 只保护中转封装，泄露后不影响数据机密性（数据由 AnLiu 或记录层保护），最多导致中转被冒用而产生计费；
- 每个分配有速率上限和空闲回收时间；
- **流量计费**（D6）：会话中转的流量（双向合计）计入**发起连接的客户端的用户账户**。访问别人分享的设备时，计入被分享者（访问者）的账户，而不是设备属主；中转流量**按套餐**（D11）：账户的套餐（免费级或订阅的级别）给出每月的流量额度，中转时从中扣除；额度用完后该账户的新会话只能走 P2P，已有的中转会话立即降为低速（默认 128 kbps），保证信令和少量操作可用，同时通知用户；免费级的中转始终限速 128 kbps。规则与实现见 signaling.md"流量额度"。重放的报文被服务器丢弃，不计费。呼叫发起后的前 15 秒不计费（服务器配置 `relay_free_s`；打洞通常在此之前完成，会话随即离开中转）；每个呼叫两个方向的中转字节数和其中计费的部分记在呼叫记录中（signaling.md "呼叫记录"）。套餐的级别、额度、价格属于运营策略，由平台配置（`npf-admin plan`），不在本文范围；
- **匿名客户端没有中转**：平台不为匿名客户端的会话分配任何中转，信令连接只转发 E2E 握手消息；握手消息每个会话最多 8 条、每条不超过 512 字节，防止被用来偷偷传数据；
- P2P 打通后切换路径的过程见打洞文档第 10 节。

WS 中转段有两层加密（TLS + 记录层）：TLS 用于伪装，记录层保证服务器和 CDN 都看不到内容。UDP 中转报文没有任何明文标识，`relay_id` 只出现在密文中。

## 11. 服务器端安全

- **根密钥**离线保管，按 Shamir 秘密分享拆成 3 份，任意 2 份可以恢复；只在签发中间证书时使用；
- **在线签发密钥**放在 KMS/HSM 中，至少是加密存储、按最小权限访问，并记录每次签发；
- **服务器列表**带单调递增的版本号和过期时间，设备拒绝接受版本号更低的列表，防止回滚到已经被封或已经下线的服务器；
- **服务器被攻破的影响**：可以冒充设备或客户端，签发假证书，看到元数据；但已经配对（扫码或口令）的客户端与设备之间的会话仍然安全。这也是扫码配对和口令配对存在的意义；
- **日志**：不记录证书私钥、票据、口令等敏感信息；
- **厂商后台**：管理型号凭证的配额、吊销，上传序列号白名单和一机一密的公钥列表。

## 12. 实现要点与对其他模块的影响

### 12.1 密码学选型

| 用途 | 算法 | 设备端 / 客户端（C） | 服务器端（Go） |
|---|---|---|---|
| 签名 | Ed25519 | Monocypher（含 SHA-512 的可选模块） | `crypto/ed25519` |
| 密钥交换 | X25519 | Monocypher | `crypto/ecdh` |
| 哈希 / KDF | BLAKE2b | Monocypher | `golang.org/x/crypto/blake2b` |
| 设备 / 客户端 ↔ 服务器握手 | Noise XK，ChaChaPoly，BLAKE2b | 与 E2E 握手共用同一份 Noise 实现 | `github.com/flynn/noise` |
| E2E 握手 | Noise IK / XXpsk3，ChaChaPoly，BLAKE2b | 自己实现（基于 Monocypher，约 500 行） | 不需要 |
| PAKE | CPace（X25519 + Elligator2） | 自己实现（Monocypher 提供 Elligator2） | 不需要 |
| TLS | TLS 1.3 | mbedTLS 3.6 LTS（静态链接） | `crypto/tls` |

Monocypher 约 4000 行，单个 C 文件，CC0 / BSD-2 许可，适合嵌入到轻量的设备端。服务器不参与 E2E 握手，Go 端只需要签名验签和 7.2 的 Noise XK（响应方）。

mbedTLS 3.6 不支持 Ed25519，也没有 Elligator2，因此应用层密码学统一用 Monocypher，mbedTLS 只负责 TLS。两者分开，今后更换 TLS 库不影响应用层协议。

### 12.2 TLS 库：mbedTLS 3.6（D4）

实测（2026-09-29，mbedTLS 3.6.7，x86-64，gcc 13 `-Os -ffunction-sections -fdata-sections`，链接时 `--gc-sections`；最小 TLS 1.3 客户端程序，扣除空程序约 1 KB）：

| 配置 | 代码段 |
|---|---|
| X25519 + P-256，ECDSA 服务器证书，只支持 ChaCha20-Poly1305 | 约 136 KB |
| 同上，加 AES-128-GCM | 约 142 KB |

同样条件下 wolfSSL 5.9.4 的最小配置约 150 KB，并不更小；mbedTLS 是 Apache-2.0 许可，wolfSSL 是 GPLv3 或商业许可，对要把设备端集成进闭源固件的厂商来说，mbedTLS 更省事。ARM Thumb-2 下代码一般比 x86-64 小 20%–30%。

在同一测试中，mbedTLS 客户端（`MBEDTLS_SSL_VERIFY_NONE`，不校验证书）与 Go `crypto/tls` 服务器（自签名 ECDSA 证书）握手并收发数据成功。

配置文件放在 `third_party/mbedtls-config/npf_mbedtls_config.h`，要点：

- 只开 TLS 1.3 客户端（`MBEDTLS_SSL_PROTO_TLS1_3`、`MBEDTLS_SSL_CLI_C`），不编译 TLS 1.2 和服务器端代码；
- 密钥交换 X25519 与 P-256；服务器证书只支持 ECDSA P-256（服务器统一申请 ECDSA 证书），不编译 RSA，省下大块代码；
- 套件 ChaCha20-Poly1305（默认）；如果 NAS 的 CPU 有 AES 指令，可以编译时再打开 AES-128-GCM；
- 接收缓冲 16 KB、发送缓冲 4 KB，减小内存占用。

**版本**：mbedTLS 3.6 是 LTS 版本，官方承诺维护到 2027 年 3 月。4.x 把密码学部分拆到了独立的 TF-PSA-Crypto 项目，配置方式变化较大，届时再评估迁移。
